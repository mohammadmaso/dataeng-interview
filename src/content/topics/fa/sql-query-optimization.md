## 🎯 خلاصه

> SQL می‌گوید **چه** می‌خواهی. **optimizer** (بهینه‌ساز) تصمیم می‌گیرد **چطور** به آن برسد: از کدام ایندکس استفاده کند، کدام الگوریتم join را اجرا کند، جدول‌ها را با چه ترتیبی join کند، و فیلترها را کجا اعمال کند. `EXPLAIN` همین تصمیم را نشان می‌دهد.

- optimizer **مبتنی بر هزینه (cost-based)** است: با کمک **آمار (statistics)** جدول‌ها، هزینه‌ی پلن‌های مختلف را تخمین می‌زند و ارزان‌ترین را انتخاب می‌کند.
- بیشتر کوئری‌های کند از **تخمین‌های اشتباه** می‌آیند (optimizer فکر می‌کند ۱۰۰ ردیف است، ولی واقعاً ۲ میلیون است) یا از **شکل پلنی** که نمی‌تواند از ایندکس استفاده کند.
- ترتیب عیب‌یابی: پلن واقعی را بگیر، گره‌ای را پیدا کن که زمان یا تعداد ردیف‌ها در آن از کنترل خارج می‌شود، آمار را چک کن، sargability را چک کن، و بعد کوئری، ایندکس یا چیدمان داده را عوض کن.
- سه الگوریتم join (nested loop، hash، merge) هزینه‌ی متفاوتی دارند. اینکه پلن کدام را استفاده می‌کند، نشان می‌دهد چه چیزی لازم دارد: ایندکس، حافظه، یا ورودی مرتب.

## 🌱 از ساده شروع کنیم (مبتدی)

> **💡 تشبیه:** یک اپ نقشه. تو می‌نویسی «از خانه تا فرودگاه». اپ همه‌ی خیابان‌ها را امتحان نمی‌کند. از نقشه‌ی ترافیک (آمار) استفاده می‌کند، زمان هر مسیر را حدس می‌زند (هزینه) و یک مسیر (پلن) نشانت می‌دهد. اگر داده‌ی ترافیک قدیمی باشد، تو را از خیابانی بسته می‌فرستد.

وقتی کوئری اجرا می‌کنی، دیتابیس چهار مرحله طی می‌کند:

1. **Parse**: SQL را می‌خواند و چک می‌کند جدول‌ها و ستون‌ها وجود دارند.
2. **Rewrite**: آن را بازنویسی می‌کند (مثلاً view ها را باز می‌کند).
3. **Plan**: پلن‌های کاندید می‌سازد، هزینه‌ی هرکدام را تخمین می‌زند، و ارزان‌ترین را برمی‌دارد.
4. **Execute**: پلن انتخاب‌شده را اجرا و ردیف‌ها را برمی‌گرداند.

مرحله‌ی ۳ را با `EXPLAIN` می‌بینی. این دستور پلن را نشان می‌دهد بدون اینکه کوئری را اجرا کند. `EXPLAIN ANALYZE` کوئری را واقعاً اجرا می‌کند و زمان و تعداد ردیف واقعی را کنار تخمین‌ها می‌گذارد.

```sql
CREATE TABLE customers (id int PRIMARY KEY, city text, segment text);
CREATE TABLE orders (id bigint PRIMARY KEY, customer_id int, created_at timestamp, amount numeric);
CREATE INDEX ON orders (created_at);

EXPLAIN ANALYZE
SELECT c.city, SUM(o.amount)
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= '2026-01-01' AND o.created_at < '2026-02-01'
GROUP BY c.city;
```

پلن را از **داخل به بیرون** بخوان: خطوط تورفته‌تر زودتر اجرا می‌شوند و خروجی‌شان به خطوط بالاتر می‌رود.

## 🔧 واقعاً چطور کار می‌کند (متوسط)

### آمار و cardinality

optimizer موقع برنامه‌ریزی داده‌ها را نگاه نمی‌کند. از **آمار** استفاده می‌کند: تعداد ردیف‌ها، تعداد مقادیر متمایز، پرتکرارترین مقادیر، و histogram هر ستون. با این‌ها **cardinality** (تعداد ردیف‌ها در هر مرحله‌ی پلن) را تخمین می‌زند. یک تخمین بد در یک مرحله به همه‌ی مراحل بالایی منتقل می‌شود.

```text
Hash Join  (cost=... rows=48000) (actual time=... rows=212000 loops=1)
  -> Index Scan using orders_created_at_idx on orders o
       Index Cond: (created_at >= '2026-01-01' AND created_at < '2026-02-01')
       (rows=48000) (actual rows=212000)
```

این یک پلن ساده‌شده است. تخمین (۴۸٬۰۰۰) حدود ۴ برابر کمتر از تعداد واقعی (۲۱۲٬۰۰۰) است. در این حالت planner ممکن است nested loop انتخاب کند که برای ۴۸٬۰۰۰ ردیف خوب است و برای ۲۱۲٬۰۰۰ ردیف وحشتناک. راه‌حل معمولاً `ANALYZE` روی جدول است (به‌روزرسانی آمار)، یا آمار توسعه‌یافته وقتی دو ستون به هم وابسته‌اند، مثل `city` و `zip_code`.

### الگوریتم‌های join

| الگوریتم | بهترین حالت | نیاز دارد به | هزینه‌ی تقریبی |
|---|---|---|---|
| **Nested loop** | طرف خارجی کوچک است؛ طرف داخلی روی کلید join ایندکس دارد | ایندکس روی کلید داخلی | تعداد ردیف‌های خارجی × یک جستجوی ایندکس برای هر کدام |
| **Hash join** | join برابری است؛ یک طرف در حافظه جا می‌شود | حافظه برای جدول hash | ساخت hash روی طرف کوچک‌تر، و probe با طرف دیگر: تقریباً n + m اگر جا شود |
| **Merge join** | هر دو ورودی از قبل روی کلید join مرتب‌اند | ورودی مرتب (ایندکس هم می‌تواند ترتیب بدهد) | تقریباً n + m بعد از مرتب‌سازی |

hash join و merge join شرط join از نوع **برابری** می‌خواهند. nested loop برای هر شرطی کار می‌کند، مثل `<` یا `BETWEEN`.

hash join محدودیت حافظه دارد. وقتی جدول hash از `work_mem` (در PostgreSQL، برای هر عملیات) بزرگ‌تر شود، join به **batch** تقسیم می‌شود و روی دیسک نوشته می‌شود. `EXPLAIN ANALYZE` این را به صورت `Batches: 8` یا بیشتر نشان می‌دهد. همین برای sort هم رخ می‌دهد: `Sort Method: external merge Disk: ...kB`. این **spill به دیسک** است و اغلب دلیل پنهان اینکه کوئری ده برابر کندتر از انتظار است.

### sargable بودن شرط‌ها

شرطی **sargable** (search-argumentable) است که موتور بتواند از ایندکس یا آمار برایش استفاده کند. الگوی ضدِ رایج این است که روی ستون تابع یا محاسبه بگذاری:

```sql
-- sargable نیست: ایندکس روی created_at مستقیم قابل استفاده نیست
WHERE DATE(o.created_at) = '2026-01-15'

-- sargable است: بازه‌ی نیم‌باز روی ستون خام
WHERE o.created_at >= '2026-01-15' AND o.created_at < '2026-01-16'
```

همین قانون برای `WHERE amount * 1.09 > 100` هم هست. محاسبه را به سمت ثابت ببر: `WHERE amount > 100 / 1.09`.

### predicate pushdown و partition pruning

**Predicate pushdown** یعنی فیلتر را هرچه زودتر اعمال کنی. در پلن، فیلتر کنار scan قرار می‌گیرد، نه بالای join با یک میلیون ردیف. در فایل‌های Parquet یا ORC، موتور با آمار کمینه/بیشینه‌ای که در footer فایل است می‌تواند کل row group ها را رد کند. در view یا subquery، optimizer وقتی امن باشد `WHERE` بیرونی را به داخل می‌برد. از `LIMIT`، window function ها و تابع‌های volatile عبور نمی‌کند.

**Partition pruning** یعنی رد کردن کل partition ها. اگر `orders` بر اساس ماهِ `created_at` partition شده باشد، کوئری با `WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01'` فقط یک partition را می‌خواند. در `EXPLAIN` فقط همان partition در scan دیده می‌شود. قرار دادن کلید partition داخل تابع اغلب مانع pruning می‌شود، همان‌طور که مانع استفاده از ایندکس می‌شود.

### materialized view

**materialized view** نتیجه‌ی یک کوئری را روی دیسک ذخیره می‌کند تا خواننده‌ها دوباره محاسبه نکنند. در PostgreSQL، `REFRESH MATERIALIZED VIEW` آن را دوباره محاسبه می‌کند و خواننده‌ها را بلاک می‌کند. `REFRESH ... CONCURRENTLY` اجازه می‌دهد خواننده‌ها ادامه دهند، ولی یک ایندکس unique روی view لازم دارد. معامله‌ی آن **تازگی** در برابر **هزینه‌ی محاسبه** است: view فقط تا آخرین refresh به‌روز است.

## 🧠 عمق و trade-offها (سنیور)

**یک مسیر عیب‌یابی برای «این کوئری کند است»:**

1. **پلن واقعی را بگیر** روی داده‌ی واقعی‌نما (`EXPLAIN (ANALYZE, BUFFERS)` در PostgreSQL). به پلن فقط تخمینی اعتماد نکن.
2. **گره‌ای را پیدا کن که زمان یا ردیف‌ها از هم جدا می‌شوند.** `rows=` (تخمین) را با `actual rows=` (واقعی) مقایسه کن. اختلاف ۱۰ برابر یا بیشتر اولین مظنون است.
3. **آمار را چک کن.** جدول‌ها آخرین بار کی `ANALYZE` شده‌اند؟ بارگذاری‌های حجیم اغلب آمار را کهنه نگه می‌دارند تا `ANALYZE` اجرا شود.
4. **sargability و کلیدهای join را چک کن.** تابع روی ستون، cast ضمنی (مقایسه‌ی `int` با `text`) و کلیدهای join با نوع متفاوت، همگی پلن بد می‌سازند.
5. **spill را چک کن.** `Batches` بیشتر از ۱ یا `external merge Disk` یعنی حافظه برای آن عملیات کم است.
6. **فقط بعدش چیزی را عوض کن:** کوئری را بازنویسی کن، یک ایندکس هدفمند اضافه کن (ببین [[sql-indexing]])، partitioning را تغییر بده، یا داده را از قبل جمع کن و در یک جدول بگذار.

**موتورها فرق دارند.** Spark با adaptive query execution (AQE) در زمان اجرا استراتژی join و تعداد partition ها را عوض می‌کند، و می‌تواند طرف کوچک را broadcast کند به‌جای shuffle (ببین [[shuffle]]). اما کلید join که skew دارد باز هم یک task را کند می‌کند، پس ریشه‌ی مشکل [[data-skew]] است نه الگوریتم join. Trino و BigQuery و Snowflake پروفایل کوئری با زمان هر عملگر می‌دهند. ClickHouse به جای B-tree از sparse index و part ها استفاده می‌کند. قبل از نقل یک تنظیم خاص، مستندات موتور و نسخه‌ی خودت را ببین.

**ترتیب join.** برای join های زیاد، ترتیب مهم است. optimizerهای امروزی ترتیب‌های زیادی را بررسی می‌کنند، ولی جستجو برای تعداد join های خیلی زیاد محدود است و ورودی آن خود تخمین‌ها هستند. قبل از اینکه با hint پلن را تحمیل کنی، به optimizer آمار خوب بده و join های غیرضروری را حذف کن.

**plan hint.** بعضی موتورها اجازه‌ی تحمیل پلن می‌دهند (مثلاً با extension یا `pg_hint_plan`). این را آخرین راه بدان: hintی که امروز کار می‌کند بعد از رشد داده ممکن است غلط شود.

**پایش.** کوئری‌های کند را از لاگ سرور یا view آمار کوئری پیگیری کن، و تغییر پلن در طول زمان را هم. پلنی که بعد از تغییر داده برمی‌گردد، یکی از علل رایج «دیروز سریع بود» است.

**کی کوئری را بهینه نکنیم.** اگر همان aggregate سنگین هر دقیقه برای هر داشبورد اجرا شود، یک جدول یا view ماتریالایزشده که هر ساعت refresh می‌شود اغلب بهتر از سریع‌تر کردن هر اجراست.

## 🧪 امتحان کن

از PostgreSQL نسخه‌ی ۱۳ به بعد با اسکیمای بالا استفاده کن. حدود یک میلیون سفارش و ۱۰۰٬۰۰۰ مشتری با `generate_series` وارد کن، و بعد روی هر دو جدول `ANALYZE` بزن.

1. کوئری `EXPLAIN ANALYZE` بخش مبتدی را اجرا کن. الگوریتم join را نام ببر و بگو کدام طرف build side است.
2. فیلتر را به `WHERE DATE(o.created_at) = '2026-01-15'` تغییر بده. گره‌ی scan را قبل و بعد از بازنویسی به بازه‌ی نیم‌باز مقایسه کن.
3. `SET work_mem = '64kB';` را اجرا کن و بعد یک کوئری که همه‌ی سفارش‌ها را بر اساس `amount` مرتب می‌کند با `EXPLAIN ANALYZE` بررسی کن. خط `external merge` و اندازه‌ی دیسک را پیدا کن.

**۱.** برای بازه‌ای که ردیف زیادی را مطابقت می‌دهد، پلن معمولاً طرف کوچک‌تر (`customers` یا `orders` فیلترشده بعد از index scan) را hash می‌کند و با طرف دیگر probe می‌زند. اگر ایندکس روی `customers(id)` باشد و سفارش‌های مطابق خیلی کم باشند، nested loop برنده می‌شود. پلن تو ممکن است فرق کند؛ نکته این است که عملگر و build side را نام ببری.

**۲.** نسخه‌ی تابعی معمولاً یک sequential scan روی `orders` نشان می‌دهد (یا فیلتری روی scan با تعداد ردیفی نزدیک به کل جدول). نسخه‌ی بازه‌ای `Index Scan` یا `Bitmap Index Scan` روی `orders_created_at_idx` نشان می‌دهد. ردیف‌های خروجی یکسان‌اند.

**۳.** با `work_mem` برابر ۶۴ کیلوبایت، sort در حافظه جا نمی‌شود. پلن `Sort Method: external merge  Disk: ...kB` نشان می‌دهد. با `RESET work_mem;` برگردان. اندازه‌های دقیق به داده بستگی دارد.

## 💬 گوشه‌ی مصاحبه

**سؤال: «این کوئری کند است. قدم‌به‌قدم عیب‌یابی‌اش را توضیح بده.»** جواب متوسط: «`EXPLAIN ANALYZE` می‌زنم، دنبال sequential scan روی جدول‌های بزرگ می‌گردم، و چک می‌کنم ایندکس‌ها استفاده می‌شوند.» جواب سنیور: «اول پلن واقعی را روی داده‌ی واقعی‌نما می‌گیرم، نه پلن تخمینی. اولین گره‌ای را پیدا می‌کنم که تخمین و تعداد واقعی ردیف‌ها اختلاف بزرگی دارند، چون هر گره‌ی بالاتر تخمین اشتباه را به ارث می‌برد. تاریخ آخرین به‌روزرسانی آمار، تابع روی ستون‌های فیلتر، عدم تطابق نوع در کلیدهای join، و spill به دیسک را چک می‌کنم. فقط بعد از آن ایندکس اضافه می‌کنم یا کوئری را عوض می‌کنم، و اصلاح را روی پلن و روی داده‌ی هم‌اندازه‌ی production تأیید می‌کنم.»

**سؤال: «چه وقتی optimizer به‌جای hash join، nested loop انتخاب می‌کند؟»** وقتی ورودی خارجی کوچک است و طرف داخلی روی کلید join ایندکس دارد، پس هر ردیف خارجی یک جستجوی سریع می‌شود. hash join وقتی برنده است که هر دو طرف بزرگ باشند و جدول hash در حافظه جا شود.

**سؤال: «چرا `WHERE DATE(col) = ...` کوئری‌ام را کند می‌کند؟»** تابع ستون را هم از ایندکس و هم از آمار پنهان می‌کند. در نتیجه optimizer انتخاب‌گری را بد تخمین می‌زند و جدول را اسکن می‌کند. بازه‌ی نیم‌باز روی ستون خام هر دو مشکل را حل می‌کند.

> **🎤 این را در مصاحبه بگو:** «از روی پلن واقعی عیب‌یابی می‌کنم، نه از حدس. دنبال اولین گره‌ای می‌گردم که تخمین ردیفش غلط است، چون پلن از همان‌جا مسیر را گم می‌کند. بعد علت را رفع می‌کنم: آمار، sargability، کلیدهای join، حافظه، یا چیدمان داده.»

## ⚠️ اشتباهات رایج

> **⚠️ مراقب باش:** `EXPLAIN` را بدون `ANALYZE` بخوانی و زمان‌هایش را واقعی فرض کنی. `EXPLAIN` ساده فقط تخمین planner را نشان می‌دهد.

> **⚠️ مراقب باش:** قبل از نگاه کردن به پلن، ایندکس اضافه کنی. اگر علت تخمین اشتباه یا تابع روی ستون باشد، ایندکس جدید ممکن است اصلاً استفاده نشود.

- نادیده گرفتن فاصله‌ی بزرگ بین ردیف‌های تخمینی و واقعی. معمولاً علت اصلی همین است.
- اجرای کوئری روی دیتابیس توسعه با ۱٬۰۰۰ ردیف و فرض اینکه production همان رفتار را دارد.
- پیچیدن ستون‌های فیلتر داخل تابع یا cast، که استفاده از ایندکس و pruning را می‌بندد.
- فراموش کردن اینکه join با شرط غیربرابری نمی‌تواند hash join یا merge join باشد.
- تلقی `work_mem` به‌عنوان تنظیم سراسری. این مقدار برای هر عملیات است، پس sort های موازی زیاد می‌توانند چند برابر این مقدار مصرف کنند.
- تحمیل ترتیب join یا hint پلن، و بررسی نکردن دوباره‌ی آن بعد از رشد داده.

## ✅ خودت را بسنج

۱. در یک پلن `EXPLAIN ANALYZE`، گره‌ای `rows=500` (تخمین) و `actual rows=900000` (واقعی) نشان می‌دهد. اولین چیزی که باید چک کنی کدام است؟
   - A) تأخیر شبکه تا کلاینت
   - B) اینکه آمار جدول کهنه است یا نه، و اینکه تابع روی ستون یا ستون‌های وابسته تخمین را خراب کرده یا نه
   - C) تعداد هسته‌های CPU
   - D) ترتیب ستون‌ها در لیست `SELECT`

<details><summary>جواب</summary>

**B** — اختلاف بزرگ بین تخمین و واقعی معمولاً یعنی آمار کهنه است یا planner نمی‌تواند شرط را تخمین بزند (مثلاً تابع روی ستون یا ستون‌های وابسته). A، C و D تخمین ردیف‌ها را تغییر نمی‌دهند.

</details>

۲. شرط join به شکل `a.ts BETWEEN b.start_ts AND b.end_ts` است. کدام استراتژی طبیعی‌ترین گزینه است؟
   - A) hash join روی `a.ts`
   - B) nested loop، با ایندکس روی کران‌های `b` وقتی موجود باشد
   - C) hash join روی `b.start_ts`
   - D) merge join روی `a.ts = b.start_ts`

<details><summary>جواب</summary>

**B** — hash join و merge join ردیف‌ها را با برابری روی یک کلید جور می‌کنند، و شرط بازه‌ای کلید برابری ندارد. nested loop هر شرطی را ارزیابی می‌کند، و ایندکس روی کران‌های بازه هر ردیف خارجی را به یک جستجوی سریع تبدیل می‌کند. A، C و D همگی به کلید برابری نیاز دارند که این شرط ندارد.

</details>

۳. کدام شرط برای ایندکس روی `created_at` sargable است؟
   - A) `WHERE EXTRACT(YEAR FROM created_at) = 2026`
   - B) `WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'`
   - C) `WHERE created_at::text LIKE '2026%'`
   - D) `WHERE created_at + interval '1 day' > now()`

<details><summary>جواب</summary>

**B** — بازه روی ستون خام است. A، C و D همگی تابع، cast یا محاسبه را روی ستون می‌گذارند و ستون را از دید ایندکس پنهان می‌کنند.

</details>

۴. (سنیور) یک job شبانه کوئری‌ای ۴۰ ثانیه‌ای دارد و `EXPLAIN ANALYZE` روی یک hash join مقدار `Batches: 16` نشان می‌دهد. محتمل‌ترین علت و اولین راه‌حل چیست؟
   - A) ایندکس وجود ندارد؛ روی هر کلید join یک B-tree اضافه کن
   - B) جدول hash در حافظه جا نمی‌شود و روی دیسک spill می‌کند؛ حافظه‌ی آن عملیات را بالا ببر، یا طرف build را کوچک کن (اول فیلتر کن یا از قبل جمع بزن)
   - C) آمار خیلی جدید است؛ `ANALYZE` را حذف کن
   - D) کوئری ستون‌های زیادی دارد

<details><summary>جواب</summary>

**B** — `Batches` بالاتر از ۱ یعنی جدول hash spill کرده. راه‌حل حافظه‌ی بیشتر برای آن عملیات، یا طرف build کوچک‌تر است. A علت spill نیست، C جهت درست را برعکس می‌گوید، و D ربطی ندارد.

</details>

۵. (سنیور، trade-off) یک داشبورد هر چند دقیقه یک aggregate را روی ۲ میلیارد ردیف اجرا می‌کند. بهترین تغییر کدام است؟
   - A) یک hint بگذار که nested loop را تحمیل کند
   - B) یک جدول یا view ماتریالایزشده بساز که با برنامه‌ی موردنیاز داشبورد refresh شود، و داشبورد را به آن وصل کن
   - C) جمع‌آوری آمار را غیرفعال کن
   - D) `GROUP BY` را حذف کن

<details><summary>جواب</summary>

**B** — تکرار یک aggregate سنگین، محاسبه‌ی هدررفته است. نتیجه‌ی از قبل محاسبه‌شده که با تازگی لازم داشبورد refresh شود، راه معمول است. A شکننده است، C پلن‌ها را بدتر می‌کند، و D نتیجه را عوض می‌کند.

</details>

## 🗂️ فلش‌کارت

| رو | پشت |
|---|---|
| optimizer مبتنی بر هزینه چیست؟ | هزینه‌ی پلن‌های کاندید را از روی آمار تخمین می‌زند و ارزان‌ترین را انتخاب می‌کند |
| `EXPLAIN ANALYZE` چه چیزی به `EXPLAIN` اضافه می‌کند؟ | کوئری را واقعاً اجرا می‌کند و زمان و تعداد ردیف واقعی را کنار تخمین‌ها می‌گذارد |
| cardinality چیست؟ | تعداد ردیف (تخمینی یا واقعی) در یک مرحله‌ی پلن |
| چه وقتی nested loop join خوب است؟ | ورودی خارجی کوچک و ایندکس روی کلید join طرف داخلی |
| hash join به چه نیاز دارد؟ | شرط برابری و حافظه برای جدول hash؛ وقتی حافظه تمام شود به batch ها spill می‌کند |
| چه چیزی شرط را sargable می‌کند؟ | ستون خام با ثابت‌ها مقایسه شود، بدون تابع، cast یا محاسبه روی آن |
| partition pruning چیست؟ | رد کردن partition هایی که با فیلتر نمی‌خوانند، بر اساس کلید partition |
| spill به دیسک چیست؟ | عملگری (sort یا hash) که از حد حافظه‌اش بیشتر شده و فایل موقت می‌نویسد |
