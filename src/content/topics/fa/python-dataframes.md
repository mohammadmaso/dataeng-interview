## 🎯 خلاصه

> **DataFrame** یک جدول در حافظه با ستون‌های نام‌دار است. **pandas** ابزار پیش‌فرض است و **Polars** و **DuckDB** موتورهای جدیدترند که روی یک ماشین سریع‌ترند، چون روی **ستون‌ها** کار می‌کنند، **موازی** اجرا می‌شوند، و (Polars و DuckDB) کل کوئری را قبل از اجرا **بهینه** می‌کنند.

- از عملیات **برداری** (عبارت روی کل ستون) استفاده کن. از حلقه‌ی پایتونی روی سطرها پرهیز کن.
- به **dtype حافظه** دقت کن: ستون رشته‌های تکراری به‌صورت `object` می‌تواند ده برابر حافظه‌ی یک `category` مصرف کند.
- موتورهای **lazy** اول یک plan می‌سازند و یک‌باره اجرایش می‌کنند؛ موتورهای eager هر مرحله را فوراً اجرا می‌کنند.
- **DuckDB** اجازه می‌دهد SQL را مستقیم روی فایل‌های Parquet روی دیسک بنویسی، بدون اینکه قبلش لودشان کنی.
- ابزارهای یک‌ماشینه اغلب برای ده‌ها گیگابایت کافی‌اند. Spark برای داده‌ای است که در یک ماشین جا نمی‌شود، یا برای shuffle در سطح کلاستر.

## 🌱 از ساده شروع کنیم (مبتدی)

> **💡 تشبیه:** DataFrame یک صفحه‌گسترده با ستون‌های تایپ‌شده است. اعمال `amount * 1.09` روی کل یک ستون مثل این است که یک فرمول را با یک کلیک تا یک میلیون سطر پایین بکشی. حلقه‌ی `for` روی سطرها مثل تایپ کردن دستی فرمول برای هر سطر است.

```python
import pandas as pd

orders = pd.DataFrame({
    "customer": ["ali", "sara", "ali", "reza"],
    "amount":   [10.0, 5.5, 7.0, 3.0],
    "status":   ["paid", "paid", "refunded", "paid"],
})

paid = orders[orders["status"] == "paid"]           # فیلتر: یک مقایسه‌ی برداری
per_customer = (
    paid.groupby("customer", as_index=False)        # گروه‌بندی + تجمیع
        .agg(total=("amount", "sum"), orders=("amount", "size"))
)
print(per_customer)
#   customer  total  orders
# 0      ali   10.0       1
# 1     reza    3.0       1
# 2     sara    5.5       1
```

به چیزی که نیست توجه کن: حلقه‌ای وجود ندارد. فیلتر، گروه‌بندی و جمع همه به‌صورت عملیات روی کل ستون‌ها بیان شده‌اند، و pandas آن‌ها را با کد کامپایل‌شده و بهینه اجرا می‌کند.

## 🔧 واقعاً چطور کار می‌کند (متوسط)

### حافظه‌ی ستونی و برداری‌سازی

هر ستون به‌صورت یک بلوک پیوسته از مقادیر ذخیره می‌شود. جمع روی `amount` یک بلوک را می‌خواند، پس cache و دستورهای SIMD پردازنده خوب کار می‌کنند. حلقه‌ی سطربه‌سطر پایتون برعکس عمل می‌کند: برای هر مقدار یک شیء پایتون می‌سازد و روی هرکدام dispatch می‌کند، که معمولاً ۱۰ تا ۱۰۰ برابر کندتر است.

```python
import numpy as np, pandas as pd

df = pd.DataFrame({"x": np.random.rand(1_000_000)})
df["y_slow"] = [v * 2 for v in df["x"]]   # حلقه‌ی پایتون: برای هر سطر یک float پایتونی
df["y_fast"] = df["x"] * 2                # برداری: یک عملیات کامپایل‌شده
```

قاعده‌ی سرانگشتی: اگر `for _, row in df.iterrows()` نوشته‌ای، دنبال یک عبارت، `np.where`، `.map` با تابع برداری، یا عبارت SQL/Polars باش.

### حافظه و dtypeها

pandas متن را به‌طور پیش‌فرض در ستون‌های `object` نگه می‌دارد. هر مقدار یک شیء رشته‌ی پایتون جداگانه با سربار خودش است. مقادیر تکراری (کد وضعیت، نام کشور) حافظه را هدر می‌دهند.

```python
import pandas as pd

df = pd.DataFrame({"status": ["paid"] * 1_000_000})
print(df.memory_usage(deep=True).sum() / 1e6)      # ده‌ها MB رشته‌ی پایتونی

df["status"] = df["status"].astype("category")     # کدهای عددی کوچک + یک جدول مراجعه
print(df.memory_usage(deep=True).sum() / 1e6)      # حدود ۱ MB
```

انتخاب‌های مفید دیگر: `int32` به‌جای `int64` وقتی بازه اجازه می‌دهد، `float32` برای معیارهای غیرمالی، و نوع رشته‌ی پشتیبانی‌شده با Arrow (`dtype="string[pyarrow]"`) برای سربار کمتر. dtype را هنگام لود داده تعیین کن (`read_csv(..., dtype=...)`)، نه بعداً، چون اوج حافظه در زمان لود است که job را می‌شکند.

### groupby و merge

`groupby` سطرها را بر اساس کلید تقسیم می‌کند، تجمیع را اعمال می‌کند و نتایج را کنار هم می‌گذارد. `merge` یک join به سبک SQL است:

```python
customers = pd.DataFrame({"customer": ["ali", "sara"], "city": ["Tehran", "Shiraz"]})
enriched = orders.merge(customers, on="customer", how="left")   # reza برای city مقدار NaN می‌گیرد
```

joinها و groupbyها روی کلید جدول hash می‌سازند. کلیدهای تکراری در یک طرف، سطرها را ضرب می‌کنند (join چندبه‌چند)، که رایج‌ترین باگ بی‌صداست: قبل و بعد از merge تعداد سطرها را چک کن، یا `validate="many_to_one"` بده.

### ارزیابی تنبل با Polars

Polars دو API دارد: `DataFrame` eager و `LazyFrame` lazy. lazy یعنی تا `.collect()` هیچ چیز اجرا نمی‌شود. بهینه‌ساز می‌تواند فیلترها را تا خود خواننده‌ی فایل ببرد و فقط ستون‌های لازم را بخواند.

```python
import polars as pl

orders.to_parquet("orders.parquet", index=False)  # به pyarrow نیاز دارد؛ یک فایل نمونه می‌سازد

result = (
    pl.scan_parquet("orders.parquet")             # lazy: فقط متادیتا را می‌خواند
      .filter(pl.col("status") == "paid")         # به خواننده‌ی Parquet پایین برده می‌شود
      .group_by("customer")
      .agg(pl.col("amount").sum().alias("total"), pl.len().alias("orders"))
      .sort("customer")
      .collect()                                  # کل plan همین‌جا اجرا می‌شود
)
print(result)
```

`lf.explain()` plan بهینه‌شده را چاپ می‌کند. اگر `FILTER` را نزدیک scan و یک لیست کوتاه از ستون‌ها ببینی، بهینه‌ساز کارش را کرده. این همان ایده‌ی بهینه‌ساز Catalyst در Spark و predicate pushdown در خواننده‌های Parquet است.

### DuckDB روی Parquet

DuckDB یک پایگاه داده‌ی تحلیلی درون‌فرایندی است: کتابخانه است، نه سرور. Parquet، CSV و Arrow را مستقیم می‌خواند و SQL را با یک موتور برداری و موازی اجرا می‌کند.

```python
import duckdb

result = duckdb.sql("""
    SELECT customer, SUM(amount) AS total, COUNT(*) AS orders
    FROM 'orders.parquet'
    WHERE status = 'paid'
    GROUP BY customer
    ORDER BY customer
""").df()                                          # .pl() نتیجه‌ی Polars می‌دهد، .arrow() نتیجه‌ی Arrow

print(result)
```

رشته‌ی `'orders.parquet'` در `FROM` یک ارجاع به فایل است. DuckDB فقط ستون‌ها و row groupهای لازم را می‌خواند، و به همین دلیل برای تحلیل‌های ad-hoc روی فایل‌هایی که برای pandas بزرگ‌اند عالی است.

### Apache Arrow: قالب حافظه‌ی مشترک

Arrow یک چیدمان ستونی درون‌حافظه تعریف می‌کند که ابزارهای زیادی آن را به اشتراک می‌گذارند. pandas (با backend آرو)، Polars، DuckDB و پل پایتونی Spark می‌توانند داده را بدون کپی یا parse مجدد، اغلب به‌صورت zero-copy، رد و بدل کنند. به‌طور عملی: جدول Arrow را به‌عنوان شیء تبادل بین ابزارها، و Parquet را به‌عنوان فرمت فایل روی دیسک استفاده کن ([[columnar-storage]]، [[parquet]]).

```python
import duckdb, polars as pl

arrow_tbl = duckdb.sql("SELECT * FROM 'orders.parquet'").arrow()
df_polars = pl.from_arrow(arrow_tbl)
```

## 🧠 عمق و trade-offها (سنیور)

- **انتخاب ابزار.**
  - **pandas**: پیش‌فرض اکوسیستم، API بسیار بزرگ، اغلب تک‌thread، و پرمصرف از نظر حافظه. تا چند گیگابایت راحت است؛ حافظه‌ی RAM چند برابر حجم داده در نظر بگیر.
  - **Polars**: چندthread، بهینه‌ساز lazy، تایپ‌های سخت‌گیر، و API کوچک‌تر اما در حال رشد. برای ETL روی یک ماشین وقتی داده از ظرفیت pandas بزرگ‌تر است.
  - **DuckDB**: بهترین وقتی منطقت طبیعتاً SQL است و داده در فایل (Parquet، CSV) یا Arrow است. در notebook، کانتینر یا job پایتونی بدون سرور اجرا می‌شود.
  - قاعده‌ی سرانگشتی، که روی بار کاری خودت بسنجی: یک ماشین با RAM و دیسک محلی کافی، ده‌ها گیگابایت را با DuckDB یا Polars خوب پردازش می‌کند. Spark وقتی لازم می‌شود که داده در یک node جا نشود، shuffle توزیع‌شده لازم باشد، یا چند job باید یک کلاستر را با fault tolerance شریک شوند.
- **spill و out-of-core.** Polars در حالت streaming و DuckDB وقتی حافظه کم است می‌توانند روی دیسک spill کنند؛ pandas معمولاً نمی‌تواند. قبل از قول دادن که job روی لپ‌تاپ اجرا می‌شود، نام دقیق گزینه‌ها را در مستندات نسخه‌ات چک کن.
- **drift اسکیما.** `read_csv` در pandas نوع‌ها را از اولین chunk حدس می‌زند. یک سطر بعدی با `"N/A"` یک ستون عددی را `object` می‌کند، و بعد join بی‌صدا مچ نمی‌کند. اسکیما را در مرز ورودی اعلام کن (dtypeها یا اسکیمای Polars) و اعتبارسنجی کن ([[data-quality]]).
- **قطعیت و ترتیب سطرها.** `groupby` در pandas به‌طور پیش‌فرض کلیدها را مرتب می‌کند؛ `group_by` در Polars ترتیب را تضمین نمی‌کند مگر `sort` کنی. هرگز به ترتیب ضمنی در تست یا گزارش تکیه نکن.
- **null و NaN.** در pandas `NaN` یک float است، پس یک ستون عددی با مقدار گمشده به float تبدیل می‌شود. Polars و Arrow یک bitmap جدا برای اعتبار دارند، پس nullها درست تایپ می‌شوند. این را وقتی داده را بین موتورها جابه‌جا می‌کنی چک کن.
- **رصد.** برای job دسته‌ای روی یک ماشین، بیشترین RSS، زمان هر مرحله، تعداد سطرهای ورودی و خروجی هر join و تعداد سطرهای ردشده توسط اعتبارسنجی را دنبال کن. join ای که تعداد سطرها را دو برابر می‌کند، فقط با شمردن دیده می‌شود.
- **کی اصلاً DataFrame لازم نیست.** اگر تبدیل چند join SQL روی یک جدول warehouse است، داخل warehouse بماند. بیرون بردن داده به لپ‌تاپ برای یک job DataFrame یک کپی، یک نقطه‌ی خرابی و یک مشکل زمان‌بندی اضافه می‌کند.

## 🧪 امتحان کن

یک `orders.parquet` مثل مثال Polars بساز و یک `customers.csv` با ستون‌های `customer,city` برای `ali`، `sara` و `reza` درست کن.

1. همان کوئری «جمع پرداخت‌شده برای هر مشتری» را در **pandas**، **Polars** (lazy) و **DuckDB SQL** بنویس. مطمئن شو هر سه یک عدد می‌دهند.
2. `orders.parquet` را با `pl.scan_parquet(...).select(["customer"]).collect()` بخوان. توضیح بده بهینه‌ساز از خواندن چه چیزی جلوگیری کرد.
3. `orders` را با `customers` join کن و یک سطر با کلید تکراری `ali` به `customers` اضافه کن. قبل از اجرا تعداد سطرهای نتیجه را پیش‌بینی کن، بعد `validate="many_to_one"` را به merge در pandas اضافه کن و خطا را ببین.

<details><summary>راه‌حل‌ها را نشان بده</summary>

**۱.** هر سه نسخه همان سطرها را می‌دهند (`ali 10.0`، `reza 3.0`، `sara 5.5`). نسخه‌ی pandas در متن درس است؛ Polars زنجیره‌ی lazy بالاست؛ DuckDB همان SQL بالاست. باید دقیقاً یکی باشند، و همین نکته است: انتخاب ابزار درباره‌ی کارایی، حافظه و راحتی است، نه نتیجه.

**۲.** `select` به خواننده‌ی Parquet می‌گوید بقیه‌ی ستون‌ها را نخواند. `explain()` یک projection فقط روی `customer` نشان می‌دهد. فایل همچنان اسکن می‌شود، اما داده‌ی خیلی کمتری decode و در حافظه نگه داشته می‌شود.

**۳.** قبل از تغییر، `orders` چهار سطر و `customers` دو کلید (`ali`، `sara`) دارد، و `reza` در left join بدون مچ می‌ماند. با یک `ali` دوم، برای هر سطر سفارش `ali` دو سطر مشتری مچ می‌شود؛ سفارش‌های `ali` (دو تا) در مجموع چهار سطر می‌دهند، به‌جای دو. جمع نهایی: ۶ سطر. `validate="many_to_one"` خطای `MergeError` می‌دهد، چون طرف راست روی `customer` یکتا نیست، و این دقیقاً محافظتی است که می‌خواهی.

## 💬 گوشه‌ی مصاحبه

**سؤال: «فایل ۲۰ گیگابایتی‌ام در pandas کند است. چه کار می‌کنی؟»**
جواب متوسط: «با `chunksize` به‌صورت تکه‌تکه می‌خوانم، از dtype از نوع category استفاده می‌کنم، یا به Polars می‌روم.»
جواب سنیور: «اول چک می‌کنم کار فیلتر و تجمیع است یا نه، چون در این صورت باید یک موتور ستونی فایل را بخواند که بتواند predicate و projection را پایین ببرد. از Polars lazy یا DuckDB روی Parquet استفاده می‌کنم، حافظه‌ی اوج را می‌سنجم، و فقط اگر داده در یک ماشین جا نشد یا shuffle کلاستری لازم بود به Spark می‌روم. همچنین می‌پرسم اصلاً داده باید به Parquet باشد یا نه.»

**سؤال: «کی دیگر به Spark نیاز نداری؟»**
جواب سنیور: «وقتی داده و working set به‌راحتی روی یک ماشین جا شوند، منطق ستونی یا SQL باشد، و نیازی به fault tolerance توزیع‌شده نباشد. هزینه‌ی Spark مدیریت کلاستر، serialization و shuffle است، و برای داده‌ی کوچک این‌ها فقط سربار هستند. با این حال اگر همان کد بعداً باید روی داده‌ی مقیاس پتابایت اجرا شود، Spark را نگه می‌دارم.»

> **🎤 این را در مصاحبه بگو:** «ابزار را با اندازه‌ی داده و محل داده انتخاب می‌کنم. pandas برای داده‌ی کوچک، Polars یا DuckDB برای کار بزرگ‌تر روی یک ماشین، و Spark وقتی داده یا shuffle به کلاستر نیاز دارد. هرچه باشد، تعداد سطرها را در join ها اعتبارسنجی می‌کنم و dtypeها را هنگام لود ثابت می‌کنم.»

## ⚠️ اشتباهات رایج

> **⚠️ هشدار:** حلقه زدن روی سطرها با `iterrows()` یا `apply(axis=1)` برای حساب ساده. کند است و باگ‌ها را پنهان می‌کند. از عبارت‌های ستونی استفاده کن.

> **⚠️ هشدار:** merge روی کلید غیریکتا بی‌صدا سطرها را ضرب می‌کند. همیشه یکتایی کلید را در طرفی که انتظار داری یکتا باشد چک کن.

- لود کردن یک CSV بزرگ با dtypeهای پیش‌فرض و بعد تعجب از اینکه حافظه پنج برابر حجم فایل است.
- استفاده از `object` برای رشته‌های با تعداد مقدار کم، به‌جای `category`.
- فرض اینکه خروجی `group_by` در Polars مرتب است. مرتب نیست، مگر اینکه `sort` کنی.
- فراموش کردن اینکه `NaN` در pandas ستون‌های عددی صحیح را به float تبدیل می‌کند، که join روی ID ها را خراب می‌کند.
- صدا زدن زودهنگام `.collect()` در زنجیره‌ی Polars، که بهینه‌ساز را بی‌اثر می‌کند.
- انتخاب Spark برای یک فایل ۵۰۰ مگابایتی از روی عادت.

   - C) نسخه‌ی lazy همیشه حافظه‌ی کمتری مصرف می‌کند و هرگز فایل را نمی‌خواند
   - D) نسخه‌ی lazy یک فایل Parquet موقت می‌نویسد

<details><summary>جواب</summary>

**B** — `scan_parquet` تنبل است. بهینه‌ساز می‌تواند فیلتر را پایین ببرد و فقط ستون‌های لازم را بخواند. `read_parquet` اول کل فایل را لود می‌کند.

</details>

۳. چرا یک ستون از یک میلیون رشته‌ی وضعیت تکراری در pandas می‌تواند حافظه‌ی بسیار بیشتری از حالت `astype("category")` مصرف کند؟
   - A) `category` با gzip فشرده می‌کند
   - B) `object` برای هر مقدار یک رشته‌ی پایتونی جدا نگه می‌دارد، در حالی که `category` کدهای عددی کوچک و یک جدول مراجعه‌ی کوچک نگه می‌دارد
   - C) `category` مقادیر null را حذف می‌کند
   - D) pandas بدون `category` اصلاً نمی‌تواند رشته ذخیره کند

<details><summary>جواب</summary>

**B** — ستون object برای هر سطر یک رشته‌ی پایتونی نگه می‌دارد. ستون category کدهای فشرده‌ای دارد که به جدول کوچکی از مقادیر متمایز اشاره می‌کنند.

</details>

۴. **(سنیور)** یک `merge` در pandas روی `customer_id` بعد از نوسازی یک جدول بُعد، سه برابر تعداد سطرهای مورد انتظار می‌دهد. علت محتمل چیست و چه محافظی اضافه می‌کنی؟

   - A) merge از نوع `how="left"` است که همیشه سطرها را سه برابر می‌کند
   - B) بُعد الان کلیدهای تکراری دارد، پس هر سطر واقعی چند سطر بُعد را مچ می‌کند؛ یکتایی کلید را چک کن و `validate="many_to_one"` بگذار (یا ابتدا بُعد را dedupe کن)
   - C) merge در pandas غیرقطعی است؛ از `sort=True` استفاده کن
   - D) راه‌حل، `groupby` بعد از merge است

<details><summary>جواب</summary>

**B** — join چندبه‌چند سطرها را ضرب می‌کند. کاردینالیتی را با `validate=` اعمال کن و خود بُعد را طوری درست کن که کلیدش یکتا باشد (مثلاً با فیلتر آخرین نسخه).

</details>

۵. **(سنیور)** برای یک job شبانه با ۳۰ گیگابایت فایل Parquet روی یک ماشین ۶۴ گیگابایتی، کی DuckDB را به Spark ترجیح می‌دهی، و چه چیزی نظرت را عوض می‌کند؟

   - A) هرگز؛ Spark همیشه سریع‌تر است
   - B) DuckDB وقتی خوب است که داده در ماشین جا شود، منطق SQL/ستونی باشد، و نیاز به کلاستر نباشد؛ اگر داده از یک node بزرگ‌تر شود، job به shuffle توزیع‌شده یا fault tolerance بین چند node نیاز داشته باشد، یا تیم باید یک پلتفرم کلاستری مشترک داشته باشد، به Spark برو
   - C) DuckDB فقط با CSV کار می‌کند
   - D) DuckDB نمی‌تواند Parquet بخواند

<details><summary>جواب</summary>

**B** — تصمیم به این بستگی دارد که داده و کار در یک node جا شوند یا نه، و آیا اجرای توزیع‌شده لازم است. روی داده‌ی خودت بسنج؛ به ادعای کلی سرعت اعتماد نکن.

</details>

## 🗂️ فلش‌کارت

| جلوی کارت | پشت کارت |
|---|---|
| چرا عملیات برداری سریع‌ترند؟ | کد کامپایل‌شده را روی ستون‌های پیوسته اجرا می‌کنند، بدون شیء پایتونی برای هر سطر |
| `object` در برابر `category` برای رشته‌های تکراری | `object` یک رشته‌ی پایتونی برای هر سطر؛ `category` کدهای کوچک و یک جدول مراجعه |
| `scan_parquet` چه چیزی برمی‌گرداند؟ | یک plan تنبل (LazyFrame) که فقط با `.collect()` اجرا می‌شود |
| predicate pushdown چیست؟ | بردن فیلتر داخل خواننده‌ی فایل تا داده‌ی کمتری خوانده شود |
| `validate="many_to_one"` از چه جلوگیری می‌کند؟ | از کلیدهای تکراری در طرف راست merge که سطرها را ضرب می‌کنند |
| Apache Arrow چیست؟ | قالب ستونی مشترک درون‌حافظه که ابزارها با کپی کم یا بدون کپی رد و بدل می‌کنند |
| DuckDB چه کاری می‌کند؟ | SQL را درون‌فرایندی و مستقیم روی Parquet، CSV و Arrow اجرا می‌کند |
| Spark کی لازم است؟ | وقتی داده یا shuffle در یک ماشین جا نمی‌شود، یا کلاستر لازم است |

## 🔗 ادامه

- **python-concurrency** توضیح می‌دهد چرا عملیات pandas و NumPy در C سریع‌اند و حلقه‌ی پایتونی نه، و GIL روی کار موازی چه اثری دارد.
- **python-large-files** خواندن chunk به chunk و streaming را پوشش می‌دهد، مسیر دیگر برای داده‌ای که در حافظه جا نمی‌شود.
- **columnar-storage** و **data-formats** توضیح می‌دهند چرا Parquet و چیدمان ستونی اسکن را ارزان می‌کنند.
- **pyspark-api** و **spark-architecture** نشان می‌دهند وقتی همان منطق باید توزیع‌شده اجرا شود چه چیزی عوض می‌شود.
- **other-batch-engines** موتورهای دسته‌ای دیگر را با Spark مقایسه می‌کند، برای مواردی که یک ماشین کافی نیست.
