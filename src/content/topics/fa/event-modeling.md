## 🎯 خلاصه

> یک **event** (رویداد) یک واقعیتِ تغییرناپذیر است که در یک لحظه‌ی مشخص اتفاق افتاده. مدل‌سازی رویداد یعنی تعریف این‌که **یک رویداد چه شکلی دارد**، **چطور نام‌گذاری و نسخه‌بندی می‌شود**، و **چطور میلیون‌ها رویداد خام را به sessionها، funnelها و معیارها تبدیل می‌کنی**.

- هر رویداد یک **envelope** مشترک دارد: مجموعه‌ای ثابت از فیلدها (`event_id`، `event_name`، `event_time`، `user_id` و ...) که هر مصرف‌کننده روی آن‌ها حساب می‌کند.
- جزئیات مخصوص هر کسب‌وکار در یک شیٔ انعطاف‌پذیر به نام **properties** می‌رود (JSON یا ستون `Map`).
- رویدادها append-only هستند. رویداد گذشته را هیچ‌وقت به‌روز نمی‌کنی؛ نسخه‌ی جدید یا یک رویداد اصلاحی اضافه می‌کنی.
- sessionها، funnelها و retention از رویدادها و با window function و conditional aggregation **مشتق** می‌شوند.

## 🌱 از ساده شروع کنیم (مبتدی)

> **💡 تشبیه:** هر رویداد یک خط از فیش خرید فروشگاه است. می‌گوید *چه کسی* خرید، *چه چیزی* خریده شد، *کی* و *چقدر*. فیش بعد از چاپ عوض نمی‌شود. اگر فروشگاه اشتباه کرده باشد، یک فیش جدید چاپ می‌کند که قبلی را اصلاح کند.

یک وب‌سایت هر بار که کاربر کاری انجام می‌دهد یک پیام می‌فرستد. این یک رویداد است، به صورت JSON:

```json
{
  "event_id": "2f6c1e0a-6d1b-4c1e-9a55-0b7f3c2a9d10",
  "event_name": "add_to_cart",
  "event_time": "2026-01-05T10:15:02Z",
  "user_id": "u_1024",
  "properties": {"sku": "SKU-77", "qty": 2, "price": 15.5}
}
```

چهار چیز این‌جا کار می‌کنند:

- `event_id` یکتاست. با آن می‌توانی وقتی همان رویداد دوبار رسید، تکراری‌ها را حذف کنی.
- `event_name` می‌گوید چه اتفاقی افتاده. از فعل در `snake_case` استفاده کن: `page_view`، `add_to_cart`، `purchase`.
- `event_time` زمانی است که رویداد **واقعاً** اتفاق افتاده، روی دستگاه یا سرور، به UTC.
- `properties` جزئیاتی را نگه می‌دارد که با نوع رویداد فرق می‌کند.

اگر هر رویداد شکل متفاوتی داشت، هر کوئری کد مخصوص می‌خواست. یک envelope مشترک اجازه می‌دهد همه‌ی رویدادها در یک جدول باشند.

## 🔧 واقعاً چطور کار می‌کند (متوسط)

### envelope

یک envelope رایج این فیلدها را دارد:

| فیلد | کاربرد |
|---|---|
| `event_id` | شناسه‌ی یکتا، برای حذف تکراری و دیباگ |
| `event_name` | نوع رویداد، از یک فهرست کنترل‌شده |
| `schema_version` | نسخه‌ی قرارداد `properties` |
| `event_time` | زمان وقوع (ساعت کلاینت یا سرور) |
| `ingested_at` | زمانی که pipeline شما رویداد را دریافت کرده |
| `user_id` / `anonymous_id` | شناسه‌ی کاربر لاگین‌شده، و شناسه‌ی دستگاه قبل از لاگین |
| `properties` | فیلدهای مخصوص رویداد (JSON یا `Map`) |

دو زمان مهم‌اند. `event_time` زمان کسب‌وکار است و `ingested_at` زمان پردازش. فاصله‌ی بین آن دو **تأخیر (lateness)** است و توضیح می‌دهد چرا عدد دیروز امروز عوض می‌شود. همین ایده در [[event-time]] و [[late-arriving-data]] آمده.

### رویداد پهن در برابر باریک

- **باریک (شبیه EAV)**: یک ردیف برای هر property، مثلاً `(event_id, key, value)`. انعطاف‌پذیر است، ولی هر کوئری pivot و join می‌خواهد و اسکن آن کند است.
- **پهن**: یک ردیف برای هر رویداد با ستون‌های تایپ‌شده‌ی زیاد (`sku`، `qty`، `price`، `page_url` و ...). کوئری سریع و فشرده‌سازی خوب دارد، ولی اضافه کردن property یعنی `ALTER TABLE` روی جدول بزرگ.
- **نیمه‌ساخت‌یافته**: envelope را به صورت ستون‌های تایپ‌شده نگه می‌داری و `properties` را در یک ستون `JSON` یا `Map` ذخیره می‌کنی. انبارهای ستونی رایج (مثل ClickHouse، BigQuery، Snowflake و Spark با Parquet) می‌توانند مسیر JSON را موقع کوئری استخراج کنند یا بعداً به ستون تبدیلش کنند.

بیشتر تیم‌ها گزینه‌ی سوم را انتخاب می‌کنند. چند property‌ای که خیلی از کوئری‌ها روی‌شان فیلتر می‌کنند (مثل `sku`) را به ستون واقعی ارتقا می‌دهند و بقیه را در map نگه می‌دارند.

### tracking plan و نسخه‌ی schema

**tracking plan** قراردادِ بین محصول، توسعه‌دهنده‌های موبایل/وب و مهندس داده است. برای هر `event_name` فهرست می‌کند کدام propertyها لازم‌اند، تایپ و مقادیر مجازشان چیست، و مالک آن کیست. وقتی یک property عوض می‌شود، `schema_version` را بالا ببر:

```text
add_to_cart v1: sku (string), qty (int)
add_to_cart v2: sku (string), qty (int), price_cents (int)   -- price became integer cents
```

قواعدی که بیشتر خرابی‌ها را جلو می‌گیرند:

- اضافه کردن یک فیلد اختیاری با نسخه‌ی قبلی سازگار است.
- تغییر نام یا تایپ یعنی نسخه‌ی جدید، و مدتی هر دو را با هم اجرا می‌کنی.
- مصرف‌کننده‌ها قبل از parse کردن `properties`، `schema_version` را می‌خوانند.

برای اجرای قرارداد، schemaها را در یک [[schema-registry]] ثبت کن و رویدادها را موقع ingestion اعتبارسنجی کن. رویدادهای نامعتبر به یک [[dead-letter-queue]] می‌روند، نه این‌که جدول را خراب کنند.

### sessionها

**session** گروهی از رویدادهای یک کاربر است که بین‌شان مکث طولانی نیست. قاعده‌ی رایج یک وقفه‌ی ۳۰ دقیقه‌ای است. در SQL این کار در سه مرحله انجام می‌شود: پیدا کردن فاصله، علامت‌گذاری نقطه‌ی شروع session جدید، و شماره‌گذاری sessionها با جمع تجمعی.

```sql
WITH ordered AS (
  SELECT user_id, event_time, event_name,
         LAG(event_time) OVER (PARTITION BY user_id ORDER BY event_time) AS prev_time
  FROM events
),
flagged AS (
  SELECT *,
         CASE WHEN prev_time IS NULL
                OR event_time - prev_time > INTERVAL '30 minutes'
              THEN 1 ELSE 0 END AS is_new_session
  FROM ordered
),
numbered AS (
  SELECT *,
         SUM(is_new_session) OVER (
           PARTITION BY user_id ORDER BY event_time
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS session_no
  FROM flagged
)
SELECT user_id, session_no,
       MIN(event_time) AS started_at,
       MAX(event_time) AS ended_at,
       COUNT(*)        AS events
FROM numbered
GROUP BY user_id, session_no;
```

این همان ایده‌ی «gaps and islands» است که در مسئله‌های [[window-function]] استفاده می‌شود. نحو `INTERVAL` مخصوص PostgreSQL است؛ برای موتور خودت تطبیقش بده.

### funnelها

**funnel** نشان می‌دهد چند کاربر به هر مرحله رسیده‌اند. ساده‌ترین نسخه با conditional aggregation است:

```sql
SELECT
  COUNT(DISTINCT CASE WHEN event_name = 'page_view'   THEN user_id END) AS viewed,
  COUNT(DISTINCT CASE WHEN event_name = 'add_to_cart' THEN user_id END) AS carted,
  COUNT(DISTINCT CASE WHEN event_name = 'purchase'    THEN user_id END) AS bought
FROM events
WHERE event_time >= TIMESTAMP '2026-01-01 00:00:00';
```

این نسخه ترتیب را اجباری نمی‌کند: کاربری که قبل از دیدن محصول خرید کرده هم شمرده می‌شود. funnel **سخت‌گیرانه** (strict) باید بگوید هر مرحله **بعد از** مرحله‌ی قبلی رخ داده، که معمولاً یعنی `MIN(event_time)` هر مرحله برای هر کاربر و مقایسه‌ی آن‌ها، یا یک تابع funnel اختصاصی در موتورهایی که دارند.

## 🧠 عمق و trade-offها (سنیور)

- **ingestion‌ی idempotent.** producerها retry می‌کنند، پس تکراری‌ها عادی‌اند. در یک بازه‌ی محدود روی `event_id` حذف تکراری کن، یا از [[upsert]] با کلید `event_id` در فرمت جدولی که پشتیبانی می‌کند استفاده کن. تعداد تکراری‌ها را به‌عنوان معیار کیفیت داده ثبت کن.
- **زمان رویداد در برابر زمان پردازش.** جدول خام را برای تحلیل بر اساس `event_time` پارتیشن کن، ولی `ingested_at` را برای دیباگ pipeline نگه دار. رویدادهای دیرهنگام در پارتیشن‌های قدیمی می‌نشینند، پس backfill باید برنامه‌ریزی شود. برای سیستم‌های streaming به [[watermark]] نگاه کن.
- **کاردینالیتی propertyها.** ذخیره‌ی متن آزاد یا رشته‌های ساخته‌شده توسط کاربر به‌عنوان کلید گروه‌بندی، آمار ستون‌ها و dictionaryها را منفجر می‌کند. از فهرست کنترل‌شده استفاده کن و مقادیر با کاردینالیتی بالا را فقط به‌صورت payload نگه دار، نه ستون گروه‌بندی.
- **حریم خصوصی.** رویدادها اغلب داده‌ی شخصی دارند. شناسه‌ها را pseudonymize کن، جدول نگاشت را جدا نگه دار، و قبل از این‌که داده به دسترسی گسترده‌ی تحلیلگرها برسد [[data-masking]] اعمال کن. درخواست حذف باید به رویدادهای خام هم برسد.
- **ذخیره‌سازی.** رویدادهای خام حجیم‌اند. روزانه پارتیشن کن، در فرمت ستونی ذخیره کن، و نگهداری خام را کوتاه و جدول‌های تجمیعی را بلندمدت نگه دار.
- **streaming در برابر batch.** sessionها روی stream به state با timeout نیاز دارند (session windowها در Flink یا Spark Structured Streaming). sessionهای batch ساده‌ترند ولی تأخیر دارند. انتخاب به تازگی لازم برای معیار بستگی دارد.
- **بیش‌ازحد مدل نکن.** مدل‌کردن همه‌ی propertyهای ممکن از اول تیم محصول را کند می‌کند. پیش‌فرض خوب: یک envelope پایدار، یک map انعطاف‌پذیر، و چند ستون ارتقایافته که tracking plan مشخصشان کرده.

## 🧪 امتحان کن

این جدول کوچک را در PostgreSQL 13 یا بالاتر (یا هر موتور SQL که `LAG`، `SUM OVER` و `INTERVAL` را داشته باشد) اجرا کن:

```sql
CREATE TABLE events (user_id text, event_time timestamp, event_name text);
INSERT INTO events VALUES
 ('u1','2026-01-05 10:00','page_view'),
 ('u1','2026-01-05 10:10','add_to_cart'),
 ('u1','2026-01-05 12:00','page_view'),
 ('u2','2026-01-05 10:05','page_view'),
 ('u2','2026-01-05 10:20','purchase'),
 ('u3','2026-01-05 09:00','add_to_cart');
```

۱. کوئری sessionization بالا را اجرا کن. کاربر `u1` چند session دارد و چرا؟
۲. کوئری funnel را اجرا کن. مقدار `viewed`، `carted` و `bought` چقدر است؟
۳. کوئری بنویس که کاربرانی را بشمارد که **بعد از** دیدن محصول خرید کرده‌اند (ترتیب سخت‌گیرانه)، با `MIN(event_time)` برای هر نام رویداد.

**۱.** `u1` دو session دارد. رویدادهای ساعت ۱۰:۰۰ و ۱۰:۱۰ کمتر از ۳۰ دقیقه فاصله دارند. رویداد ۱۲:۰۰ ‌حدود ۱۱۰ دقیقه بعد است، پس session شماره‌ی ۲ را شروع می‌کند. `u2` یک session و `u3` هم یک session دارد.

**۲.** `viewed = 2` (u1, u2)، `carted = 2` (u1, u3)، `bought = 1` (u2).

**۳.**
```sql
WITH firsts AS (
  SELECT user_id,
         MIN(CASE WHEN event_name = 'page_view' THEN event_time END) AS viewed_at,
         MIN(CASE WHEN event_name = 'purchase'  THEN event_time END) AS bought_at
  FROM events
  GROUP BY user_id
)
SELECT COUNT(*) AS bought_after_view
FROM firsts
WHERE viewed_at IS NOT NULL AND bought_at > viewed_at;
```
نتیجه: `1` (u2 ساعت ۱۰:۰۵ دیده و ساعت ۱۰:۲۰ خریده).

## 💬 گوشه‌ی مصاحبه

**سؤال: «داده‌ی clickstream را برای تحلیل چطور مدل می‌کنی؟»** پاسخ متوسط: «یک جدول رویداد با envelope استاندارد: شناسه‌ی رویداد، نام، زمان، شناسه‌ی کاربر، و یک ستون JSON برای properties. پارتیشن‌بندی روزانه.» پاسخ سنیور: «envelope یک قرارداد است، پس آن را با tracking plan و schema registry نسخه‌بندی می‌کنم، موقع ingestion اعتبارسنجی می‌کنم و رویدادهای بد را به dead letter queue می‌فرستم. هم زمان رویداد و زمان ingestion را نگه می‌دارم، روی `event_id` حذف تکراری می‌کنم، فقط propertyهای پرفیلتر را ستون می‌کنم و sessionها و funnelها را در لایه‌ی مدل‌شده مشتق می‌کنم.»

**سؤال: «چرا عدد داشبورد دیروز امروز عوض می‌شود؟»** رویدادهای دیرهنگام و حذف تکراری‌ها. رویدادها بعد از زمان وقوعشان می‌رسند و retryها تکراری می‌سازند که بعداً حذف می‌شوند. تأخیر را اندازه بگیر و برای هر معیار سیاست «قفل کردن» عدد را مشخص کن.

> **🎤 این را در مصاحبه بگو:** «رویدادها را واقعیت‌های تغییرناپذیر با envelope پایدار و payload نسخه‌دار می‌بینم. جزئیات انعطاف‌پذیر در map می‌رود، ستون‌های پرمصرف ستون می‌شوند و sessionها و funnelها view‌های مشتق‌شده‌اند. همیشه زمان رویداد را از زمان ingestion جدا می‌کنم، چون بیشتر مشکلات درستیِ داده همان‌جا پنهان‌اند.»

## ⚠️ اشتباهات رایج

> **⚠️ مراقب باش:** استفاده از زمان ingestion به‌جای زمان رویداد. وقتی pipeline کند شود داشبوردها جابه‌جا می‌شوند، و یک backfill بی‌صدا رویدادها را به روز اشتباه می‌برد.

> **⚠️ مراقب باش:** تغییر معنای یک property بدون بالا بردن `schema_version`. رویدادهای قدیم و جدید در یک ستون قاطی می‌شوند و معیار بدون هیچ خطایی خراب می‌شود.

- ساختن یک نام رویداد جدید برای هر تغییر کوچک UI. این کار صدها نام تقریباً یکسان می‌سازد؛ ترجیح بده یک رویداد با یک property داشته باشی.
- استفاده از مقادیر متن آزاد به‌عنوان کلید گروه‌بندی. تعداد مقادیر متمایز بی‌حد رشد می‌کند.
- حذف تکراری روی `user_id` به‌جای `event_id`. چند رویداد برای یک کاربر کاملاً معتبرند.
- ساختن session با پنجره‌ی ساعت ثابت به‌جای وقفه‌ی بی‌فعالیتی. sessionها در زمان‌های دلخواه می‌شکنند.
- گزارش دادن یک funnel بدون ترتیب به‌عنوان funnel سخت‌گیرانه.
- ذخیره‌ی اطلاعات شخصی در `properties` بدون طبقه‌بندی، که به همه‌ی جدول‌های پایین‌دستی نشت می‌کند.

   - D) خریدها همیشه دوبار ثبت می‌شوند

**B** — funnel بدون ترتیب کاربری را که خریده ولی بازدید ثبت‌شده ندارد می‌شمارد، و رویدادهای تکراری اگر با `event_id` حذف نشوند شمارش را بالا می‌برند. قبل از سرزنش کردن کوئری، هر دو را بررسی کن.

</details>

۴. **(سنیور)** retryهای ingestion حدود ۰٫۵٪ رویداد تکراری می‌سازند. معیار درآمد روزانه کمی بیش‌ازحد است و بعد از backfill عوض می‌شود. چه چیزی را عوض می‌کنی، و چرا فقط `DISTINCT` روی کل ردیف کافی نیست؟

   - A) ستون `properties` را حذف کن تا ردیف‌ها یکتا شوند
   - B) روی `event_id` (کلید یکتای تولیدشده توسط producer) در لایه‌ی مدل‌شده حذف تکراری کن، یا upsert با کلید `event_id` بزن؛ `DISTINCT` روی کل ردیف شکست می‌خورد چون retryها `ingested_at` یا فیلدهای انتقال را عوض می‌کنند
   - C) تعداد پارتیشن‌ها را زیاد کن
   - D) همه‌ی زمان‌ها را به وقت محلی تبدیل کن

<details><summary>پاسخ</summary>

**B** — نسخه‌های retry‌شده `event_id` یکسان دارند ولی ممکن است `ingested_at` یا فیلدهای انتقال‌شان فرق کند، پس `DISTINCT` روی کل ردیف هر دو را نگه می‌دارد. حذف تکراری بر اساس کلید درست و ارزان است و باید قبل از تجمیع درآمد اجرا شود.

</details>

۵. **(سنیور)** محصول یک property جدید به نام `checkout_step` می‌خواهد که روزانه ۴۰٬۰۰۰ مقدار متن آزاد متمایز دارد. ریسک چیست و چه پیشنهادی می‌دهی؟

   - A) ریسکی نیست؛ انبارهای ستونی هر کاردینالیتی را هضم می‌کنند
   - B) کاردینالیتی بالا dictionaryها و آمار را بزرگ می‌کند و گروه‌بندی را کند می‌کند؛ یک فهرست کنترل‌شده‌ی مراحل پیشنهاد بده، متن خام را فقط در payload نگه دار، و یک ستون enum کوچک ارتقا بده
   - C) متن آزاد را نمی‌توان در JSON ذخیره کرد
   - D) همه‌ی رویدادها را با یک ردیف برای هر کاربر جایگزین کن

<details><summary>پاسخ</summary>

**B** — متن آزاد بی‌حد به‌عنوان کلید گروه‌بندی گران است و گزارش‌گیری از آن سخت. یک ستون enum کنترل‌شده جواب سؤال تحلیلی را می‌دهد و متن خام برای دیباگ در payload می‌ماند.

</details>

## 🗂️ فلش‌کارت

| Front | Back |
|---|---|
| رویداد (event) چیست؟ | یک واقعیت تغییرناپذیر درباره‌ی چیزی که در یک لحظه‌ی مشخص اتفاق افتاده |
| هدف envelope | مجموعه‌ای ثابت از فیلدها که هر مصرف‌کننده روی آن حساب می‌کند (شناسه، نام، زمان، کاربر، نسخه) |
| `event_time` در برابر `ingested_at` | زمان کنش در برابر زمان دریافت pipeline؛ فاصله‌شان تأخیر است |
| تغییر امن بدون نسخه‌ی جدید | اضافه کردن یک property اختیاری |
| قاعده‌ی رایج session | session جدید بعد از ۳۰ دقیقه بی‌فعالیتی |
| funnel سخت‌گیرانه در برابر بدون ترتیب | سخت‌گیرانه ترتیب هر کاربر را اجبار می‌کند؛ بدون ترتیب فقط وجود هر مرحله را می‌سنجد |
| چرا روی `event_id` حذف تکراری؟ | retryها همان شناسه را تکرار می‌کنند؛ `DISTINCT` روی کل ردیف وقتی فیلدهای انتقال فرق دارند آن‌ها را نمی‌بیند |

## 🔗 ادامه

- **dwh-fundamentals** زمینه‌ی انبار داده‌ای را توضیح می‌دهد که جدول‌های رویداد در آن زندگی می‌کنند.
- **schema-evolution** و **pattern-schema-evolution** نشان می‌دهند چطور قرارداد را بدون شکستن مصرف‌کننده‌ها عوض کنی.
- **dimensional-modeling** نشان می‌دهد رویدادها چطور با fact و dimension در star schema مرتبط می‌شوند.
- **design-clickstream-analytics** همین ایده‌ها را در یک طراحی سیستم سرتاسری به کار می‌برد.
- مستندات موتور خودت را برای توابع JSON و map بخوان؛ نحو بین انبارهای داده فرق دارد.
