## 🎯 خلاصه

> در مخزن‌های NoSQL **اول کوئری‌ها را مدل می‌کنی**، بعد جدول‌ها را. join وجود ندارد و مسیر دسترسی را **کلید** تعیین می‌کند: partition key (در Cassandra) یا row key (در HBase). کلید را طوری انتخاب کن که هر کوئری یک بازه‌ی کوچک و پیوسته روی یک نود بخواند، و نوشتن‌ها در کل خوشه پخش شوند.

- **Cassandra:** یک جدول برای هر کوئری. partition key نود را انتخاب می‌کند؛ clustering columnها سطرهای داخل partition را مرتب می‌کنند.
- **HBase:** یک ایندکس مرتب، یعنی row key. سطرها به ترتیب کلید ذخیره می‌شوند، پس کلید صعودی همه‌ی نوشتن‌ها را به یک region می‌فرستد (hot spot).
- **Redis:** کلید همان آدرس است. ساختارهای داده (hash، sorted set، list) را انتخاب کن که با الگوی خواندن جور باشند و در حافظه جا شوند.
- عمداً denormalize کن. تکرار داده بین جدول‌ها عادی است و هزینه‌اش در زمان نوشتن پرداخت می‌شود.

## 🌱 از ساده شروع کنیم (مبتدی)

> **💡 تشبیه:** یک دفترچه‌ی تلفن که بر اساس نام خانوادگی مرتب شده. می‌توانی «مسعودی» را در چند ثانیه پیدا کنی، ولی «همه‌ی کسانی که در خیابان ولیعصر زندگی می‌کنند» یعنی خواندن کل دفترچه. مخزن NoSQL یک دفترچه با یک ترتیب مرتب‌سازی است. اگر ترتیب دوم بخواهی، دفترچه‌ی دوم چاپ می‌کنی. فضای ذخیره ارزان است؛ اسکن کل دفترچه ارزان نیست.

در SQL از موجودیت‌ها شروع می‌کنی و بعداً join می‌زنی. در یک مخزن wide-column مثل Cassandra از یک **سؤال** شروع می‌کنی: «۱۰۰ خوانش آخر سنسور `s-42` در یک روز مشخص را نشان بده». جواب این سؤال جدول را تعیین می‌کند:

```sql
-- Cassandra (CQL): one table shaped by one question
CREATE TABLE readings_by_sensor_day (
  sensor_id text,
  day       date,
  ts        timestamp,
  value     double,
  PRIMARY KEY ((sensor_id, day), ts)
) WITH CLUSTERING ORDER BY (ts DESC);

SELECT ts, value
FROM readings_by_sensor_day
WHERE sensor_id = 's-42' AND day = '2026-10-12'
LIMIT 100;
```

کلید اصلی را با دقت بخوان:

- **partition key** یعنی `(sensor_id, day)` که در پرانتز دوتایی است. همه‌ی سطرهایی با همان سنسور و روز کنار هم روی یک مجموعه‌ی replica قرار می‌گیرند.
- **clustering column** یعنی `ts` سطرهای داخل آن partition را مرتب می‌کند، اینجا از جدیدترین به قدیمی‌ترین.
- کوئری کل partition key را نام می‌برد، پس دیتابیس مستقیم به یک جا می‌رود و یک برش پیوسته را می‌خواند.

> **⚠️ مراقب باش:** اگر سؤال دیگری بپرسی، مثل «همه‌ی خوانش‌هایی که مقدارشان بیشتر از ۹۰ است روی همه‌ی سنسورها»، این جدول نمی‌تواند کارا جواب دهد. برای آن کوئری جدول دوم می‌سازی، یا از سیستم دیگری استفاده می‌کنی. در NoSQL این عادی است.

## 🔧 واقعاً چطور کار می‌کند (متوسط)

### Cassandra: partition واحد همه‌چیز است

Cassandra کلید partition را به یک token هش می‌کند، و token مشخص می‌کند کدام نودها داده را نگه می‌دارند (hash کردن سازگار؛ اصطلاح consistent-hashing را در واژه‌نامه ببین). قواعد بعدی از همین می‌آیند:

- **برابری روی کل partition key** سریع است. کوئری بدون آن تبدیل به اسکن کل خوشه می‌شود، که کند است و معمولاً به‌صورت پیش‌فرض رد می‌شود.
- **clustering columnها** کوئری‌های بازه‌ای مرتب داخل یک partition می‌دهند، مثل «۲۴ ساعت گذشته» با بازه‌ی روی `ts`.
- **اندازه‌ی partition مهم است.** partitionی که بی‌کران رشد می‌کند (یک سنسور برای همیشه) خواندن و repair آن کند می‌شود. راه حل معمول **time bucketing** است: روز یا ساعت را به partition key اضافه کن، مثل مثال بالا. راهنمایی اندازه بین نسخه‌ها عوض می‌شود، پس docs نسخه‌ی خودت را چک کن، ولی اصل ثابت است: partition ها را کران‌دار نگه دار.
- **partition keyهای با کاردینالیتی پایین hot spot می‌سازند.** کلیدی مثل `country = 'IR'` بیشتر ترافیک را روی چند replica که آن را دارند می‌ریزد. بخش با کاردینالیتی بالا (شناسه‌ی کاربر، شماره‌ی bucket) اضافه کن یا بر اساس زمان تقسیم کن.

کوئری دوم به جدول دوم نیاز دارد. تکرار هزینه‌ی آن است:

```sql
-- Same events, another question: "which sensors had an alert today?"
CREATE TABLE alerts_by_day (
  day        date,
  sensor_id  text,
  ts         timestamp,
  severity   text,
  PRIMARY KEY ((day), severity, sensor_id, ts)
);
```

جنبه‌ی بد `alerts_by_day` را ببین: همه‌ی هشدارهای یک روز در یک partition می‌افتند. اگر تعداد هشدارها زیاد باشد، آن partition داغ است. بیشتر bucket می‌کنی، مثلاً با `(day, hour)`، و برای یک روز چند partition را می‌خوانی.

> **🎤 این را در مصاحبه بگو:** «از کوئری شروع می‌کنم. partition key باید در کوئری معلوم باشد و داده را پخش کند. clustering key ترتیبی را می‌دهد که برای خواندن بازه‌ای لازم دارم. اگر کوئری دوم کلیدهای متفاوتی بخواهد، جدول اضافه می‌کنم و روی هر دو می‌نویسم.»

### HBase: یک ایندکس مرتب، یعنی row key

HBase (روی HDFS و الهام‌گرفته از Bigtable) فقط یک ایندکس دارد: **row key**. سطرها بر اساس row key مرتب ذخیره می‌شوند و هر region (یک بازه‌ی پیوسته از کلیدها) توسط یک RegionServer سرویس می‌گیرد. column familyها ستون‌هایی را که کنار هم ذخیره می‌شوند گروه می‌کنند؛ تعداد familyها را کم نگه دار، چون هر کدام فایل‌های ذخیره‌ی جدا دارند.

این قاعده‌ی اصلی HBase را می‌سازد: **طراحی row key هم الگوی خواندن و هم توزیع نوشتن را تعیین می‌کند.**

- **اسکن بازه‌ای** روی پیشوند row key ارزان است، چون سطرها کنار هم‌اند. `device-42#...` یک دستگاه را اسکن می‌کند.
- **کلید صعودی** (timestamp در ابتدا، شناسه‌ی auto-increment) همه‌ی نوشتن‌های جدید را به آخرین region می‌فرستد. آن یک سرور تبدیل به گلوگاه می‌شود. این hot spot کلاسیک است.

سه راه حل استاندارد، که اغلب با هم استفاده می‌شوند:

```python
import zlib

SALT_BUCKETS = 16
MAX_TS_MS = 9_999_999_999_999  # fixed width, 13 digits

def row_key(device_id: str, event_ts_ms: int) -> bytes:
    # 1) reversed timestamp: the newest rows of a device sort first
    reversed_ts = MAX_TS_MS - event_ts_ms
    # 2) salt: spread devices over buckets; crc32 is deterministic across processes
    salt = zlib.crc32(device_id.encode()) % SALT_BUCKETS
    # 3) fixed-width fields keep the lexicographic order correct
    return f"{salt:02d}|{device_id}|{reversed_ts:013d}".encode()
```

- **Salt** (پیشوند bucket) نوشتن‌ها را بین regionها پخش می‌کند. از شناسه‌ی دستگاه مشتق می‌شود، پس همه‌ی سطرهای یک دستگاه salt یکسان دارند و اسکن یک دستگاه هم‌چنان یک بازه‌ی پیوسته است.
- **timestamp معکوس** باعث می‌شود «آخرین N رویداد یک دستگاه» یک اسکن کوتاه از ابتدای بازه‌ی آن دستگاه باشد.
- **عددهای با عرض ثابت** مهم‌اند. `"9"` به صورت متن بعد از `"10"` می‌آید. هر عدد را به یک عرض پد کن، وگرنه ترتیب غلط است.

> **⚠️ مراقب باش:** salting پخش نوشتن را با هزینه‌ی خواندن عوض می‌کند. برای اسکن *همه‌ی* دستگاه‌ها به ترتیب زمان، حالا باید برای هر bucket یک اسکن بزنی و نتایج را ادغام کنی. قبل از salt کردن، تصمیم بگیر کدام کوئری مهم‌تر است.

### Redis: کلید همان آدرس است

Redis داده را در حافظه نگه می‌دارد و با کلید آدرس‌دهی می‌شود. مدل‌سازی یعنی انتخاب یک **ساختار داده** که با خواندن جور باشد:

```text
user:42:profile          HASH   name, country, plan       -> HGETALL for the profile page
leaderboard:2026-10      ZSET   member = user id, score   -> top 10 with ZREVRANGE
session:9f1c...          STRING with TTL                  -> expires automatically
```

برای جدول امتیازات: `ZADD leaderboard:2026-10 1500 user:42` امتیاز را می‌نویسد و `ZREVRANGE leaderboard:2026-10 0 9 WITHSCORES` ده نفر اول را می‌خواند. sorted set رتبه‌بندی را انجام می‌دهد، پس برنامه میلیون‌ها سطر را مرتب نمی‌کند. حافظه محدودیت است: هر کلید در RAM زندگی می‌کند، پس اندازه‌ی هر ساختار و سیاست TTL بخشی از مدل‌اند.

## 🧠 عمق و trade-offها (سنیور)

- **هزینه‌ی زمان نوشتن برای سرعت زمان خواندن.** هر جدول کوئری یک کپی است که باید سازگار بماند. تصمیم بگیر چه کسی همه‌ی کپی‌ها را می‌نویسد (یک سرویس، outbox، یا پایپ‌لاین stream)، و وقتی یکی از نوشتن‌ها شکست می‌خورد چه می‌شود. نوشتن idempotent کمک می‌کند: رویدادی که دو بار نوشته شود باید همان سطر را بسازد.
- **اندازه‌گیری partition یعنی capacity planning.** تعداد سطر در هر partition را از اندازه‌ی bucket و نرخ رویداد تخمین بزن. مثلاً ۲۰۰ رویداد در ثانیه برای هر سنسور یعنی ۲۰۰ × ۸۶٬۴۰۰ = ۱۷٫۲۸ میلیون رویداد در روز برای یک سنسور. یک bucket ساعتی هنوز ۲۰۰ × ۳٬۶۰۰ = ۷۲۰٬۰۰۰ رویداد دارد، که بسته به اندازه‌ی هر سطر ممکن است برای یک partition زیاد باشد، پس شاید bucket ریزتر یا کلید دیگری لازم باشد. محاسبه را در بازبینی طراحی نشان بده.
- **حذف‌ها و tombstone.** در Cassandra حذف یک tombstone می‌نویسد و خوانش‌ها باید tombstoneها را رد کنند تا compaction آن‌ها را پاک کند. جدولی شبیه صف، که مدام درج و حذف می‌شود، کند می‌شود. TTL روی داده، یا مدلی که سطرها مدام حذف نشوند را ترجیح بده.
- **سازگاری انتخابی برای هر کوئری است.** Cassandra اجازه می‌دهد سطح سازگاری را برای هر خواندن و نوشتن انتخاب کنی؛ HBase برای هر سطر سازگاری قوی دارد؛ replication در Redis به صورت پیش‌فرض async است. اول مسیر خواندن مهم را مدل کن، بعد سطح سازگاری لازمش را انتخاب کن (درس consistency-models را ببین).
- **hot keyها فقط مسئله‌ی partition نیستند.** یک کلید خیلی محبوب (پروفایل یک سلبریتی، یک شمارنده‌ی جهانی) می‌تواند یک نود را حتی با طراحی خوب partition اشباع کند. راه حل‌ها کش، تقسیم شمارنده به shardها، یا read replica است (درس pattern-hot-keys را ببین).
- **مدل را پایش کن، نه فقط خوشه را.** توزیع اندازه‌ی partition، تعداد tombstone، بار regionها در HBase و حافظه‌ی هر الگوی کلید در Redis را دنبال کن. طراحی کلیدی که ماه اول خوب بود، در مقیاس بزرگ‌تر شکست می‌خورد.
- **کی NoSQL برای این کار مناسب نیست:** اگر سؤال‌ها هر هفته عوض می‌شوند و نیاز به join بین موجودیت‌های زیاد دارند، یک دیتابیس رابطه‌ای یا انبار تغییرش ارزان‌تر است. NoSQL وقتی ارزش دارد که الگوهای دسترسی معلوم، پایدار و با حجم بالا باشند.

## 🧪 امتحان کن

یک اپلیکیشن ride-hailing پینگ‌های GPS از ۲۰۰٬۰۰۰ راننده‌ی فعال را ذخیره می‌کند، که هر کدام هر ۴ ثانیه یک پینگ می‌فرستند. دو کوئری مهم‌اند: (الف) «۵۰ پینگ آخر راننده‌ی `d-123`» برای بازپخش سفر، و (ب) «همه‌ی رانندگان داخل یک geohash cell الان» برای dispatch.

1. جدول Cassandra را برای کوئری (الف) بنویس. partition key و clustering key را انتخاب کن.
2. تعداد پینگ‌ها در روز برای کل ناوگان و تعداد سطر در روز برای هر راننده را تخمین بزن.
3. چرا `geohash` به تنهایی partition key بدی برای کوئری (ب) است؟ یک طراحی بهتر پیشنهاد بده.
4. در HBase برای اسکن بازپخش سفر چه row keyای استفاده می‌کنی، و چطور از region داغ برای پینگ‌های جدید دوری می‌کنی؟

1. `CREATE TABLE pings_by_driver_day (driver_id text, day date, ts timestamp, lat double, lon double, PRIMARY KEY ((driver_id, day), ts)) WITH CLUSTERING ORDER BY (ts DESC);` با کوئری‌ای مثل `WHERE driver_id = 'd-123' AND day = '2026-10-12' LIMIT 50`.
2. یک پینگ هر ۴ ثانیه یعنی ۸۶٬۴۰۰ / ۴ = ۲۱٬۶۰۰ پینگ برای هر راننده در روز. برای ۲۰۰٬۰۰۰ راننده، یعنی ۲۰۰٬۰۰۰ × ۲۱٬۶۰۰ = ۴٫۳۲ میلیارد پینگ در روز.
3. یک geohash cell پرتراکم (مرکز شهر) در یک زمان، همه‌ی رانندگانش را دارد و یک partition داغ می‌سازد. برای dispatch، یک جدول کوتاه‌عمر یا یک store در حافظه با کلید cell و bucket زمانی بساز، یا cellهای شلوغ را به cellهای ریزتر تقسیم کن، و آخرین موقعیت را در store مناسب lookup آخرین وضعیت نگه دار.
4. `driver_id` و بعد timestamp معکوس با یک پیشوند salt که از شناسه‌ی راننده مشتق می‌شود، مثل مثال Python بالا. salt نوشتن‌های جدید را بین regionها پخش می‌کند و timestamp معکوس «۵۰ پینگ آخر» را به یک اسکن کوتاه تبدیل می‌کند.

## 💬 گوشه‌ی مصاحبه

**سؤال: «این را برای Cassandra چطور مدل می‌کنی؟»** جواب متوسط: «کوئری‌ها را می‌نویسم، بعد برای هر کوئری یک جدول می‌سازم که مقدار جستجو partition key باشد و ترتیب مرتب‌سازی در clustering columnها.» جواب سنیور: «اندازه و رشد partition را هم چک می‌کنم. وقتی ممکن است partition بی‌کران رشد کند، بر اساس زمان bucket می‌کنم، و می‌گویم هر نوشتن چطور به همه‌ی جدول‌ها می‌رسد، با retryهای idempotent. یک هشدار پایش برای اندازه‌ی partition و تعداد tombstone اضافه می‌کنم.»

**سؤال: «چرا یکی از RegionServerهای HBase شلوغ است؟»** جواب متوسط: «احتمالاً row key صعودی است، مثل timestamp، پس هر نوشتن جدید به آخرین region می‌رود.» جواب سنیور: «اول همین را چک می‌کنم و بعد با متریک‌های بار region تأیید می‌کنم. راه حل در کلید است: پیشوند salt، timestamp معکوس برای اسکن‌های «جدیدترین اول»، و pre-split جدول تا regionها قبل از رسیدن بار وجود داشته باشند.»

**سؤال: «کی Redis را به جای یک دیتابیس برای مدل‌سازی انتخاب می‌کنی؟»** جواب متوسط: «برای خواندن کم‌تأخیر روی یک کلید معلوم، مثل session یا شمارنده.» جواب سنیور: «وقتی داده در حافظه جا می‌شود، دسترسی با کلید یا یک ساختار رتبه‌بندی ساده است، و می‌توانم replication async را بپذیرم یا داده را از یک منبع حقیقت بازسازی کنم. منبع حقیقت را جای دیگری نگه می‌دارم.»

> **🎤 این را در مصاحبه بگو:** «در مخزن NoSQL کوئری کلید را تعیین می‌کند. partition key را با کوئری هم‌خوان می‌کنم، partitionها را bucket می‌کنم تا کران‌دار بمانند، و نوشتن‌ها را پخش می‌کنم تا هیچ نود یا region واحدی همه‌ی آن‌ها را نگیرد. اگر دو کوئری کلیدهای متفاوت بخواهند، یک کپی دوم داده را می‌پذیرم و نوشتن‌ها را قابل اعتماد می‌کنم.»

## ⚠️ اشتباهات رایج

> **⚠️ مراقب باش:** گذاشتن timestamp در ابتدای row key در HBase یا partition key در Cassandra بدون bucket کردن. همه‌ی نوشتن‌های جدید به یک جا می‌روند.

> **⚠️ مراقب باش:** طراحی جدول Cassandra حول یک موجودیت و بعد اضافه کردن `ALLOW FILTERING` برای جواب دادن به کوئری جدید. این کل خوشه را اسکن می‌کند. به جای آن جدول را برای کوئری بساز.

- مدل‌سازی NoSQL مثل یک اسکیمای رابطه‌ای نرمال با کلید خارجی و انتظار join.
- استفاده از یک ستون با کاردینالیتی پایین (وضعیت، کشور) به عنوان تنها partition key.
- گذاشتن اجازه به یک partition که برای همیشه رشد کند، به جای bucket کردن بر اساس زمان.
- استفاده از یک جزء عددی در row key بدون عرض ثابت، پس ترتیب lexicographic غلط می‌شود.
- فراموش کردن اینکه هر جدول کوئری اضافه یک نوشتن است که باید سازگار نگه داشته شود.
- استفاده از یک جدول Cassandra به عنوان صف، با درج و حذف مداوم، که مخزن را با tombstone پر می‌کند.

## ✅ خودت را بسنج

1. در Cassandra partition key چه چیزی را تعیین می‌کند؟
   - A) ترتیب سطرها داخل partition
   - B) اینکه کدام replicaها داده را دارند و آیا کوئری کارا جواب داده می‌شود
   - C) نوع ستون‌های جدول
   - D) تعداد ستون‌های مجاز در جدول

<details><summary>جواب</summary>

**B** — partition key هش می‌شود تا replicaهای مالک را تعیین کند. کوئری‌ای که کل partition key را دارد به یک جا می‌رود؛ clustering columnها ترتیب داخل آن را تعیین می‌کنند.

</details>

2. در HBase کدام الگوی row key برای نوشتن‌های جدید hot spot می‌سازد؟

   - A) `device_id#reversed_ts`
   - B) `salt|device_id|ts`
   - C) `timestamp` در ابتدای کلید (صعودی یکنواخت)
   - D) `user_id` و بعد `event_type`

<details><summary>جواب</summary>

**C** — کلیدهای صعودی یکنواخت همیشه در آخرین region می‌نشینند، پس یک RegionServer همه‌ی نوشتن‌های جدید را می‌گیرد. salting یا معکوس کردن timestamp آن‌ها را پخش می‌کند.

</details>

3. یک جدول Cassandra با `PRIMARY KEY ((country), user_id)` دارد. بیشتر ترافیک از یک کشور است. خطر چیست؟

   - A) هیچ؛ clustering key بار را متعادل می‌کند
   - B) یک partition داغ روی چند replica، چون partition key با کاردینالیتی پایین نوشتن‌ها را متمرکز می‌کند
   - C) جدول نمی‌تواند `user_id` را ذخیره کند
   - D) Cassandra درج را رد می‌کند

<details><summary>جواب</summary>

**B** — `country` مقادیر کمی دارد، پس یک partition بیشتر داده و ترافیک را می‌گیرد. یک بخش با کاردینالیتی بالاتر به partition key اضافه کن یا partition را bucket کن.

</details>

4. **(سنیور)** یک تیم می‌خواهد با اضافه کردن `ALLOW FILTERING` به جدول موجود Cassandra به یک کوئری جدید جواب دهد. چرا این ایده بد است، و کار درست چیست؟

   - A) در هر نسخه خطای syntax است
   - B) اسکن بین partitionها را اجبار می‌کند که در مقیاس بزرگ کند و پرفشار است؛ یک جدول جدید با کلید مناسب کوئری بساز و روی هر دو جدول بنویس
   - C) با مرتب‌سازی در حافظه کوئری را سریع‌تر می‌کند
   - D) فقط روی clustering key اثر دارد

<details><summary>جواب</summary>

**B** — فیلتر بدون partition key، خواندن از partitionهای زیاد روی نودهای زیاد است. طراحی درست یک جدول کوئری با partition key درست است، با هزینه‌ای که در زمان نوشتن پرداخت می‌شود و سازگاری نوشتن‌ها.

</details>

5. **(سنیور)** partition شما `(sensor_id)` است و یک سنسور برای همیشه ۲۰۰ رویداد در ثانیه می‌فرستد. چرا این شکست می‌خورد، و راه حل اصولی چیست؟

   - A) سنسورها نمی‌توانند این‌همه رویداد بفرستند
   - B) partition بی‌کران رشد می‌کند و خواندن، repair و compaction را کند می‌کند؛ یک bucket زمانی مثل روز به partition key اضافه کن، و اندازه‌ی bucket را با محاسبه از نرخ رویداد تعیین کن
   - C) به جای آن برای همه‌ی سنسورها از Redis استفاده کن
   - D) رویدادها را به صورت یک سطر واحد ذخیره کن

<details><summary>جواب</summary>

**B** — partitionهای بی‌کران شکست کلاسیک Cassandra هستند. bucket زمانی اندازه را کران‌دار می‌کند، و طول bucket باید از نرخ محاسبه شود: ۲۰۰ رویداد در ثانیه یعنی ۱۷٬۲۸۰٬۰۰۰ در روز، پس یک bucket روزانه هنوز خیلی بزرگ است و bucket ساعتی یا ریزتر امن‌تر است.

</details>

## 🗂️ فلش‌کارت

| جلو | پشت |
|---|---|
| partition key در Cassandra | هش می‌شود تا replicaها را انتخاب کند؛ در هر کوئری کارا باید باشد |
| clustering column | سطرهای داخل یک partition را مرتب می‌کند؛ کوئری بازه‌ای را ممکن می‌کند |
| partition بی‌کران | بی‌پایان رشد می‌کند و خواندن و repair را کند می‌کند؛ با time bucketing حل می‌شود |
| row key در HBase | تنها ایندکس؛ سطرها بر اساس آن در regionها مرتب ذخیره می‌شوند |
| علت hot spot در HBase | row key صعودی یکنواخت، که همه‌ی نوشتن‌ها را به آخرین region می‌فرستد |
| salting | پیشوند bucket که از شناسه‌ی موجودیت مشتق می‌شود تا نوشتن‌ها بین regionها پخش شوند |
| timestamp معکوس | باعث می‌شود جدیدترین سطرهای یک موجودیت اول مرتب شوند |
| sorted set در Redis (ZSET) | ساختار رتبه‌بندی‌شده در حافظه، برای جدول امتیازات و خواندن top-N |

## 🔗 ادامه

- **nosql-families** خانواده‌های key-value، document، wide-column و graph را مقایسه می‌کند؛ این تعیین می‌کند کدام قواعد مدل‌سازی اعمال شوند.
- **partitioning-sharding** توضیح می‌دهد کلیدها چطور به نودها نگاشت می‌شوند، پایه‌ی همه‌ی قواعد این درس.
- **physical-modeling-olap** همان ایده‌ی query-first را برای موتورهای تحلیلی ستونی نشان می‌دهد.
- **pattern-hot-keys** تشخیص و کاهش hot keyها را عمیق‌تر پوشش می‌دهد.
- **storage-engines** توضیح می‌دهد LSM tree، memtable و compaction را، که رفتار tombstone و نوشتن را توضیح می‌دهند.
