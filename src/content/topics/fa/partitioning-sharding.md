## 🎯 خلاصه

> **Partitioning** (پارتیشن‌بندی) یک دیتاست بزرگ را به تکه‌های کوچک‌تر می‌شکند. **Sharding** همان پارتیشن‌بندی است، ولی تکه‌ها روی ماشین‌های مختلف پخش می‌شوند و هر ماشین مالک چند تکه است. هدف این است که هر تکه آن‌قدر کوچک باشد که بشود سریع خواندش، و بتوانی ماشین اضافه کنی بدون اینکه همه‌چیز از نو نوشته شود.

- **Range** همسایه‌ها را کنار هم نگه می‌دارد. برای range scan خوب است و برای کلیدهایی که همیشه بزرگ‌تر می‌شوند (مثل timestamp) خطرناک.
- **Hash** کلیدها را یکنواخت پخش می‌کند. برای lookup تکی خوب است و برای range scan بد.
- **پارتیشن زمانی** پیش‌فرض انبارها و lakeها است. باعث می‌شود «۷ روز اخیر» ارزان شود.
- دشمن‌های واقعی **skew** (یک پارتیشن خیلی بزرگ‌تر یا شلوغ‌تر از بقیه) و **rebalancing** (جابه‌جایی داده وقتی تعداد ماشین‌ها عوض می‌شود) هستند.

## 🌱 از ساده شروع کنیم (مبتدی)

> **💡 Analogy:** یک کتابخانه با یک میلیون کتاب. می‌توانی کتاب‌ها را بر اساس نام نویسنده (الفبایی، یعنی range) بچینی، یا با کدی که نویسنده‌ها را بین ده اتاق یکنواخت پخش کند (hash)، یا بر اساس سال انتشار (زمان). هر روش بعضی سؤال‌ها را سریع و بعضی را کند می‌کند.

فرض کن جدول کاربران ۸ ردیف دارد و ۴ سرور. از `id mod 4` به‌جای یک تابع hash واقعی استفاده می‌کنیم:

```text
Hash partitioning (id mod 4):
server 0: ids 4, 8
server 1: ids 1, 5
server 2: ids 2, 6
server 3: ids 3, 7

Range partitioning (by id):
server A: ids 1-2
server B: ids 3-4
server C: ids 5-6
server D: ids 7-8
```

حالا دو سؤال بپرس:

- «کاربر ۶ را بده.» هر دو چیدمان تو را به دقیقاً یک سرور می‌فرستند. پارتیشن‌بندی برای lookupهای تکی کمک می‌کند.
- «کاربرهای ۳ تا ۴ را بده.» range partitioning فقط سرور B را می‌خواند. hash داده‌ها را روی دو سرور پخش کرده، و در بازه‌ی بزرگ‌تر ممکن است به همه‌شان بزنیم.

پارتیشن‌بندی خودش کوئری را ارزان نمی‌کند. کاری که می‌کند این است که موتور تکه‌هایی را که لازم نیست **رد کند**، و بقیه‌ی تکه‌ها را موازی روی ماشین‌ها اجرا کند.

## 🔧 واقعاً چطور کار می‌کند (متوسط)

**اصطلاح‌ها.** آدم‌ها «partition» و «shard» را سرسری به کار می‌برند. در Postgres یا انبار داده، partition اغلب تکه‌ای از یک جدول روی یک ماشین است. shard معمولاً تکه‌ای از داده روی ماشین جداگانه است که با routing به آن می‌رسی. در Hive و Spark، partition یک directory به ازای هر مقدار است (مثلاً `dt=2026-01-01`).

**سه استراتژی کلاسیک:**

| استراتژی | چطور ردیف پارتیشنش را انتخاب می‌کند | خوب برای | بد برای |
|---|---|---|---|
| Range | کلید در بازه‌ی `[lo, hi)` می‌افتد | range scan، پنجره‌ی زمانی، داده‌ی مرتب | کلیدهای یکنواخت‌صعودی (همه‌ی نوشتن‌های جدید به آخرین بازه می‌روند)، بازه‌های ناهموار |
| Hash | `hash(key) mod N` یا موقعیت روی ring | پخش یکنواخت، lookup تکی | range scan (نتیجه پراکنده می‌شود)، عوض کردن N |
| List / directory | کلید برابر یک مقدار است (کشور، tenant) | مرزهای واضح کسب‌وکار، جداسازی هر tenant | اندازه‌ی بسیار ناهموار (یک tenant بزرگ) |

پارتیشن‌بندی range اعلانی در PostgreSQL (نسخه‌ی ۱۰ به بعد) این شکلی است:

```sql
CREATE TABLE events (id bigint, ts timestamptz, payload text)
  PARTITION BY RANGE (ts);

CREATE TABLE events_2026_01 PARTITION OF events
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

EXPLAIN SELECT * FROM events
WHERE ts >= '2026-01-10' AND ts < '2026-01-11';
-- The plan scans only events_2026_01 (partition pruning).
```

**چرا `mod N` هنگام تغییر اندازه آزاردهنده است.** با `hash mod N`، عوض کردن N تقریباً همه‌چیز را جابه‌جا می‌کند. رفتن از ۴ به ۵ سرور یک کلید را فقط وقتی نگه می‌دارد که `h mod 4 = h mod 5` باشد. این برای ۴ باقی‌مانده از هر ۲۰ تا برقرار است، پس حدود **۸۰٪ کلیدها جابه‌جا می‌شوند**. برای اضافه کردن یک نود، ۸۰٪ کل کلاستر را کپی کردن قابل قبول نیست.

**Consistent hashing** این را حل می‌کند. کلیدها و نودها را روی یک ring بگذار؛ هر کلید متعلق به اولین نود در جهت ساعت‌گرد است. اضافه کردن یک نود فقط کمانِ قبل از خودش را می‌گیرد، تقریباً `1/N` از کلیدها (حدود ۲۰٪ برای رفتن از ۴ به ۵ نود). سیستم‌هایی مثل Cassandra و store‌های سبک Dynamo، **virtual node** (چند موقعیت روی ring برای هر ماشین) دارند تا بار صاف شود. ببین [[consistent-hashing]].

**استراتژی‌های rebalancing:**

- **تعداد ثابت پارتیشن.** پارتیشن‌های خیلی بیشتر از ماشین‌ها بساز (مثلاً ۱۰۰۰ تا برای ۱۰ ماشین). جابه‌جا کردن کل یک پارتیشن ارزان است و فقط نگاشت پارتیشن به ماشین عوض می‌شود.
- **تقسیم پویا.** store‌های range (مثل HBase و Bigtable) وقتی پارتیشن از حدی بزرگ‌تر شود آن را به دو تکه تقسیم می‌کنند و تکه‌های کوچک را ادغام می‌کنند.
- **خودکار در برابر دستی.** rebalancing خودکار راحت است، ولی می‌تواند وسط اوج ترافیک جابه‌جایی سنگینی شروع کند. بیشتر تیم‌ها برای جابه‌جایی‌های بزرگ یک آدم را در حلقه نگه می‌دارند.

**Secondary indexها روی داده‌ی پارتیشن‌شده** دو شکل دارند:

- **Local index** (document-partitioned): هر پارتیشن فقط ردیف‌های خودش را ایندکس می‌کند. نوشتن به یک پارتیشن می‌خورد. کوئری با ستون غیرکلید باید به **همه‌ی** پارتیشن‌ها بزند و نتیجه‌ها را جمع کند (scatter-gather). secondary indexهای داخلی Cassandra این‌طورند.
- **Global index** (term-partitioned): خود ایندکس بر اساس مقدار ایندکس‌شده پارتیشن می‌شود. خواندن به یک پارتیشن ایندکس می‌رود، ولی نوشتن ممکن است پارتیشن‌های ایندکس روی ماشین‌های دیگر را به‌روز کند، پس کندتر یا async است. global secondary indexهای DynamoDB به این معنا async هستند.

**Request routing** جواب «کدام ماشین این کلید را دارد؟» را می‌دهد. کلاینت می‌تواند نقشه‌ی پارتیشن را داشته باشد، یک لایه‌ی routing درخواست را فوروارد کند، یا هر نود بتواند به مالک فوروارد کند. یک سرویس metadata (ZooKeeper، etcd یا کاتالوگ خود دیتابیس) نقشه را به‌روز نگه می‌دارد.

**Partition در برابر bucket در Hive و Spark.** **Partition** در Hive یا Spark یک directory به ازای هر مقدار است، پس `WHERE dt = '2026-01-10'` فقط یک directory را لیست می‌کند. **Bucket** تعداد ثابتی فایل در هر پارتیشن است که با `hash(column) mod B` انتخاب می‌شود. bucketها امکان sampling و bucketed join را می‌دهند (دو جدول که به یک شکل روی کلید join bucket شده‌اند، بدون shuffle join می‌شوند). partition بر اساس مقدار prune می‌کند؛ bucket ردیف‌ها را داخل پارتیشن سازمان می‌دهد.

## 🧠 عمق و trade-offها (سنیور)

- **skew را اندازه بگیر، حدس نزن.** نسبت `max partition size / average partition size` و همین نسبت را برای نرخ درخواست حساب کن. مثال: ۱۰ پارتیشن ۱۰۰ GB دارند و یکی‌شان ۴۰ GB است. میانگین ۱۰ GB است، پس فاکتور skew برابر ۴ است و همان یک نود گلوگاه است، حتی اگر کلاستر متعادل به‌نظر برسد.
- **کلید داغ hash را خنثی می‌کند.** hash کلیدهای *مجزا* را پخش می‌کند. یک کاربر مشهور، یک tenant بزرگ یا یک کلید «امروز» هنوز به یک پارتیشن می‌رسد. راه‌حل‌ها: کلید را بشکن (`key + suffix تصادفی 0..9` و موقع خواندن ادغام کن)، salt اضافه کن، کلید داغ را cache کن، یا tenant بزرگ را پارتیشن جدا بده. ببین [[hot-key]] و [[salting]].
- **تله‌ی پارتیشن زمانی.** پارتیشن‌بندی بر اساس `event_date` برای pruning عالی است، ولی همه‌ی نوشتن‌های جدید به پارتیشن امروز می‌روند. مطمئن شو نرخ نوشتن یک روز در توان یک پارتیشن است، یا روز جاری را با ساعت یا bucket هش زیر-پارتیشن کن.
- **تعداد پارتیشن یک trade-off است.** پارتیشن‌های کم موازی‌سازی را محدود می‌کنند و فایل‌های بزرگ و کند می‌سازند. پارتیشن‌های زیاد overhead فایل کوچک و metadata می‌آورند (metastore مثل Hive و لیست کردن object با افزایش تعداد بزرگ‌تر می‌شوند). اندازه‌ی پارتیشن را با بودجه‌ی recovery و compaction تنظیم کن، و به‌جای عدد ثابت، docs موتورت را چک کن.
- **عملیات بین شاردها گران است.** join بین شاردها جابه‌جایی داده لازم دارد و تراکنش بین شاردها به پروتکلی مثل two-phase commit نیاز دارد. unique constraint روی ستونی که کلید پارتیشن نیست سخت است. طوری طراحی کن که کوئری رایج روی یک شارد بماند: ردیف‌های مرتبط را با کلید مشترک کنار هم بیاور (مثلاً `tenant_id` در همه‌ی جدول‌ها).
- **چه چیزی را مانیتور کنی.** توزیع اندازه‌ی پارتیشن، QPS و latency percentileها برای هر پارتیشن، تعداد پارتیشن‌هایی که هر کوئری لمس می‌کند (scatter-gather نشانه‌ی خطر است)، و پیشرفت rebalancing.
- **کی شاردینگ نکنی.** اگر یک ماشین خوب تنظیم‌شده (یا مجموعه‌ی read replica) بار و داده را تحمل کند، شاردینگ فقط routing، عملیات و مشکلات سازگاری اضافه می‌کند بدون سود. شاردینگ کن وقتی لازم است، نه وقتی تصور می‌کنی شاید لازم شود.

## 🧪 امتحان کن

از PostgreSQL نسخه‌ی ۱۰ به بعد استفاده کن.

1. **Pruning.** یک جدول `events` با پارتیشن range بساز که دو پارتیشن ماهانه (ژانویه و فوریه‌ی ۲۰۲۶) دارد. روی یک کوئری برای یک روز از فوریه `EXPLAIN` بزن. کدام پارتیشن در plan ظاهر می‌شود؟
2. **Skew.** جدول `orders` کلید پارتیشن `customer_id` دارد. یک مشتری ۶۰٪ ردیف‌ها را دارد. توضیح بده چرا hash کردن کلید مشکل را حل نمی‌کند، و دو راه‌حل پیشنهاد بده.
3. **Rebalancing.** یک اسکریپت کوتاه Python بنویس که ۱۰٬۰۰۰ کلید را hash می‌کند (مثلاً با `hashlib.md5`)، کسری از کلیدها را که با `hash % n` بین ۴ و ۵ bucket پارتیشنشان عوض می‌شود حساب می‌کند، و آن را با consistent hashing با ۴ و ۵ نود مقایسه می‌کند (می‌توانی تخمین بزنی که حدود ۱/۵ کلیدها جابه‌جا می‌شوند).

<details><summary>جواب‌ها را نشان بده</summary>

**1.** فقط پارتیشن فوریه، مثلاً `events_2026_02`. planner بقیه را حذف می‌کند چون شرط یک بازه‌ی ثابت روی کلید پارتیشن است.

**2.** hash کلیدهای مجزا را پخش می‌کند. همه‌ی ردیف‌های یک مشتری کلید یکسان دارند، پس همه به یک پارتیشن می‌روند. راه‌حل‌ها: ردیف‌های آن مشتری را با یک suffix بین چند پارتیشن پخش کن (`customer_id, bucket = hash(order_id) % 8`) و در خواندن جمع بزن، یا مشتری داغ را در پارتیشن یا جدول جدا بگذار.

**3.**
```python
import hashlib

def h(key: str) -> int:
    return int.from_bytes(hashlib.md5(key.encode()).digest()[:8], "big")

keys = [f"user-{i}" for i in range(10_000)]
moved = sum(1 for k in keys if h(k) % 4 != h(k) % 5)
print(round(moved / len(keys), 2))  # about 0.8
```
consistent hashing با رفتن از ۴ به ۵ نود حدود ۱/۵ (حدود ۰.۲) کلیدها را جابه‌جا می‌کند، چون فقط کمان نود جدید مالک عوض می‌شود.

## 💬 گوشه‌ی مصاحبه

**سؤال: «جدول کاربر با ۲ میلیارد ردیف را چطور شاردینگ می‌کنی؟»** جواب متوسط: «user id را با hash روی N شارد پخش می‌کنم، با یک لایه‌ی routing و consistent hashing، تا اضافه کردن شارد فقط بخش کمی از داده را جابه‌جا کند.»

جواب سنیور: «اول الگوی دسترسی را می‌پرسم. اگر تقریباً همه‌ی کوئری‌ها با user id است، با consistent hashing و پارتیشن‌های مجازی زیاد شارد می‌کنم، تا resharding جابه‌جایی کل پارتیشن‌ها باشد. جست‌وجو با ایمیل به global index یا جدول lookup جدا با کلید ایمیل نیاز دارد. skew را اندازه می‌گیرم و کاربران داغ را جدا برنامه‌ریزی می‌کنم، و می‌پذیرم که join بین شاردها و unique constraint روی ستون‌های دیگر گران‌اند.»

**سؤال: «در Spark، partition یا bucket؟»** partition یک directory به ازای هر مقدار است و pruning می‌دهد. bucket تقسیم فایل بر اساس hash داخل یک پارتیشن است و bucketed join و sampling را ممکن می‌کند.

> **🎤 Say this in the interview:** «کلید پارتیشن را از پرکاربردترین فیلتر انتخاب می‌کنم و قبل از تعهد توزیعش را چک می‌کنم. hash پخش یکنواخت می‌دهد ولی range scan را می‌کشد، range partitioning scan می‌دهد ولی ریسک hot spot دارد، و پارتیشن زمانی pruning ارزان می‌دهد ولی نوشتن را روی یک تکه متمرکز می‌کند. rebalancing با `mod N` تقریباً همه‌چیز را جابه‌جا می‌کند، پس consistent hashing یا تعداد ثابت پارتیشن استفاده می‌کنم.»

## ⚠️ اشتباهات رایج

> **⚠️ Watch out:** کلید پارتیشنی که در شرط `WHERE` ظاهر نمی‌شود هیچ pruning‌ای نمی‌دهد. هزینه‌ی پارتیشن‌بندی را پرداخته‌ای و باز هم همه‌چیز را می‌خوانی.

> **⚠️ Watch out:** پارتیشن‌بندی روی ستونی با مقدار خیلی کم (مثلاً `country` با ۳ مقدار) چند پارتیشن خیلی بزرگ می‌سازد. ستونی با تعداد مقدار معقول انتخاب کن و اندازه‌ها را چک کن.

- انتخاب کلید یکنواخت‌صعودی (id خودافزایشی یا timestamp) برای range partitioning بدون فکر به محل نوشتن‌های جدید.
- استفاده از `hash mod N` و تعجب از اینکه اضافه کردن یک نود ۸۰٪ داده را جابه‌جا می‌کند.
- فرض اینکه hash مشکل کلید داغ را حل می‌کند. نمی‌کند؛ یک کلید همچنان یک پارتیشن است.
- انتظار اینکه unique constraint سراسری یا join بین شاردها به‌اندازه‌ی حالت محلی ارزان باشد.
- ساختن هزاران پارتیشن روزانه‌ی ریز و بعد تعجب از کندی metastore و لیست فایل‌ها.
- اشتباه گرفتن `repartition` در Spark (shuffle در حافظه) با `partitionBy` هنگام نوشتن (directoryها روی storage).

   - C) ۵۰٪
   - D) ۸۰٪

<details><summary>جواب</summary>

**D** — کلید فقط وقتی می‌ماند که `h mod 4 = h mod 5` باشد، که برای ۴ باقی‌مانده از هر ۲۰ برقرار است. حدود ۸۰٪ کلیدها جابه‌جا می‌شوند. consistent hashing حدود ۲۰٪ را جابه‌جا می‌کرد.

</details>

3. کوئری با `email` فیلتر می‌کند، ولی جدول با `user_id` پارتیشن شده و secondary index از نوع local دارد. چه می‌شود؟
   - A) یک پارتیشن را می‌خواند
   - B) خطا می‌دهد، چون index محلی است
   - C) به همه‌ی پارتیشن‌ها scatter-gather می‌زند
   - D) همیشه از global index سریع‌تر است

<details><summary>جواب</summary>

**C** — local index فقط پارتیشن خودش را پوشش می‌دهد، پس کوئری باید از همه‌ی پارتیشن‌ها بپرسد و نتیجه‌ها را ادغام کند. global index روی `email` کوئری را به یک پارتیشن ایندکس می‌فرستاد، به قیمت نوشتن کندتر یا async.

</details>

4. **(سنیور)** پارتیشن‌های روزانه برای pruning خوب‌اند، ولی job ورود داده‌ی «امروز» کند است و پارتیشن خیلی بزرگ شده. کدام تغییر ریشه‌ی مشکل را با کم‌ترین آسیب حل می‌کند؟

   - A) حذف پارتیشن‌بندی و استفاده از یک جدول
   - B) زیر-پارتیشن کردن روز جاری بر اساس ساعت یا bucket هش، و نگه داشتن چیدمان روزانه برای pruning
   - C) افزایش تعداد پارتیشن‌های روزانه به هزار تا
   - D) پارتیشن‌بندی جدول بر اساس `customer_id`

<details><summary>جواب</summary>

**B** — مشکل تمرکز نوشتن روی یک پارتیشن است. زیر-پارتیشن کردن جدیدترین داده، نوشتن را پخش می‌کند و pruning روزانه را نگه می‌دارد. گزینه‌ی A pruning را از بین می‌برد، C overhead metadata می‌آورد، و D مشکل pruning زمانی را با مشکل skew عوض می‌کند.

</details>

5. **(سنیور)** چرا تراکنش بین شاردها یک trade-off است و یک ویژگی رایگان شاردینگ نیست؟

   - A) شاردها نمی‌توانند تراکنش ذخیره کنند
   - B) به یک پروتکل هماهنگی بین ماشین‌ها نیاز دارد که تأخیر و حالت‌های خطای جدید مثل شرکت‌کننده‌ی بلاک‌شده می‌آورد
   - C) قانون اجازه‌ی تراکنش فقط روی یک ماشین را می‌دهد
   - D) برای هر ستون یک index لازم دارد

<details><summary>جواب</summary>

**B** — تراکنش بین شاردها به پروتکلی مثل two-phase commit نیاز دارد که رفت‌وبرگشت اضافه می‌کند و وقتی یک شرکت‌کننده یا coordinator خطا بدهد می‌تواند بلاک شود. طراحی‌ای که بیشتر تراکنش‌ها روی یک شارد بمانند، بیشتر این هزینه را حذف می‌کند.

</details>

## 🗂️ فلش‌کارت

| Front | Back |
|---|---|
| Partitioning در برابر sharding | Partitioning داده را تکه می‌کند؛ sharding همان partitioning بین ماشین‌ها است و هر ماشین چند تکه دارد |
| Range در برابر hash partitioning | Range همسایه‌ها را کنار هم نگه می‌دارد (scan خوب، hot spot روی کلید صعودی)؛ hash یکنواخت پخش می‌کند (lookup خوب، scan بد) |
| چرا `hash mod N` دردسرساز است | رفتن از N به N+1 نود، N/(N+1) کلیدها را جابه‌جا می‌کند؛ از ۴ به ۵ نود حدود ۸۰٪ |
| Consistent hashing | کلیدها و نودها روی ring؛ اضافه کردن یک نود حدود ۱/N کلیدها را جابه‌جا می‌کند |
| Local در برابر global secondary index | Local: نوشتن به یک پارتیشن، خواندن از همه (scatter-gather). Global: خواندن از یک پارتیشن ایندکس، نوشتن ممکن است به چند پارتیشن بخورد |
| Partition pruning | موتور پارتیشن‌هایی را که نمی‌توانند با شرط روی کلید پارتیشن match شوند رد می‌کند |
| Hot key | یک کلید با ترافیک نامتناسب؛ hash آن را حل نمی‌کند، salt یا شکستن کلید حل می‌کند |
| Hive partition در برابر bucket | Partition یک directory به ازای هر مقدار است (pruning)؛ bucket تقسیم فایل بر اساس hash داخل پارتیشن است (bucketed join) |

## 🔗 ادامه

- **[[replication]]** نشان می‌دهد هر پارتیشن برای fault tolerance چطور کپی می‌شود؛ sharding و replication معمولاً با هم به کار می‌روند.
- **[[distributed-fundamentals]]** و **[[cap-pacelc]]** توضیح می‌دهند وقتی درخواست بین شاردها پخش می‌شود چه سازگاری‌ای را از دست می‌دهی.
- **[[pattern-hot-keys]]** عمیق‌تر به راه‌حل‌های skew و مانیتورینگ می‌پردازد.
- **[[nosql-modeling]]** نشان می‌دهد چطور کلید پارتیشن را از روی کوئری انتخاب کنی، که تصمیم کلیدی در wide-column store است.
