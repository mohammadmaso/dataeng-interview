## 🎯 خلاصه

> **NoSQL** یک چیز واحد نیست. مجموعه‌ای از مدل‌های داده است که هرکدام برای یک الگوی دسترسی ساخته شده‌اند. قانونی که در مصاحبه مهم است **مدل‌سازی query-first** است: اول پرسش‌هایی را که باید سریع جواب دهی تعیین کن، بعد داده را طوری شکل بده که هر پرسش از یک جا بخواند.

- **key-value** (Redis): گرفتن و ذخیره‌کردن با کلید، خیلی سریع، اغلب در حافظه.
- **document** (MongoDB): یک رکورد تودرتو برای هر کلید، که با فیلدهای داخلش پرس‌وجو می‌شود.
- **wide-column** (Cassandra، HBase، Bigtable، ScyllaDB): ردیف‌هایی که بر اساس partition key گروه شده و با clustering key مرتب شده‌اند. برای حجم نوشتن عظیم و مسیرهای دسترسی مشخص ساخته شده.
- **graph** (Neo4j): گره‌ها و یال‌ها، برای پیمایش‌های چندمرحله‌ای.
- **search** (Elasticsearch، OpenSearch): یک inverted index برای ارتباط متنی، فیلتر و aggregation.
- **time-series**: بهینه برای نقطه‌های زمان‌دار، نگه‌داری و downsampling.

## 🌱 از ساده شروع کنیم (مبتدی)

> **💡 تشبیه:** به انواع ذخیره‌سازی در یک فروشگاه فکر کن. **جای چتر در ورودی** یک برگه می‌دهد و همان چتر را برمی‌گرداند (key-value). **پوشه‌ی پرونده‌ی شخصی** همه‌ی اطلاعات یک مشتری را در یک جا نگه می‌دارد (document). **قفسه‌ی انبار مرتب‌شده بر اساس راهرو و بعد تاریخ** اجازه می‌دهد همه‌ی سفارش‌های یک مشتری را در یک راهرو پیدا کنی (wide-column). **فهرست الفبایی پشت کتاب** اجازه می‌دهد هر صفحه‌ای را که یک کلمه در آن است پیدا کنی (search).

یک دیتابیس رابطه‌ای از جدول‌ها شروع می‌کند و بعد از شما می‌خواهد آن‌ها را join کنید. NoSQL معمولاً از **پرسش** شروع می‌کند. اگر اپ همیشه بپرسد «20 پیام آخر این چت را نشان بده»، لایه‌ی ذخیره‌سازی را طوری طراحی می‌کنی که دقیقاً همین پرسش را با یک خواندن جواب دهد.

همین ایده در کد: پروفایل کاربر در یک document جا می‌شود:

```json
{
  "_id": "user:42",
  "name": "Ali",
  "city": "Tehran",
  "devices": [
    { "os": "android", "last_seen": "2026-10-01T09:00:00Z" }
  ]
}
```

یک کلید Redis یک کار را خیلی سریع انجام می‌دهد:

```text
SET session:9f3a "user:42"  EX 3600     # expires after one hour
GET session:9f3a                       # returns "user:42"
```

نکته‌ی جونیور: **store را بر اساس پرسشی که باید سریع جواب دهد انتخاب کن، نه بر اساس برند.**

## 🔧 واقعاً چطور کار می‌کند (متوسط)

### خانواده به خانواده

| خانواده | نمونه‌ها | واحد داده | قوی در | ضعیف در |
|---|---|---|---|---|
| Key-value | Redis، DynamoDB | مقدار برای هر کلید | خواندن و نوشتن تک‌کلیدی، cache، session | پرس‌وجو بر اساس چیزی غیر از کلید |
| Document | MongoDB | document تودرتو | خواندن یک رکورد با داده‌ی تودرتو | join و تراکنش بین documentها در مقیاس |
| Wide-column | Cassandra، HBase، Bigtable، ScyllaDB | ردیف در یک partition، مرتب با clustering keyها | نوشتن سنگین، مسیرهای دسترسی مشخص، جدول‌های خیلی بزرگ | پرس‌وجوی ad hoc، join |
| Graph | Neo4j | گره و یال | پیمایش‌های چندمرحله‌ای | تحلیل حجیم، نوشتن خیلی زیاد |
| Search | Elasticsearch، OpenSearch | document با inverted index | متن کامل، ارتباط، فیلتر فاسیت‌دار | منبع حقیقت، سازگاری قوی |
| Time-series | InfluxDB، TimescaleDB (یک extension برای PostgreSQL)، و دیگران | نقطه‌ی زمان‌دار | ورود داده و کوئری‌های پنجره‌ی زمانی | کارهای رابطه‌ای عمومی |

### wide-column: کلیدهای partition و clustering در Cassandra

در Cassandra، **partition key** مشخص می‌کند کدام nodeها یک ردیف را نگه دارند (توکن از hash کلید partition ساخته می‌شود). **ستون‌های clustering** ردیف‌های داخل یک partition را روی دیسک مرتب می‌کنند. هر partition باید اندازه‌ای محدود داشته باشد.

```sql
-- CQL (Cassandra Query Language)
CREATE TABLE messages_by_chat (
  chat_id    uuid,
  sent_at    timestamp,
  msg_id     uuid,
  sender_id  bigint,
  body       text,
  PRIMARY KEY ((chat_id), sent_at, msg_id)
) WITH CLUSTERING ORDER BY (sent_at DESC, msg_id DESC);

-- Last 20 messages in one chat: one partition, read in order
SELECT sender_id, body, sent_at
FROM messages_by_chat
WHERE chat_id = 5b2e8c1a-0000-4000-8000-000000000001
LIMIT 20;
```

- `(chat_id)` کلید partition است. همه‌ی پیام‌های یک چت کنار هم زندگی می‌کنند، پس کوئری فقط یک partition را لمس می‌کند.
- `sent_at, msg_id` ستون‌های clustering هستند، پس پیام‌ها از قبل روی دیسک از جدیدترین به قدیمی‌ترین مرتب‌اند.
- join و شرط `WHERE` دلخواه وجود ندارد. برای هر پرس‌وجو یک جدول می‌سازی (**denormalize** و داده را هنگام نوشتن تکرار می‌کنی).

partitionی که بی‌حد رشد کند به **wide partition** تبدیل می‌شود. خواندن کند می‌شود، compaction سنگین و repair سخت. راه‌حل رایج اضافه کردن یک bucket زمانی به partition key است، مثلاً `((chat_id, day), sent_at, msg_id)`. اندازه‌ی partitionها را طوری نگه دار که با ده‌ها مگابایت بشود اندازه گرفت، نه گیگابایت. راهنمایی دقیق نسخه‌ی خودت را در مستندات بررسی کن.

ذخیره‌سازی Cassandra یک طراحی LSM است (به [[storage-engines]] نگاه کن). حذف‌ها tombstone می‌سازند که خواننده‌ها باید از روی آن‌ها رد شوند تا compaction پاکشان کند.

### wide-column: کلیدهای ردیف در HBase

HBase (و Bigtable که همان ایده‌ها را دارد) ردیف‌ها را بر اساس **row key** مرتب نگه می‌دارد و جدول را به **region** تقسیم می‌کند، که هرکدام بازه‌ی پیوسته‌ای از row keyهاست. row key تنها index است. column family ها واحدهای ذخیره‌سازی‌اند و column qualifierها را می‌شود برای هر ردیف آزادانه ساخت.

مشکل اصلی طراحی **hotspot** است. اگر row key با یک مقدار صعودی مثل timestamp شروع شود، هر نوشتن جدید به آخرین region می‌رود و یک سرور کل بار را می‌گیرد.

| طراحی row key | نتیجه |
|---|---|
| `2026-10-13T09:00:01_device42` | همه‌ی نوشتن‌های جدید به جدیدترین region می‌روند: hotspot |
| `device42#2026-10-13T09:00:01` | نوشتن‌ها بین دستگاه‌ها پخش می‌شوند، ولی اسکن همه‌ی دستگاه‌ها برای یک بازه‌ی زمانی سخت است |
| `salt(0-7)#device42#timestamp` | نوشتن‌ها بین 8 bucket پخش می‌شوند و خواندن‌ها به هر 8 تا fan-out می‌کنند |
| `device42#(MAX - epoch_ms)` | جدیدترین ردیف‌های یک دستگاه اول می‌آیند و دستگاه پیشوند است |

کلید را از الگوی اصلی خواندن انتخاب کن: «همه‌ی رویدادهای یک دستگاه، جدیدترین اول» به ردیف آخر اشاره دارد. HBase داده را در HFile روی HDFS ذخیره می‌کند، با MemStore در حافظه و WAL برای دوام، پس آن هم یک طراحی LSM است.

### key-value: ساختارهای داده‌ی Redis

Redis یک store در حافظه است که مقادیرش **ساختار داده** هستند، نه فقط رشته.

- **String ها:** شمارنده‌ها (`INCR`)، مقادیر cache شده، پرچم‌ها.
- **Hash ها:** یک رکورد با فیلدها، مثل پروفایل کاربر.
- **List ها:** صف‌ها و فیدهای آیتم‌های اخیر (`LPUSH`، `LTRIM`).
- **Set ها:** عضوهای یکتا و عملیات مجموعه (`SADD`، `SINTER`).
- **Sorted set ها (ZSET):** لیدربورد و بازه بر اساس امتیاز (`ZINCRBY`، `ZRANGE ... WITHSCORES`).
- **Stream ها:** logهای append-only با consumer group.
- **HyperLogLog:** شمارش تقریبی مقادیر یکتا با حافظه‌ی ثابت و کوچک. به [[probabilistic-ds]] نگاه کن.
- **Bitmap ها:** پرچم‌های فشرده برای هر کاربر.

```text
ZINCRBY leaderboard:week42 25 user:7      # add 25 points
ZREVRANGE leaderboard:week42 0 9 WITHSCORES   # top 10
```

Redis داده را در حافظه نگه می‌دارد. پایداری با snapshot های RDB و/یا یک append-only file (AOF) انجام می‌شود. اجرای دستورها در هسته تاریخاً روی یک thread بوده، پس یک دستور کند بقیه را بلاک می‌کند. کلیدهای بزرگ و اسکن‌های طولانی را از مسیر داغ بیرون نگه دار.

### search: inverted index

یک **inverted index** هر term را به فهرست documentهایی که آن را دارند وصل می‌کند (postings list). کوئری `"kafka" AND "lag"` دو postings list را اشتراک می‌گیرد، به‌جای اسکن همه‌ی documentها.

```text
"kafka"  -> [doc 3, doc 17, doc 90]
"lag"    -> [doc 17, doc 44, doc 90]
"kafka AND lag" -> [doc 17, doc 90]
```

analyzerها term ها را تعیین می‌کنند: tokenization، تبدیل به حروف کوچک، stemming و stop wordها. Elasticsearch روی Lucene ساخته شده که segmentهایش تغییرناپذیرند و در پس‌زمینه ادغام می‌شوند، شبیه یک طراحی LSM. documentهای جدید بعد از **refresh** قابل جست‌وجو می‌شوند، پس جست‌وجو تقریباً بلادرنگ است، نه فوری.

موتورهای جست‌وجو برای فیلتر و aggregation روی فیلدهای index شده عالی‌اند، ولی معمولاً یک store **مشتق‌شده** هستند. منبع حقیقت را جای دیگری نگه دار و index را از روی آن بازسازی کن.

### document: MongoDB

MongoDB درجای BSON document ذخیره می‌کند که می‌تواند آرایه و شیء تودرتو داشته باشد. انتخاب اصلی مدل‌سازی **embed در برابر reference** است:

- **embed** وقتی داده‌ی فرزند همراه والد خوانده می‌شود و اندازه‌اش محدود است (مثلاً 10 آدرس آخر یک کاربر).
- **reference** وقتی فرزندها بزرگ، بی‌حد یا مشترک‌اند (مثلاً همه‌ی سفارش‌های یک کاربر، یا محصولی که در خیلی سفارش استفاده شده).

یک document حد اندازه‌ی 16 MB دارد، پس یک آرایه‌ی بی‌حد داخل document یک باگ طراحی است. sharding با یک **shard key** انجام می‌شود، و shard key بد (صعودی یا با کاردینالیتی کم) shardهای داغ می‌سازد، همان مشکل row keyهای HBase.

## 🧠 عمق و trade-offها (سنیور)

- **اول الگوی دسترسی را انتخاب کن.** پنج تا ده پرس‌وجوی اصلی را با نرخ و هدف تأخیرشان بنویس. بعد خانواده و طراحی کلید را انتخاب کن. یک store نوسان NoSQL با schema ای که برای پرس‌وجوهای دیگر طراحی شده، در واقع یک اسکن کامل است که لباس عوض کرده.
- **سازگاری قابل تنظیم است، ولی رایگان نیست.** Cassandra از replication factor و سطح سازگاری هر کوئری (مثلاً خواندن و نوشتن `QUORUM`) استفاده می‌کند. quorumهای هم‌پوشان در حالت عادی خواندن قوی می‌دهند، ولی هنوز لبه‌های خرابی و repair دارند. قبل از وعده‌ی تضمین‌ها، [[consistency-models]] و [[cap-pacelc]] را بخوان.
- **اعداد مقیاس مهم‌اند.** اندازه‌ی partitionها، تعداد ردیف در هر partition و نرخ درخواست در هر partition را تخمین بزن. Cassandra و HBase روی nodeهای زیاد خوب کار می‌کنند، ولی یک partition یا region داغ، توان آن بازه‌ی کلید را محدود می‌کند.
- **هزینه‌ی عملیاتی.** compaction، repair، مدیریت tombstone و تقسیم region هرکدام پایش لازم دارند. یک خوشه‌ی Cassandra که رشد tombstone را نمی‌بیند، یک incident کند در انتظار است.
- **denormalization هزینه‌ی نوشتن دارد.** هر جدول پرس‌وجو یک کپی است. به‌روزرسانی نام یک کاربر ممکن است چند جدول را عوض کند. با کسب‌وکار تصمیم بگیر کدام کپی‌ها باید دقیق باشند و کدام‌ها می‌توانند به‌صورت eventual سازگار باشند.
- **search به‌عنوان index مشتق‌شده.** Elasticsearch را از یک جریان CDC یا بارگذاری دسته‌ای تغذیه کن و reindex را یک عملیات برنامه‌ریزی‌شده در نظر بگیر. به [[cdc]] نگاه کن.
- **multi-model با PostgreSQL.** JSONB و extensionها بسیاری از نیازهای document یا time-series را بدون سیستم جدید پوشش می‌دهند. انتخاب یک store جدا باید بر اساس یک شکاف اندازه‌گیری‌شده باشد، نه یک ترند. به [[postgresql]] نگاه کن.
- **کی از NoSQL استفاده نکنیم.** وقتی به پرس‌وجوهای ad hoc روی موجودیت‌های زیاد، join و تراکنش قوی روی چند رکورد نیاز داری، معمولاً یک دیتابیس رابطه‌ای یا warehouse انتخاب بهتری است. انعطاف پرس‌وجو و پشتیبانی تراکنش، بهای بسیاری از طراحی‌های NoSQL هستند.

## 🧪 امتحان کن

1. **طراحی کلید.** یک پلتفرم IoT خوانده‌های سنسور را ذخیره می‌کند و پرس‌وجوی اصلی «100 خوانده‌ی آخر برای یک سنسور» است. یک primary key برای Cassandra پیشنهاد بده و اندازه‌ی partition را برای 1 خوانده در ثانیه در 30 روز توضیح بده.
2. **hotspot.** جدول HBase تو از `yyyyMMddHHmmss#deviceId` به‌عنوان row key استفاده می‌کند و اوج نوشتن 50,000 ردیف در ثانیه است. چه چیزی خراب می‌شود، و یک راه‌حل بده که خواندن «یک دستگاه، یک بازه‌ی زمانی» را کارآمد نگه دارد.
3. **انتخاب Redis.** باید 10 بازیکن برتر هفته را داشته باشی که با هر رویداد بازی به‌روز می‌شود. کدام ساختار Redis مناسب است و کدام دستور جواب را می‌دهد؟
4. **search یا جدول؟** کاربران عنوان محصولات را با غلط املایی جست‌وجو می‌کنند و بر اساس قیمت فیلتر می‌زنند. کدام store مناسب است و منبع حقیقت کجاست؟

**1.** `PRIMARY KEY ((sensor_id, day), reading_time)` با `CLUSTERING ORDER BY (reading_time DESC)`، که `day` تاریخ است. یک سنسور در روز 86,400 خوانده دارد، پس هر partition یک روز داده را نگه می‌دارد، حدود 86,400 ردیف. برای 30 روز، هر partition یک روز را پوشش می‌دهد، نه 30 روز را. کوئری «100 خوانده‌ی آخر» partition امروز را می‌خواند و فقط اگر امروز کمتر از 100 خوانده داشته باشد به روز قبل می‌رود. بدون bucket روزانه، یک سنسور در یک partition به 2.6 میلیون ردیف (30 × 86,400) می‌رسید.

**2.** کلید با یک مقدار زمانی صعودی شروع می‌شود، پس همه‌ی نوشتن‌های جدید به آخرین region می‌روند و یک سرور بار را می‌گیرد. راه‌حل: پیشوند salt bucket (مثلاً `hash(deviceId) % 16`) یا دستگاه را اول بگذار. با دستگاه اول، کوئری «یک دستگاه، یک بازه‌ی زمانی» یک prefix scan است. نسخه‌ی salted برای هر bucket یک اسکن لازم دارد.

**3.** یک sorted set (ZSET). هر رویداد `ZINCRBY leaderboard:week42 <points> <player>` را اجرا می‌کند، و جواب با `ZREVRANGE leaderboard:week42 0 9 WITHSCORES` می‌آید.

**4.** یک موتور جست‌وجو مثل Elasticsearch تحمل غلط املایی، ارتباط و فیلترهای فاسیت‌دار را پوشش می‌دهد. منبع حقیقت در دیتابیس محصول می‌ماند و index جست‌وجو از آن با CDC به‌روز یا بازسازی می‌شود.

## 💬 گوشه‌ی مصاحبه

**سؤال: «بین Cassandra و MongoDB چطور انتخاب می‌کنی؟»** جواب متوسط: «Cassandra برای حجم نوشتن خیلی بالا با مسیرهای دسترسی مشخص است و بدون primary روی nodeها مقیاس می‌گیرد. MongoDB برای documentهای انعطاف‌پذیر با پرس‌وجوی غنی روی فیلدها مناسب است.» جواب سنیور: «از پرس‌وجوها و نرخ نوشتن شروع می‌کنم. برای یک store رویداد با نوشتن سنگین و چندمرکزی با کلیدهای مشخص، Cassandra را ترجیح می‌دهم و partition key ها را با اندازه‌ی محدود طراحی می‌کنم. اگر اپ به index ثانویه، aggregation روی فیلدهای تودرتو و تراکنش بین چند document نیاز دارد، MongoDB جور بهتری است. قبل از تصمیم، مهارت تیم عملیات را هم می‌سنجم.»

**سؤال: «برای یک جدول time-series در HBase کلید طراحی کن.»** جواب متوسط: «اول موجودیت را بگذار تا ردیف‌های یک موجودیت کنار هم باشند، بعد یک timestamp معکوس تا جدیدترین ردیف‌ها اول بیایند.» جواب سنیور: «hotspot نوشتن و الگوی خواندن را با هم بررسی می‌کنم. پیشوند salted نوشتن‌ها را پخش می‌کند، ولی هر خواندن به fan-out روی bucketهای salt تبدیل می‌شود. تعداد bucket را از اوج نرخ نوشتن و تعداد region ها انتخاب می‌کنم.»

**سؤال: «query-first modeling یعنی چه؟»** جواب متوسط: «اول پرس‌وجوها را فهرست می‌کنی، بعد هر جدول یا document را طوری طراحی می‌کنی که پرس‌وجو یک partition یا یک کلید را بخواند.» جواب سنیور: «یعنی هنگام نوشتن denormalize می‌کنی، داده‌ی تکراری را می‌پذیری و تصمیم می‌گیری کدام کپی‌ها می‌توانند eventual باشند. هزینه در مسیر به‌روزرسانی ظاهر می‌شود، پس هر دو مسیر را با هم طراحی می‌کنم.»

> **🎤 این را در مصاحبه بگو:** «خانواده‌ی NoSQL را از الگوی دسترسی انتخاب می‌کنم، نه از برند. در Cassandra برای هر پرس‌وجو یک جدول می‌سازم، با partition key ای که اندازه‌ی partition را محدود کند و clustering column هایی که ترتیب بدهند. hotspot، tombstone و compaction را پایش می‌کنم، و index های جست‌وجو را طوری نگه می‌دارم که از منبع حقیقت قابل بازسازی باشند.»

## ⚠️ اشتباهات رایج

> **⚠️ حواست باشد:** مدل‌سازی NoSQL مثل schema رابطه‌ای، و بعد درخواست join و فیلتر ad hoc. کوئری به اسکن کامل یا fan-out روی همه‌ی nodeها برمی‌گردد.

> **⚠️ حواست باشد:** یک کلید صعودی (timestamp، شناسه‌ی auto-increment) به‌عنوان پیشوند partition key یا row key. همه‌ی نوشتن‌ها به یک جا می‌روند.

- استفاده از `ALLOW FILTERING` در Cassandra برای این‌که یک کوئری کار کند. روی بسیاری از partitionها اسکن می‌کند و نشانه‌ی این است که جدول برای این کوئری درست نیست.
- اجازه دادن به رشد بی‌حد یک partition در Cassandra بدون bucket زمانی، و تبدیل شدن آن به wide partition.
- embed کردن یک آرایه‌ی بی‌حد در document مونگو تا رسیدن به حد 16 MB.
- استفاده از Redis به‌عنوان store دائمی اصلی بدون فکر کردن به تنظیمات پایداری و failover.
- استفاده از یک search index به‌عنوان منبع حقیقت.
- انتخاب یک خانواده چون محبوب است، بدون تخمین نرخ نوشتن، اندازه‌ی partition و نیاز به سازگاری.

## ✅ خودت را بسنج

1. در Cassandra کدام کلید تعیین می‌کند کدام nodeها یک ردیف را نگه دارند؟
   - A) clustering key
   - B) partition key
   - C) آخرین ستون primary key
   - D) نام جدول

<details><summary>جواب</summary>

**B** — partition key به یک توکن hash می‌شود و آن توکن nodeهای replica را تعیین می‌کند. ستون‌های clustering فقط ردیف‌های داخل partition را مرتب می‌کنند.

</details>

2. چرا یک row key صعودی در HBase مشکل ایجاد می‌کند؟
   - A) نمی‌شود آن را به بایت تبدیل کرد
   - B) همه‌ی نوشتن‌های جدید به آخرین region می‌روند، پس یک سرور بیشتر بار را می‌گیرد
   - C) HBase کلیدهای مرتب را قبول نمی‌کند
   - D) column familyها باید بر اساس زمان مرتب باشند

<details><summary>جواب</summary>

**B** — HBase ردیف‌ها را بر اساس کلید مرتب نگه می‌دارد، پس کلیدهای جدید در انتهای بازه همه به آخرین region می‌روند. این یک hotspot است.

</details>

3. کدام ساختار Redis برای یک لیدربورد زنده که بالاترین N را بر اساس امتیاز لازم دارد بهترین است؟
   - A) String
   - B) Hash
   - C) Sorted set
   - D) Stream

<details><summary>جواب</summary>

**C** — sorted set اعضا را بر اساس امتیاز مرتب نگه می‌دارد و `ZREVRANGE` مستقیم N تای برتر را برمی‌گرداند. stream یک log append-only است و اعضا را رتبه‌بندی نمی‌کند.

</details>

4. **(سنیور)** یک جدول Cassandra خواندنش کند است و compaction سنگین. تیم می‌بیند یک partition سال‌ها رویداد یک دستگاه پرکار را نگه می‌دارد. علت اصلی چیست و راه‌حل کدام است؟
   - A) تعداد nodeها کم است؛ node اضافه کن
   - B) partition بی‌حد است؛ یک bucket زمانی به partition key اضافه کن تا هر partition اندازه‌ی محدود داشته باشد
   - C) ترتیب clustering غلط است؛ فقط ترتیب صعودی بگذار
   - D) از batch size بزرگ‌تر برای نوشتن استفاده کن

<details><summary>جواب</summary>

**B** — partition بی‌حد خواندن، compaction و repair را گران می‌کند. اضافه کردن یک bucket زمانی (مثلاً روزانه یا ماهانه) به partition key اندازه را محدود می‌کند و پرس‌وجوها فقط bucketهای لازم را می‌خوانند.

</details>

5. **(سنیور)** چرا یک search index نباید منبع حقیقت باشد، حتی اگر همه‌ی داده را ذخیره کند؟
   - A) index های جست‌وجو نمی‌توانند متن ذخیره کنند
   - B) index یک ساختار مشتق‌شده و تقریباً بلادرنگ است که refresh و بازسازی دارد، پس باید از روی یک منبع حقیقت قابل بازسازی باشد
   - C) موتورهای جست‌وجو داده را بعد از 24 ساعت پاک می‌کنند
   - D) inverted index ها از فیلتر پشتیبانی نمی‌کنند

<details><summary>جواب</summary>

**B** — index جست‌وجو از داده‌ی منبع ساخته می‌شود، تقریباً بلادرنگ refresh می‌شود و قابل بازسازی است. نگه داشتن منبع حقیقت در جای دیگر، بازیابی، تغییر schema و reindex را امن‌تر می‌کند.

</details>

## 🗂️ فلش‌کارت

| جلو | پشت |
|---|---|
| query-first modeling | اول پرس‌وجوها را تعیین کن، بعد ذخیره‌سازی را طوری شکل بده که هر پرس‌وجو از یک جا بخواند |
| نقش partition key در Cassandra | به یک توکن hash می‌شود و تعیین می‌کند ردیف روی کدام nodeها است |
| نقش clustering column در Cassandra | ردیف‌های داخل یک partition را روی دیسک مرتب می‌کند |
| قاعده‌ی row key در HBase | ردیف‌ها بر اساس کلید مرتب‌اند، پس طراحی کلید hotspot و اسکن را کنترل می‌کند |
| wide partition | partitionی که بی‌حد رشد می‌کند و خواندن کند و compaction سنگین ایجاد می‌کند |
| کاربرد sorted set در Redis | اعضای رتبه‌بندی‌شده بر اساس امتیاز، با پرس‌وجوی بازه مثل بالاترین N |
| inverted index | هر term را به documentهایی که آن را دارند وصل می‌کند |
| embed در برابر reference (MongoDB) | داده‌ی فرزند محدود و همراه‌خوانده‌شده را embed کن؛ داده‌ی بزرگ یا بی‌حد را reference کن |
