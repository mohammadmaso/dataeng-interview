## 🎯 خلاصه

> لینوکس به تو ابزارهای کوچک و دقیقی می‌دهد که متن و فایل را به صورت **جریان (stream)** می‌خوانند. با زنجیر کردن آن‌ها با **pipe** (`|`) می‌توانی یک فایل چندگیگابایتی را روی یک ماشین در چند دقیقه پردازش کنی، اغلب قبل از اینکه به خوشه فکر کنی.

- پردازش جریانی بهتر از لود کردن کل فایل است: `grep`، `awk`، `sort` و `uniq` سطر به سطر کار می‌کنند و حافظه کم مصرف می‌کنند (جز `sort` که در صورت نیاز روی دیسک می‌ریزد).
- هر پروسه سه جریان استاندارد دارد: ورودی استاندارد (0)، خروجی استاندارد (1) و خطای استاندارد (2). هدایت (`>`، `>>`، `2>`، `<`) و pipe این‌ها را به هم وصل می‌کنند.
- ابزارهای دیسک و پروسه (`df`، `du`، `lsof`، `top`، `iostat`) را خوب بشناس. بیشتر مشکل‌های «مرموز» تولید یک دیسک پر، یک پروسه گیر کرده یا یک I/O اشباع‌شده است.
- اسکریپت‌هایی بنویس که با صدای بلند شکست بخورند: `set -euo pipefail`، متغیرهای داخل کوتیشن و کد خروج صریح.

## 🌱 از ساده شروع کنیم (مبتدی)

> **💡 Analogy:** یک خط مونتاژ آشپزخانه. هر ایستگاه (دستور) یک کار انجام می‌دهد و نتیجه را به ایستگاه بعدی (pipe) می‌دهد. همه‌ی مواد را یک‌جا از ایستگاهی به ایستگاه دیگر نمی‌بری؛ هر قطعه جریان دارد.

یک فایل لاگ کوچک برای تمرین بساز:

```bash
mkdir -p ~/lab && cd ~/lab
printf '%s\n' \
  '10.0.0.1 GET /home 200' \
  '10.0.0.2 GET /login 401' \
  '10.0.0.1 POST /api 500' \
  '10.0.0.3 GET /home 200' \
  '10.0.0.1 GET /home 200' > access.log
```

سه دستوری که هر روز لازم داری:

```bash
wc -l access.log          # شمارش سطرها: 5
head -n 2 access.log      # دو سطر اول
tail -n 1 access.log      # آخرین سطر
```

اولین pipeline. سؤال: «هر IP چند درخواست فرستاده، از پرکارترین به کم‌کارترین؟»

```bash
awk '{print $1}' access.log | sort | uniq -c | sort -rn
```

از چپ به راست بخوان: `awk` ستون اول (IP) را برمی‌دارد، `sort` IPهای یکسان را کنار هم می‌گذارد (`uniq` فقط تکرارهای **مجاور** را یکی می‌کند، پس مرتب‌سازی اجباری است)، `uniq -c` شمارش می‌کند، و `sort -rn` با ترتیب عددی و نزولی مرتب می‌کند.

> **⚠️ Watch out:** خروجی:

```text
      3 10.0.0.1
      1 10.0.0.2
      1 10.0.0.3
```

> **⚠️ Watch out:** `uniq` بدون `sort` شمارش غلط می‌دهد. فقط سطرهای همسایه را مقایسه می‌کند.

## 🔧 واقعاً چطور کار می‌کند (متوسط)

### جریان‌ها، هدایت و pipe

هر پروسه با سه file descriptor شروع می‌شود: `0` (ورودی)، `1` (خروجی) و `2` (خطا). pipe خروجی استاندارد یک پروسه را به ورودی استاندارد پروسه بعدی وصل می‌کند و هر دو **همزمان** اجرا می‌شوند. داده در بافرهای کوچک جابه‌جا می‌شود، پس حافظه با اندازه فایل زیاد نمی‌شود.

```bash
grep ' 500 ' access.log > errors.txt        # خروجی استاندارد به فایل (بازنویسی)
grep ' 500 ' access.log >> errors.txt       # الحاق به انتهای فایل
grep ' 500 ' access.log 2> err.log          # فقط خطای استاندارد به فایل
some_job > out.log 2>&1                     # هر دو جریان به یک فایل
```

`2>&1` یعنی «خطای استاندارد را به جایی بفرست که خروجی استاندارد الان به آن اشاره می‌کند». ترتیب مهم است: `> out.log 2>&1` درست کار می‌کند، `2>&1 > out.log` نه.

### جعبه‌ابزار متنی

| ابزار | کاربرد | مثال |
|---|---|---|
| `grep` | فیلتر سطرها با الگو | `grep -E 'ERROR\|FATAL' app.log` |
| `cut` | انتخاب فیلدها با جداکننده | `cut -d, -f1,3 data.csv` |
| `awk` | منطق فیلدها، جمع، شرط | `awk -F, 'NR>1 {s+=$3} END {print s}' sales.csv` |
| `sed` | ویرایش جریانی | `sed 's/,/\t/g' in.csv` |
| `sort` / `uniq` | گروه‌بندی و شمارش | `sort \| uniq -c` |
| `xargs` | تبدیل ورودی استاندارد به آرگومان | `find . -name '*.gz' \| xargs -n1 gunzip` |
| `split` | شکستن فایل بزرگ به تکه | `split -l 1000000 big.csv part_` |
| `jq` | پرس‌وجو از JSON خطی | `jq -r '.user_id' events.jsonl` |

`sort` ویژه است: از **external merge sort** استفاده می‌کند. تکه‌های جا شده در حافظه را مرتب می‌کند، روی فایل موقت می‌نویسد و آن‌ها را ادغام می‌کند. با `-S` (اندازه بافر حافظه)، `-T` (پوشه موقت روی دیسکی با جای خالی) و `--parallel` می‌توانی کمکش کنی.

```bash
sort -S 2G --parallel=4 -T /data/tmp big_ids.txt | uniq > unique_ids.txt
```

### پیدا کردن فایل‌ها

```bash
# ۱۰ فایل معمولی بزرگ‌تر زیر /var
find /var -type f -printf '%s\t%p\n' 2>/dev/null | sort -rn | head -n 10

# حذف فایل‌های قدیمی‌تر از ۳۰ روز، با امنیت نام فایل
find /data/staging -type f -mtime +30 -print0 | xargs -0 -r rm --
```

`-print0` همراه با `xargs -0` نام فایل‌هایی با فاصله یا خط جدید را درست مدیریت می‌کند. در اسکریپت همیشه از آن استفاده کن.

### کار موازی

برای فایل‌های مستقل می‌توانی چند worker همزمان اجرا کنی:

```bash
ls *.csv.gz | xargs -P 4 -I{} sh -c 'gunzip -c "{}" | wc -l'
```

`-P 4` چهار کار موازی می‌سازد.

### پروسه، CPU، I/O و دیسک

- `top` / `htop`: مصرف CPU و حافظه هر پروسه. load average را با تعداد هسته‌ها (`nproc`) مقایسه کن.
- `vmstat 1`: اگر `si`/`so` (swap ورودی/خروجی) غیرصفر باشد، فشار حافظه داری.
- `iostat -x 1` (بسته‌ی `sysstat`): اگر `%util` نزدیک ۱۰۰ و `await` بالا باشد، دیسک گلوگاه است.
- `df -h`: فضای آزاد هر **filesystem**. `du -sh dir/`: فضای مصرفی یک **درخت پوشه**.
- `lsof +L1`: فایل‌هایی که حذف شده‌اند اما هنوز توسط یک پروسه باز نگه داشته شده‌اند.

### زمان‌بندی و سرویس‌ها

```bash
# crontab -e : هر روز ساعت ۰۲:۰۰، خروجی و خطا به لاگ
0 2 * * * /opt/etl/run_daily.sh >> /var/log/etl/daily.log 2>&1
```

cron یک `PATH` حداقلی دارد و ترمینال ندارد. داخل اسکریپت از مسیر مطلق استفاده کن و هر دو جریان را لاگ کن. برای daemonهای بلندمدت (مثل brokerهای Kafka یا workerهای Airflow) یک unit از `systemd` بهتر است: پروسه را دوباره راه می‌اندازد، لاگ را در `journalctl` نگه می‌دارد و وابستگی‌ها را مدیریت می‌کند.

### کار از راه دور

```bash
ssh etl@db-host 'df -h /data'                  # اجرای یک دستور روی سرور دیگر
scp report.csv etl@db-host:/data/inbox/        # کپی یک فایل
rsync -avz --partial /data/export/ etl@db-host:/data/inbox/   # همگام‌سازی افزایشی و قابل ادامه
```

`rsync` برای انتقال‌های بزرگ مناسب است: فقط بخش‌های تغییرکرده را می‌فرستد و بعد از قطع اتصال ادامه می‌دهد.

### دسترسی‌ها

`ls -l` مثل `rwxr-x---` نشان می‌دهد: مالک، گروه، دیگران. `chmod 750 script.sh` یعنی مالک rwx (7)، گروه r-x (5)، دیگران هیچ (0). پایپ‌لاین‌ها معمولاً با یک کاربر سرویس اجرا می‌شوند؛ خطای `Permission denied` معمولاً مالک اشتباه یا نبودن بیت اجرا روی پوشه است.

## 🧠 عمق و trade-offها (سنیور)

- **کی از ابزارهای شل استفاده نکنیم.** pipeline شل برای یک ماشین، تحلیل‌های یک‌باره و چسب ETL عالی است. وقتی ورودی از یک دیسک بزرگ‌تر است، باید با دیتاست‌های دیگر join شود، یا retry و lineage لازم دارد، به Spark، DuckDB یا یک orchestrator برو.
- **Locale و مرتب‌سازی.** `sort` و `grep` به `LC_ALL` وابسته‌اند. در اسکریپت برای مرتب‌سازی بر اساس بایت و regex سریع `export LC_ALL=C` بگذار؛ وگرنه `sort | uniq` روی دو سرور ممکن است متفاوت رفتار کند.
- **حافظه و دیسک.** فایل‌های موقت `sort` می‌توانند `/tmp` را پر کنند. `-T` را روی دیسکی با جای کافی بگذار و قبل از جاب بزرگ `df` را بررسی کن. جابی که با «No space left on device» می‌میرد اغلب فایل خروجی نیمه‌کاره می‌گذارد؛ روی `file.tmp` بنویس و موفق که شدی `mv` کن.
- **دیسک پر است ولی `du` فضای خالی نشان می‌دهد.** دو علت رایج: (۱) یک فایل لاگ حذف شده ولی هنوز توسط پروسه باز است، پس بلوک‌هایش آزاد نمی‌شود. `lsof +L1` آن را نشان می‌دهد؛ به جای حذف، پروسه را ری‌استارت کن یا فایل را خالی کن. (۲) `df` کل filesystem را می‌بیند، از جمله بلوک‌های رزرو. همچنین با `df -i` inodeها را بررسی کن: ممکن است دیسک پر از فایل‌های ریز باشد بی‌آنکه بایت آزاد داشته باشد.
- **مشاهده‌پذیری.** برای هر اسکریپت batch زمان شروع، تعداد سطر ورودی، تعداد سطر خروجی و کد خروج را لاگ کن. روی کد خروج هشدار بده، نه روی وجود یک سطر لاگ. `set -o pipefail` را فعال کن: بدون آن، کد خروج pipeline فقط کد آخرین دستور است و `bad_cmd | wc -l` موفق به نظر می‌رسد.
- **اسکریپت‌های قابل اجرای مجدد.** روی یک اسم موقت بنویس، اعتبارسنجی کن، بعد rename کن. با `flock` قفل بگذار تا دو اجرای cron روی هم نیفتند. این نسخه‌ی شل [[idempotency]] است.

```bash
#!/usr/bin/env bash
set -euo pipefail

IN_DIR="/data/inbox"
OUT="/data/clean/events.csv"
LOCK="/tmp/events_etl.lock"

exec 9>"$LOCK"
flock -n 9 || { echo "another run is active" >&2; exit 0; }

tmp="$(mktemp "${OUT}.XXXX")"
trap 'rm -f "$tmp"' EXIT

for f in "$IN_DIR"/*.csv; do
  [ -e "$f" ] || { echo "no input files" >&2; exit 1; }
  tail -n +2 "$f"
done | awk -F, 'NF == 4' > "$tmp"     # فقط سطرهای با ۴ فیلد

[ -s "$tmp" ] || { echo "empty output, aborting" >&2; exit 1; }
mv "$tmp" "$OUT"
echo "rows: $(wc -l < "$OUT")"
```

`trap` فایل موقت را در هر خروجی پاک می‌کند، و `mv` روی همان filesystem باعث می‌شود فایل نهایی به‌صورت اتمیک ظاهر شود.

## 🧪 امتحان کن

از `access.log` ابتدای درس (یا هر لاگ دلخواه) استفاده کن.

1. سه کد وضعیت پرتکرار را همراه با تعدادشان، از بیشترین به کمترین، چاپ کن.
2. تعداد درخواست‌های هر IP را فقط برای `GET` بشمار.
3. برای یک CSV بزرگ با هدر، مجموع ستون سوم را بدون لود کردن فایل در Python چاپ کن.

<details><summary>راه‌حل‌ها را نشان بده</summary>

**1.**
```bash
awk '{print $4}' access.log | sort | uniq -c | sort -rn | head -n 3
```

**2.**

</details>

## 💬 گوشه‌ی مصاحبه

**سؤال: «در یک فایل لاگ بزرگ، IPهای یکتا را بشمار.»** جواب متوسط: «`awk '{print $1}' log | sort | uniq -c`. مرتب‌سازی لازم است چون `uniq` فقط سطرهای مجاور را می‌بیند.» جواب سنیور: «همین pipeline برای یک فایل ۱۰۰ گیگی روی یک ماشین با `LC_ALL=C` و یک پوشه‌ی موقت روی دیسک بزرگ کار می‌کند. برای شمارش دقیق که در حافظه جا نمی‌شود، سراغ شمارش تقریبی مثل [[hyperloglog]] می‌روم، یا موتور توزیع‌شده اگر داده در lake است.»

**سؤال: «۱۰ فایل بزرگ‌تر را پیدا کن.»** جواب متوسط: «`du -ah / | sort -rh | head`.» جواب سنیور: «`du` کل درخت را پیمایش می‌کند و روی میلیون‌ها فایل کند است. من `find ... -printf '%s %p\n' | sort -rn | head` را با محدودیت `-xdev` روی filesystem مشکوک، و روی سرور production با اولویت پایین I/O (`ionice -c3`) اجرا می‌کنم.»

**سؤال: «دیسک پر است ولی `du` فضای خالی نشان می‌دهد؛ چرا؟»** جواب سنیور: «یا یک فایل حذف‌شده هنوز توسط پروسه باز است (`lsof +L1` نشانش می‌دهد و فضا با پایان پروسه یا خالی شدن فایل آزاد می‌شود)، یا inode تمام شده (`df -i`)، یا یک mount point فایل‌های زیرش را پنهان کرده. من به همین ترتیب بررسی می‌کنم.»

> **🎤 Say this in the interview:** «من با جریان‌ها شروع می‌کنم: `grep`، `awk`، `sort | uniq -c`، `head`. می‌دانم کی یک pipeline روی یک ماشین کافی است و کی داده به Spark نیاز دارد. اسکریپت‌ها را با `set -euo pipefail`، فایل موقت و قفل می‌نویسم تا اجرای مجدد امن باشد.»

## ⚠️ اشتباهات رایج

> **⚠️ Watch out:** `rm -rf $DIR/*` وقتی `DIR` خالی یا تنظیم‌نشده باشد، از ریشه حذف می‌کند. متغیرها را داخل کوتیشن بگذار و از `${DIR:?}` استفاده کن تا زودتر شکست بخورد.

- پارس کردن خروجی `ls` در اسکریپت. نام فایل با فاصله آن را خراب می‌کند؛ از glob یا `find -print0` استفاده کن.
- فراموش کردن `sort` قبل از `uniq`.
- اعتماد به کد خروج یک pipeline بدون `pipefail`.
- حذف یک فایل لاگ بزرگ که پروسه هنوز در آن می‌نویسد. فضا آزاد نمی‌شود.
- نوشتن مستقیم خروجی نهایی؛ کرش وسط کار یک فایل نیمه‌کاره می‌گذارد که معتبر به نظر می‌رسد.
- اجرای جاب‌های `cron` با مسیر نسبی و بدون `PATH`، و بعد دیباگ کردن «توی ترمینال من کار می‌کند».
- استفاده از `grep` روی فایل فشرده‌ی gzip بدون `zgrep` یا `zcat`.

## ✅ خودت را بسنج

۱. کدام جفت دستور درست تعداد هر مقدار متمایز ستون اول را می‌شمارد؟
   - A) `cut -f1 f | uniq -c`
   - B) `cut -f1 f | sort | uniq -c`
   - C) `uniq -c f | sort`
   - D) `sort f | cut -f1 -c`

<details><summary>جواب</summary>

**B** — `uniq` فقط تکرارهای مجاور را یکی می‌کند، پس مقادیر باید اول مرتب شوند. گزینه‌ی A روی ورودی مرتب‌نشده شمارش غلط می‌دهد.

</details>

۲. دستور `./load.sh | tee load.log` اجرا می‌شود و اسکریپت شکست می‌خورد، ولی pipeline کد خروج ۰ می‌دهد. چه چیزی جا افتاده؟
   - A) `set -x`
   - B) `set -o pipefail` (یا `set -euo pipefail`)
   - C) `nohup`
   - D) `chmod +x`

<details><summary>جواب</summary>

**B** — بدون `pipefail` کد خروج pipeline، کد آخرین دستور (`tee`) است که موفق بوده. با `pipefail` کد خروج اولین دستور شکست‌خورده برگردانده می‌شود.

</details>

۳. پارتیشن `/var` ۱۰۰٪ پر است. یک فایل لاگ ۴۰ گیگی را حذف کردی ولی `df -h` هنوز ۱۰۰٪ نشان می‌دهد. محتمل‌ترین علت چیست؟
   - A) `df` نتیجه را کش می‌کند؛ ۲۴ ساعت صبر کن
   - B) یک پروسه هنوز فایل حذف‌شده را باز دارد؛ بلوک‌ها فقط وقتی آزاد می‌شوند که فایل بسته شود
   - C) لاگ باید جابه‌جا شود، نه حذف
   - D) `du` به پرچم `-a` نیاز دارد

<details><summary>جواب</summary>

**B** — ورودی دایرکتوری رفته ولی inode و بلوک‌ها تا وقتی یک file descriptor باز است باقی می‌مانند. `lsof +L1` آن را پیدا می‌کند. ری‌استارت پروسه (یا خالی کردن فایل با `: > file` اگر پروسه باید ادامه دهد) فضا را آزاد می‌کند.

</details>

۴. **(سنیور)** یک جاب شبانه روی یک سرور ۱۶ هسته‌ای ۲ ترابایت JSON فشرده‌ی gzip را می‌خواند و باید لیست یکتای user ID تولید کند. کدام رویکرد قابل دفاع‌تر است و ریسک اصلی چیست؟
   - A) `cat *.gz | sort -u` با پوشه‌ی موقت پیش‌فرض؛ ریسکی ندارد
   - B) استخراج موازی هر فایل با `xargs -P`، ادغام مرتب و یکتا با `sort -u` و `-T` روی دیسک بزرگ، و `mv` اتمیک در پایان؛ ریسک این است که دیسک موقت پر شود
   - C) لود کردن همه‌چیز در یک dict پایتون در یک پروسه؛ ریسک فقط سرعت است
   - D) `grep -c` روی هر فایل؛ ریسک این است که `grep` نمی‌تواند gzip بخواند

<details><summary>جواب</summary>

**B** — استخراج موازی از هسته‌ها استفاده می‌کند، `sort -u` با حافظه محدود و ریختن روی دیسک ادغام می‌کند، و `mv` اتمیک اجرای مجدد را امن نگه می‌دارد. ریسک این است که فایل‌های موقت می‌توانند بخش بزرگی از ۲ ترابایت را بخواهند، پس اول فضای آزاد را بسنج. گزینه‌ی A `/tmp` کوچک را نادیده می‌گیرد، C حافظه را تمام می‌کند، D تعداد سطر می‌شمارد و ID تولید نمی‌کند.

</details>

۵. **(سنیور)** چرا `cron` ابزار اشتباه برای daemonی است که بعد از کرش باید دوباره بالا بیاید؟
   - A) `cron` نمی‌تواند اسکریپت شل اجرا کند
   - B) `cron` جاب‌ها را طبق زمان‌بندی شروع می‌کند؛ پروسه‌ی بلندمدت را نظارت یا ری‌استارت نمی‌کند، کاری که `systemd` انجام می‌دهد
   - C) `cron` فقط با root اجرا می‌شود
   - D) `cron` نمی‌تواند لاگ بنویسد

<details><summary>جواب</summary>

**B** — cron زمان‌بند جاب‌های یک‌باره است. یک سرویس `systemd` با `Restart=on-failure` پروسه را نظارت می‌کند، لاگ‌هایش را در journal نگه می‌دارد و آن را بعد از وابستگی‌هایش راه می‌اندازد.

</details>

## 🗂️ فلش‌کارت

| Front | Back |
|---|---|
| چرا قبل از `uniq` باید sort کنیم؟ | `uniq` فقط سطرهای مجاور را مقایسه می‌کند؛ sort سطرهای یکسان را کنار هم می‌گذارد |
| `2>&1` یعنی چه؟ | خطای استاندارد را به جایی بفرست که خروجی استاندارد الان به آن اشاره می‌کند |
| `set -o pipefail` چه می‌کند؟ | اگر هر دستوری در pipeline شکست بخورد کل pipeline شکست می‌خورد، نه فقط آخری |
| `xargs -0` با `find -print0` | مدیریت امن نام فایل‌هایی با فاصله یا خط جدید |
| `df` در برابر `du` | `df`: فضای آزاد هر filesystem؛ `du`: فضای مصرفی یک درخت پوشه |
| دیسک پر، `du` فضای خالی نشان می‌دهد | فایل حذف‌شده‌ای که هنوز باز است (`lsof +L1`)، یا نبود inode آزاد (`df -i`) |
| `sort` با فایل‌های بزرگ چه می‌کند؟ | external merge sort: تکه‌های مرتب روی دیسک، بعد ادغام |
| چرا در جاب‌های cron از `flock` استفاده کنیم؟ | جلوگیری از همپوشانی اجراها و خراب شدن خروجی |

## 🔗 ادامه

- **python-large-files** همان ایده‌ی «جریانی بخوان، لود نکن» را با generator و خواندن تکه‌ای در Python نشان می‌دهد.
- **file-ingestion** و **data-formats** توضیح می‌دهند فایل‌هایی که با این ابزارها پردازش می‌کنی (CSV، JSON خطی، Parquet) چه ساختاری دارند.
- **networking-essentials** ترافیک `ssh`، `rsync` و HTTP را توضیح می‌دهد که داده را بین این ماشین‌ها جابه‌جا می‌کند.
- [[shuffle]] نسخه‌ی توزیع‌شده‌ی الگوی sort-and-group را توضیح می‌دهد که اینجا با `sort | uniq` دیدی.
- یک بار `man sort`، `man find` و `man awk` را بخوان؛ فهرست گزینه‌ها سریع‌ترین راه برای جلوگیری از نتیجه‌ی غلط در production است.
