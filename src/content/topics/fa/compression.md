## 🎯 خلاصه

> فشرده‌سازی **زمان CPU** را با **بایت** عوض می‌کند. بایت کمتر یعنی دیسک، شبکه و I/O کمتر. هزینه‌اش CPU برای فشرده‌سازی و باز کردن است و، در بعضی فرمت‌ها، از دست رفتن **قابلیت تقسیم (splittability)**، یعنی توانایی خواندن فایل به تکه‌های موازی.

- **gzip**: نسبت فشرده‌سازی خوب، کمی کند، انتخاب استاندارد برای فایل‌های متنی. فایل متنی gzip‌شده قابل تقسیم نیست.
- **snappy**: خیلی سریع، نسبت متوسط، بدون سطح فشرده‌سازی. انتخاب رایج در پشته‌های ستونی و streaming.
- **lz4**: سریع‌ترین باز کردن، نسبت پایین‌تر. مناسب مسیرهای داغ (hot path).
- **zstd**: قابل تنظیم از سریع تا خیلی قوی، نسبت خوب با سرعت خوب، و پشتیبانی از dictionary آموزش‌دیده. انتخاب قوی برای سیستم‌های جدید.
- فشرده‌سازی روی داده‌ی **ستونی و encode‌شده** بهترین نتیجه را می‌دهد: اول encoding (dictionary، run-length، delta)، بعد یک codec عمومی.

## 🌱 از ساده شروع کنیم (مبتدی)

> **💡 تشبیه:** بستن چمدان. لباس‌ها را محکم تا کنی (فشرده‌سازی)، چمدان سبک‌تر می‌شود و حمل آن راحت‌تر است (شبکه و دیسک). ولی تا کردن و باز کردن زمان می‌برد. اگر سفر کوتاه است و حمل‌کننده سریع است، سبک بسته‌بندی کن. اگر کانتینر را از اقیانوس می‌فرستی، هر چه محکم‌تر بهتر.

ایده‌ی اصلی را با عدد ببین. فرض کن باید **۱۰ گیگابایت** لاگ را روی لینک **۱ گیگابیت** بر ثانیه جابه‌جا کنی. ۱ گیگابیت بر ثانیه یعنی ۱۲۵ مگابایت بر ثانیه.

- خام: ۱۰٬۰۰۰ مگابایت / ۱۲۵ مگابایت بر ثانیه = **۸۰ ثانیه** روی سیم.
- فشرده با نسبت ۴:۱: ۲٬۵۰۰ مگابایت / ۱۲۵ = **۲۰ ثانیه** روی سیم، به‌علاوه‌ی زمان CPU برای فشرده‌سازی و باز کردن.

این‌که فشرده‌سازی برنده باشد یا نه، بستگی دارد به این‌که گلوگاه شبکه (یا دیسک) باشد یا CPU. هر دو جواب با داده تغییر می‌کنند.

دو اصطلاحی که مدام می‌شنوی:

- **نسبت فشرده‌سازی (ratio)**: حجم اصلی تقسیم بر حجم فشرده. `10 GB -> 2.5 GB` نسبت ۴:۱ یا ۴x است.
- **قابل تقسیم (splittable)**: یک فایل بزرگ می‌تواند توسط چند worker پردازش شود، هر کدام یک بازه‌ی بایتی متفاوت را بخوانند. به همین دلیل Spark یا Hadoop می‌توانند روی یک فایل چند task بسازند.

## 🔧 واقعاً چطور کار می‌کند (متوسط)

### codecها

| Codec | نسبت | سرعت فشرده‌سازی | سرعت باز کردن | سطح | کاربرد معمول |
|---|---|---|---|---|---|
| gzip (DEFLATE) | بالا | کند تا متوسط | متوسط | دارد | آرشیو، خروجی متنی، HTTP |
| snappy | متوسط | خیلی سریع | خیلی سریع | ندارد | انتخاب رایج Parquet و streaming |
| lz4 | پایین تا متوسط | خیلی سریع | سریع‌ترین | دارد | مسیرهای داغ، cache، پیش‌فرض ClickHouse |
| zstd | بالا (قابل تنظیم) | سریع تا کند | سریع | دارد (۱ تا ۲۲) | عمومی، سیستم‌های جدید، dictionary |

سرعت‌ها **نسبی‌اند**. همیشه داده‌ی خودت را روی سخت‌افزار خودت اندازه بگیر. اسکریپت زیر codecهای کتابخانه‌ی استاندارد را روی لاگ مصنوعی اجرا می‌کند تا شکل این trade-off را ببینی:

```python
import bz2
import gzip
import lzma
import random
import time
import zlib

random.seed(7)
# Synthetic web-log lines: repetitive paths and status codes, like real logs
PATHS = ["/home", "/search?q=kafka", "/api/v1/orders", "/static/app.js", "/login"]
lines = []
for i in range(200_000):
    lines.append(f"2026-10-01T12:{i % 60:02d}:00Z GET {random.choice(PATHS)} "
                 f"{random.choice([200, 200, 200, 404, 500])} {random.randint(100, 9000)}\n")
raw = "".join(lines).encode("utf-8")

codecs = {
    "zlib (DEFLATE, gzip's core)": (lambda b: zlib.compress(b, 6), zlib.decompress),
    "gzip level 6": (lambda b: gzip.compress(b, compresslevel=6), gzip.decompress),
    "bz2 level 9": (lambda b: bz2.compress(b, 9), bz2.decompress),
    "lzma (xz) preset 6": (lambda b: lzma.compress(b, preset=6), lzma.decompress),
}

print(f"raw size: {len(raw) / 1e6:.1f} MB")
for name, (enc, dec) in codecs.items():
    t0 = time.perf_counter()
    packed = enc(raw)
    t1 = time.perf_counter()
    restored = dec(packed)
    t2 = time.perf_counter()
    assert restored == raw, "round trip failed"
    print(f"{name:28s} ratio {len(raw) / len(packed):6.1f}x  "
          f"compress {t1 - t0:6.3f}s  decompress {t2 - t1:6.3f}s")
```

اجرایش کن. codecهای قوی‌تر (bz2، lzma) نسبت بهتری می‌دهند ولی برای فشرده‌سازی CPU خیلی بیشتری می‌خواهند. زمان‌ها به ماشین تو بستگی دارند، پس آن‌ها را الگو بدان، نه benchmark.

### قابلیت تقسیم: هزینه‌ی پنهان

فرمت قابل تقسیم اجازه می‌دهد یک موتور فایل ۱۰ گیگابایتی را به ۱۰۰ تکه‌ی ۱۰۰ مگابایتی بخواند، به‌صورت موازی. یک جریان فشرده‌ی غیرقابل تقسیم باید از اول خوانده شود، پس **یک task کل فایل را می‌خواند**.

- یک **CSV با gzip** قابل تقسیم نیست. یک task در Spark کل فایل را می‌گیرد و executorهای دیگر منتظر می‌مانند.
- یک فایل **Parquet** به row groupها و column chunkها تقسیم می‌شود. فشرده‌سازی **داخل** این واحدها انجام می‌شود، پس فایل هر codecی که انتخاب کنی قابل تقسیم می‌ماند.
- **Avro** بلوک‌های داده‌اش را با codec انتخابی فشرده می‌کند، پس فایل در مرز بلوک‌ها قابل تقسیم می‌ماند، مثل Parquet.

قاعده: برای متن خام، فرمت بلوکی قابل تقسیم یا فایل‌های کوچک فشرده‌نشده را ترجیح بده. برای داده‌ی ستونی، فشرده‌سازی داخل خود فرمت این مشکل را ندارد.

### فشرده‌سازی در Kafka

Kafka **batch**های رکورد را فشرده می‌کند، نه پیام‌های تکی. codec را producer تنظیم می‌کند:

```properties
# producer configuration
compression.type=zstd
linger.ms=20
batch.size=131072
```

batchهای بزرگ‌تر بهتر فشرده می‌شوند، و به همین خاطر `linger.ms` و `batch.size` مهم‌اند. broker batch را همان‌طور که دریافت کرده ذخیره می‌کند. مصرف‌کننده آن را باز می‌کند. اگر تنظیم topic در broker با producer فرق داشته باشد، broker ممکن است دوباره فشرده کند که CPU broker را مصرف می‌کند. codec را بین producerها و topicها یکسان نگه دار.

### فشرده‌سازی در Parquet و Spark

فرمت‌های ستونی هر column chunk را جداگانه فشرده می‌کنند. ستون رشته‌های کم‌تکرار (کد کشور، وضعیت) خیلی بهتر از ستون UUIDهای تصادفی فشرده می‌شود، چون **encoding** (dictionary، run-length، delta) قبل از اجرای codec بیشترِ کار را انجام می‌دهد.

```python
(df.write
   .option("compression", "zstd")          # codec for the Parquet output
   .mode("overwrite")
   .parquet("s3a://lake/bronze/events/"))
```

همین تنظیم به‌صورت کانفیگ Spark SQL با نام `spark.sql.parquet.compression.codec` هم در دسترس است. به‌جای فرض کردن مقدار پیش‌فرض، آن را برای نسخه‌ی Spark خودت بررسی کن.

### فشرده‌سازی در ClickHouse

ClickHouse امکان انتخاب codec را **برای هر ستون** می‌دهد، و codecهای تخصصی دارد که قبل از codec عمومی اجرا می‌شوند:

```sql
CREATE TABLE events
(
    ts       DateTime CODEC(DoubleDelta, ZSTD(1)),
    user_id  UInt64   CODEC(Delta, ZSTD),
    url      String   CODEC(ZSTD(3))
)
ENGINE = MergeTree
ORDER BY ts;
```

`DoubleDelta` زمان‌های صعودی را به اختلاف‌های نزدیک به صفر تبدیل می‌کند، و codec عمومی بعد از آن خوب فشرده می‌کند. سطح بالاتر ZSTD، CPU هنگام insert را بیشتر می‌کند و در عوض partهای کوچک‌تری روی دیسک می‌سازد.

## 🧠 عمق و trade-offها (سنیور)

- **بر اساس گلوگاه انتخاب کن.** اگر خوشه به شبکه گیر کرده (ترافیک بین AZ، object storage کند)، codec قوی‌تر می‌ارزد. اگر CPU گلوگاه است (join یا regexی که هسته‌ها را پر کرده)، codec سبک‌تر مثل snappy یا lz4 کل‌اش ارزان‌تر است. زمان کل job را اندازه بگیر، نه فقط حجم فایل را.
- **سطح فشرده‌سازی یک دستگیره است، نه یک flag.** برای zstd، سطح‌های ۱ تا ۳ سریع و ارزان‌اند؛ سطح‌های خیلی بالا هزینه‌ی CPU زیادی برای بهره‌ی کم اضافه می‌کنند. برای ingestion معمولاً سطح سریع درست است؛ برای آرشیو سرد، سطح بالا.
- **فایل‌های کوچک فشرده‌سازی را خراب می‌کنند.** فشرده‌سازی تعداد زیادی فایل ریز نسبت بد می‌دهد و overhead هر فایل را اضافه می‌کند. فایل‌های کوچک را قبل از فشرده‌سازی ادغام کن و [[small-files]] را ببین.
- **Dictionary.** zstd می‌تواند از روی نمونه‌هایی از رکوردهای کوچک و مشابه (مثلاً رویدادهای JSON با یک schema) dictionary آموزش دهد. این برای topicهای Kafka و key-value storeهایی با پیام‌های کوچک کمک می‌کند که هر پیام تنها خوب فشرده نمی‌شود.
- **داده‌ی رمزشده فشرده نمی‌شود.** اول فشرده کن، بعد رمز کن، نه برعکس. متن رمزشده تصادفی به نظر می‌رسد و codec نمی‌تواند کوچکش کند.
- **پایش.** حجم ورودی و خروجی هر topic یا جدول، نسبت فشرده‌سازی در طول زمان، CPU روی producerها و brokerها، و زمان باز کردن در مصرف‌کننده‌ها را دنبال کن. افت ناگهانی نسبت معمولاً یعنی schema بالادستی عوض شده (مثلاً یک ستون ID تصادفی اضافه شده).
- **سازگاری.** هر مصرف‌کننده باید codec را پشتیبانی کند. codec جدید را فقط بعد از ارتقای همه‌ی readerها منتشر کن، وگرنه خطاهای خواندن می‌بینی که شبیه خرابی داده‌اند.

## 🧪 امتحان کن

از اسکریپت پایتون بخش متوسط استفاده کن، یا هر دیتاست خودت با بیش از ۱۰ مگابایت متن.

1. **نسبت در برابر CPU.** codecها را به دو مورد gzip سطح ۱ و gzip سطح ۹ تغییر بده. پیش‌بینی کن کدام بهتر فشرده می‌کند و کدام زمان بیشتری می‌برد. بعد اجرا کن.
2. **قابلیت تقسیم.** در دو جمله توضیح بده چرا یک CSV ۵۰ گیگابایتی با gzip روی خوشه‌ی Spark با ۱۰۰ executor ممکن است کندتر از یک فایل Parquet ۵ گیگابایتی از همان داده اجرا شود.
3. **محاسبه‌ی Kafka.** یک producer با سرعت ۲۰۰ مگابایت بر ثانیه JSON می‌فرستد. فشرده‌سازی نسبت ۵:۱ می‌دهد. چند مگابایت بر ثانیه روی شبکه می‌رود، و اگر retention هفت روز باشد، روزانه چقدر دیسک (با حجم فشرده) صرفه‌جویی می‌شود؟

<details><summary>جواب‌ها را نشان بده</summary>

**۱.** نسخه‌ی سطح ۹ بهتر فشرده می‌کند و زمان فشرده‌سازی بیشتری دارد؛ زمان باز کردن معمولاً نزدیک است. عددهای دقیق به داده و ماشین بستگی دارند.

**۲.** فایل gzip قابل تقسیم نیست، پس یک task کل ۵۰ گیگابایت را می‌خواند و ۹۹ executor دیگر کاری ندارند. فایل Parquet به row groupهای زیادی تقسیم می‌شود، کار بین کل خوشه پخش می‌شود و هر task فقط ستون‌های لازم را می‌خواند.

**۳.** روی شبکه: ۲۰۰ / ۵ = ۴۰ مگابایت بر ثانیه. روزانه: ۴۰ × ۸۶٬۴۰۰ = ۳٬۴۵۶٬۰۰۰ مگابایت، یعنی حدود ۳٬۴۵۶ گیگابایت یا ۳.۴۵۶ ترابایت داده‌ی فشرده در روز. بدون فشرده‌سازی: ۲۰۰ × ۸۶٬۴۰۰ = ۱۷٬۲۸۰٬۰۰۰ مگابایت یعنی ۱۷.۲۸ ترابایت در روز. برای هفت روز retention: حدود ۲۴.۲ ترابایت فشرده در برابر ۱۲۰.۹۶ ترابایت خام، یعنی حدود ۹۶.۸ ترابایت صرفه‌جویی.

## 💬 گوشه‌ی مصاحبه

**سؤال: «برای یک topic از رویدادهای JSON در Kafka کدام فشرده‌سازی را انتخاب می‌کنی؟»**
جواب متوسط: «zstd یا lz4 را در producer می‌گذارم، با batching تا batchها برای فشرده‌سازی به اندازه‌ی کافی بزرگ باشند.»
جواب سنیور: «بستگی به گلوگاه دارد. اگر brokerها یا شبکه محدودیت‌اند، zstd با سطح متوسط، چون نسبت، دیسک و ترافیک بین AZ را کم می‌کند. اگر producerها CPU-bound‌اند، lz4 یا snappy. با `linger.ms` batch می‌سازم تا فشرده‌سازی داده‌ی کافی ببیند، و قبل از تغییر codec مطمئن می‌شوم همه‌ی مصرف‌کننده‌ها آن را پشتیبانی می‌کنند.»

**سؤال: «چرا job من برای یک فایل ۴۰ گیگابایتی فقط یک task دارد؟»**
جواب متوسط: «احتمالاً متن gzip شده است که قابل تقسیم نیست.»
جواب سنیور: «جریان gzip نقطه‌ی تقسیم داخلی ندارد، پس Spark کل فایل را به یک task می‌دهد. راه‌حل این است که داده را به Parquet یا فرمت بلوکی دیگری بنویسی، یا ورودی را به چند فایل فشرده‌ی جدا تقسیم کنی تا موازی‌سازی از تعداد فایل‌ها بیاید.»

> **🎤 این را در مصاحبه بگو:** «فشرده‌سازی CPU را با بایت عوض می‌کند. codec را بر اساس گلوگاه انتخاب می‌کنم، قابل تقسیم بودن فرمت را چک می‌کنم، و نسبت و زمان باز کردن را روی داده‌ی واقعی تست می‌کنم قبل از این‌که تصمیم بگیرم.»

## ⚠️ اشتباهات رایج

> **⚠️ توجه:** فایل متنی gzip شده قابل تقسیم نیست. یک `.csv.gz` ۵۰ گیگابایتی، هر قدر executor هم اضافه کنی، در یک task اجرا می‌شود.

> **⚠️ توجه:** فشرده‌سازی داده‌ای که از قبل فشرده یا رمزشده است، سودی ندارد و CPU را هدر می‌دهد.

- انتخاب بالاترین سطح به‌صورت پیش‌فرض. بهره‌ی اضافی اغلب کم است و هزینه‌ی CPU زیاد.
- قضاوت codec فقط با نسبت. زمان باز کردن را هم حساب کن، چون خواننده‌ها در هر query آن را می‌پردازند.
- فشرده‌سازی پیام‌های ریز یکی‌یکی در Kafka. از batching استفاده کن.
- فراموش کردن این‌که codec باید برای هر مصرف‌کننده و موتور قابل خواندن باشد.
- رمزکردن قبل از فشرده‌سازی که نسبت را از بین می‌برد.
- فرض کردن codec پیش‌فرض Spark یا Kafka بدون بررسی نسخه‌ای که اجرا می‌کنی.

2. یک فایل ۴۰ گیگابایتی `.csv.gz` توسط یک job در Spark خوانده می‌شود. محتمل‌ترین علامت چیست؟
   - A) خیلی از taskها سریع تمام می‌شوند
   - B) یک task بیشتر کار را انجام می‌دهد و بقیه‌ی executorها بیکارند
   - C) فایل اصلاً قابل خواندن نیست
   - D) pushdown مربوط به Parquet خودکار اعمال می‌شود

<details><summary>جواب</summary>

**B** — جریان gzip قابل تقسیم نیست، پس کل فایل به یک task می‌رسد. بقیه‌ی executorها چیزی برای خواندن ندارند.

</details>

3. چرا فایل‌های Parquet با gzip یا zstd هم قابل تقسیم می‌مانند؟
   - A) فشرده‌سازی روی کل فایل اعمال می‌شود
   - B) فشرده‌سازی جداگانه روی هر row group و column chunk اعمال می‌شود، پس هر واحد مستقل است
   - C) Parquet فشرده‌سازی را غیرفعال می‌کند
   - D) Parquet داده را به‌صورت ASCII ذخیره می‌کند

<details><summary>جواب</summary>

**B** — فایل به واحدهای فشرده‌شده‌ی مستقل تقسیم می‌شود. خواننده می‌تواند مستقیم به یک row group برود و فقط همان را باز کند.

</details>

4. (سنیور) producer به یک سطح بالاتر zstd رفته، CPU برای brokerها به‌شدت بالا رفته ولی ترافیک شبکه تغییری نکرده. علت محتمل چیست و چه چیزی را بررسی می‌کنی؟

<details><summary>جواب</summary>

محتمل‌ترین علت recompression است: تنظیم `compression.type` در topic با آنچه producer می‌فرستد فرق دارد، پس brokerها هر batch را باز و دوباره encode می‌کنند. تنظیم topic را بررسی کن و با producer یکسان کن. سپس با اندازه‌گیری نسبت و latency end-to-end تصمیم بگیر که سطح بالاتر ارزش هزینه‌ی CPU را دارد یا نه. زمان باز کردن به سطح فشرده‌سازی زیاد وابسته نیست، پس مصرف‌کننده‌ها معمولاً مقصر نیستند.

</details>

5. چرا رمزنگاری باید بعد از فشرده‌سازی بیاید؟
   - A) رمزنگاری روی داده‌ی فشرده کندتر است
   - B) خروجی رمزشده تصادفی به نظر می‌رسد، پس نمی‌توان فشرده‌اش کرد
   - C) فشرده‌سازی به کلید نیاز دارد
   - D) کلید داخل بلوک فشرده ذخیره می‌شود

<details><summary>جواب</summary>

**B** — رمزنگاری خوب الگوی تکراری ندارد، پس codec نمی‌تواند کوچکش کند. اول فشرده کن، بعد رمز کن.

</details>

## 🗂️ فلش‌کارت

| جلو | پشت |
|---|---|
| نسبت فشرده‌سازی (ratio) | حجم اصلی تقسیم بر حجم فشرده، مثلاً ۴:۱ |
| قابل تقسیم (splittable) | فایل بتواند توسط چند task موازی، هر کدام روی یک بازه‌ی بایتی یا بلوکی، خوانده شود |
| چرا CSV با gzip سخت موازی می‌شود؟ | gzip یک جریان یکپارچه است و نقطه‌ی تقسیم داخلی ندارد |
| سریع‌ترین باز کردن در این درس | lz4 (با نسبت پایین‌تر) |
| codec قابل تنظیم با dictionary | zstd |
| Parquet کجا فشرده می‌کند؟ | داخل هر row group و column chunk |
| Kafka فشرده‌سازی را روی چه واحدی انجام می‌دهد؟ | batch رکوردها، با تنظیم `compression.type` در producer |
| فشرده‌سازی قبل یا بعد از رمزنگاری؟ | قبل. متن رمزشده فشرده نمی‌شود. |
