## 🎯 خلاصه

> سه روش شناخته‌شده به یک سؤال جواب می‌دهند: **کل یک انبار داده را چطور ساختار بدهیم**، نه یک جدول. **Inmon** اول یک انبار سازمانی نرمال می‌سازد و data markها را از آن مشتق می‌کند. **Kimball** data markهای ابعادی (اسکیمای ستاره‌ای) می‌سازد و آن‌ها را با بُعدهای مشترک و یکسان (conformed) به هم وصل می‌کند. **Data Vault 2.0** تاریخچه را در hubها، linkها و satelliteهایی نگه می‌دارد که فقط درج می‌شوند، و marts ستاره‌ای را روی آن می‌سازد.

- **Inmon (از بالا به پایین):** یک انبار یکپارچه و نرمال (3NF)؛ marts کپی یا view از آن هستند.
- **Kimball (از پایین به بالا):** data markهای ابعادی که پرس‌وجو آسان است؛ بُعدهای conformed آن‌ها را هماهنگ نگه می‌دارند.
- **Data Vault 2.0 (ترکیبی، قابل حسابرسی):** کلید کسب‌وکار، روابط و تاریخچه‌ی توصیفی جدا می‌شوند؛ بارگذاری موازی و فقط‌درج است.
- هیچ‌کدام «بهترین» نیستند. تفاوتشان در این است که به چه کسی خدمت می‌کنند، چقدر سریع تحویل می‌دهند، و با حسابرسی و تغییر چطور کنار می‌آیند.

## 🌱 از ساده شروع کنیم (مبتدی)

> **💡 تشبیه:** سه روش برای مرتب کردن سوابق یک شهر بزرگ. **Inmon** یک آرشیو مرکزی و کاملاً بایگانی‌شده نگه می‌دارد و از آن برای هر اداره یک اتاق مطالعه‌ی کوچک می‌سازد. **Kimball** اول برای هر اداره یک اتاق مطالعه باز می‌کند، ولی مطمئن می‌شود همه‌ی اتاق‌ها برای «مشتری» و «تاریخ» از همان کارت‌های فهرست استفاده کنند. **Data Vault** هر واقعیت را در سه نوع پوشه نگه می‌دارد: یکی برای *چه کسی یا چه چیزی* (کلید کسب‌وکار)، یکی برای *چیزها چطور به هم وصل‌اند*، و یکی برای *چه چیزی را کی می‌دانستیم* (تاریخچه). واقعیت‌های جدید فقط اضافه می‌شوند و هرگز بازنویسی نمی‌شوند.

برای مبتدی سؤال عملی این است: «داده‌ام کجا می‌رود و داشبورد چه چیزی را می‌خواند؟» یک بانک با مشتری و حساب را در نظر بگیر:

- **Inmon:** داده‌ی مشتری و حساب در جدول‌های نرمال انبار مرکزی می‌رود. گزارش «موجودی مشتری» از یک mart خوانده می‌شود که از آن جدول‌ها ساخته شده.
- **Kimball:** فوراً `fact_account_balance` را با `dim_customer` و `dim_date` می‌سازی. گزارش مستقیم از همان ستاره می‌خواند.
- **Data Vault:** کلید مشتری به یک *hub* می‌رود، رابطه‌ی مشتری-حساب به یک *link*، و نام و آدرس‌های متغیر به یک *satellite* با زمان‌بندی. گزارش از یک ستاره‌ی ساخته‌شده روی vault می‌خواند.

> **⚠️ مراقب باش:** این‌ها سه *اسکیمای* متفاوت برای یک جدول نیستند. سه *معماری* متفاوت برای کل انبار هستند. یک ستاره‌ی Kimball می‌تواند روی انبار Inmon بنشیند، و Data Vault معمولاً با ستاره‌ها برای گزارش جفت می‌شود.

## 🔧 واقعاً چطور کار می‌کند (متوسط)

### Inmon: کارخانه‌ی اطلاعات سازمانی

Inmon که اغلب «پدر انبار داده» نامیده می‌شود، انباری **موضوع‌محور، یکپارچه، زمان‌دار و غیرفرار (non-volatile)** تعریف می‌کند. در عمل:

1. سیستم‌های مبدأ در یک مدل **نرمال (3NF)** سازمانی یکپارچه می‌شوند، با یک تعریف واحد از «مشتری» و «حساب».
2. **data martهای وابسته** برای هر بخش از انبار سازمانی مشتق می‌شوند. یک mart اغلب کپی denormalize شده یا یک view است.
3. تاریخچه به طراحی نگه داشته می‌شود، چون انبار زمان‌دار است.

قدرتش یک منبع حقیقت واحد است. هزینه‌اش زمان است: طراحی کامل یک مدل سازمانی قبل از اولین داشبورد می‌تواند ماه‌ها طول بکشد.

### Kimball: معماری ناوگان ابعادی (bus)

Kimball از یک فرایند کسب‌وکار شروع می‌کند: «سفارش‌ها»، «پرداخت‌ها»، «ارسال‌ها». برای هر فرایند یک **مدل ابعادی** می‌سازی (جدول فکت در grain اعلام‌شده، و بُعدها دورش). ایده‌ی کلیدی **bus matrix** است: جدولی که فرایندها را در برابر بُعدها می‌گذارد. بُعدهایی که چند فرایند استفاده می‌کنند **conformed** هستند: همان `dim_customer` با همان کلیدها و ویژگی‌ها.

با بُعدهای conformed، martهایی که در زمان‌های مختلف ساخته شده‌اند هم‌چنان با هم می‌خوانند. هزینه‌اش نظم است: کسی باید مالک بُعدهای conformed باشد، وگرنه هر mart از بقیه دور می‌شود.

### Data Vault 2.0: hubها، linkها و satelliteها

Data Vault (Dan Linstedt) هر جدول مبدأ را به سه نوع مفهوم تقسیم می‌کند:

| ساختار | چه چیزی نگه می‌دارد | مثال | ویژگی کلیدی |
|---|---|---|---|
| **Hub** | یک کلید کسب‌وکار و metadata بارگذاری | `hub_customer` (شماره‌ی مشتری) | برای هر کلید کسب‌وکار یک سطر، برای همیشه |
| **Link** | رابطه بین hubها | `link_customer_order` | ذاتاً many-to-many؛ یک سطر برای هر ترکیب |
| **Satellite** | ویژگی‌های توصیفی و تاریخچه | `sat_customer_details` (نام، ایمیل، کشور) | وقتی ویژگی عوض شود یک سطر جدید (`load_dts`) |

نسخه‌ی 2.0 **hash key** اضافه می‌کند. کلید هر hub، link و satellite یک hash قطعی (مثلاً MD5 یا SHA-256) از کلید کسب‌وکار نرمال‌شده است. hash key به لودرهای مختلف اجازه می‌دهد موازی اجرا شوند بدون اینکه به sequence مراجعه کنند، و کار انتقال vault بین سیستم‌ها را ساده‌تر می‌کند.

```sql
-- Data Vault 2.0 sketch (Postgres syntax; hash keys as hex text)
CREATE TABLE hub_customer (
  customer_hk   char(32) PRIMARY KEY,   -- hash of the normalized business key
  customer_bk   text NOT NULL UNIQUE,   -- for example the CRM customer number
  load_dts      timestamptz NOT NULL,
  record_source text NOT NULL
);

CREATE TABLE hub_order (
  order_hk      char(32) PRIMARY KEY,
  order_bk      text NOT NULL UNIQUE,
  load_dts      timestamptz NOT NULL,
  record_source text NOT NULL
);

CREATE TABLE link_customer_order (
  link_hk       char(32) PRIMARY KEY,   -- hash of the combined business keys
  customer_hk   char(32) NOT NULL REFERENCES hub_customer (customer_hk),
  order_hk      char(32) NOT NULL REFERENCES hub_order (order_hk),
  load_dts      timestamptz NOT NULL,
  record_source text NOT NULL,
  UNIQUE (customer_hk, order_hk)
);

CREATE TABLE sat_customer_details (
  customer_hk   char(32) NOT NULL REFERENCES hub_customer (customer_hk),
  load_dts      timestamptz NOT NULL,
  hash_diff     char(32) NOT NULL,      -- hash of the descriptive columns
  name          text,
  email         text,
  country       char(2),
  record_source text NOT NULL,
  PRIMARY KEY (customer_hk, load_dts)
);
```

به چیزی که نیست دقت کن: نه update، نه delete. تغییر ایمیل مشتری یک سطر جدید در satellite می‌سازد که `hash_diff` آن با سطر قبلی فرق دارد. تاریخچه خود جدول است.

### جایی که Data Vault تمام می‌شود و martها شروع می‌شوند

Raw Vault داده را همان‌طور که رسیده ذخیره می‌کند، بدون قاعده‌ی کسب‌وکار. یک **business vault** قواعد مشتق‌شده را اضافه می‌کند. **Information martها** (معمولاً ستاره) برای گزارش ساخته می‌شوند، اغلب با جدول‌های **PIT** (point-in-time) و **bridge** که join بین satelliteها را کارا می‌کنند.

```mermaid
flowchart LR
    SRC[Source systems] --> STG[Staging]
    STG --> RV[Raw Vault: hubs, links, satellites]
    RV --> BV[Business Vault: derived rules]
    BV --> MART[Information marts: star schemas]
    MART --> BI[BI tools]
```

### کنار هم

| پرسش | Inmon | Kimball | Data Vault 2.0 |
|---|---|---|---|
| جهت | از بالا (اول سازمان) | از پایین (فرایند به فرایند) | ترکیبی: مخزن یکپارچه‌ی خام، سپس marts |
| مدل اصلی | 3NF نرمال | اسکیمای ستاره‌ای | hubها، linkها، satelliteها |
| زمان تا اولین mart | کند | سریع | متوسط (vault به‌علاوه martها) |
| تاریخچه و حسابرسی | خوب | بسته به انتخاب SCD | قوی‌ترین (فقط‌درج، زمان بارگذاری، منبع رکورد) |
| سرعت کوئری BI | از طریق martها | بهترین (برای همین طراحی شده) | از طریق martها؛ join در vault سنگین‌تر است |
| بارگذاری موازی | سخت‌تر | متوسط | آسان (hash key، بدون sequence) |
| تغییر یک مبدأ | اثر روی مدل سازمانی | اثر روی martهای مرتبط | افزودن satellite؛ ساختارهای موجود می‌مانند |
| تناسب معمول | سازمان بزرگ با تیم مرکزی قوی | تیم‌های تحلیلی که سریع داشبورد لازم دارند | صنایع تحت مقررات که مسیر حسابرسی می‌خواهند |

## 🧠 عمق و trade-offها (سنیور)

- **حسابرسی دلیل اصلی انتخاب Data Vault در بانک‌هاست.** هر سطر `load_dts` و `record_source` دارد، چیزی بازنویسی نمی‌شود، و می‌توانی هر وضعیت گذشته را بازسازی کنی. ناظران می‌پرسند «آن روز چه می‌دانستید؟» و vault مستقیم جواب می‌دهد.
- **هزینه join و لایه‌هاست.** سؤال «آدرس فعلی مشتری» ممکن است یک hub، یک satellite و یک جدول PIT و بعد یک mart را join کند. لایه‌ها را خودکار کن (dbt، تولیدکننده‌ی کد) و business vault را کوچک نگه دار. خیلی از تیم‌ها vault را انبار می‌دانند و تحلیلگران را از ستاره‌ها سرویس می‌دهند.
- **Kimball یعنی «بدون تاریخچه» نیست.** Kimball تاریخچه را با انواع SCD روی بُعدها مدیریت می‌کند. تفاوت در محل نگه‌داری تاریخچه‌ی کامل است: در بُعد (Kimball) یا در satelliteها (Data Vault).
- **مدل سازمانی Inmon سخت‌ترین برای درست شدن است.** قبل از تحویل نیاز به توافق بین بخش‌ها دارد. در سازمان بزرگ با تیم حاکمیت داده قوی کار می‌کند؛ بدون آن متوقف می‌شود.
- **hash keyها:** با یک hash خوب برخورد نادر است، ولی باید ورودی را نرمال کنی (trim، حروف بزرگ/کوچک، مدیریت null، جداکننده‌های ثابت) وگرنه یک کلید کسب‌وکار یکسان hash های متفاوت می‌گیرد. تابع hash را یک‌بار تعیین کن و هرگز عوضش نکن، چون کلیدها همه‌جا ذخیره شده‌اند.
- **واقعیت ترکیبی:** بیشتر انبارهای واقعی روش‌ها را مخلوط می‌کنند. یک ستاره‌ی Kimball روی چیدمان medallion در lakehouse، یا یک لایه‌ی خام Data Vault با martهای Kimball، رایج است. به جای دفاع از یک روش خالص، لایه‌ها و قاعده‌ی هر لایه را نام ببر.
- **کی از Data Vault استفاده نکنیم:** برای تیم کوچک با چند مبدأ و گزارش ساده، یک ستاره‌ی Kimball با SCD2 سریع‌تر تحویل داده می‌شود و استخدام نیرو برایش آسان‌تر است.

## 🧪 امتحان کن

یک شرکت خرده‌فروشی منابع `customers` (CRM)، `orders` (فروشگاه آنلاین) و `payments` (بانک) دارد. مدیریت یک داشبورد درآمد ماهانه و یک مسیر حسابرسی برای هر تغییر آدرس مشتری می‌خواهد.

1. در Data Vault کدام ساختار تاریخچه‌ی آدرس مشتری را نگه می‌دارد و چه ستون‌هایی لازم دارد؟
2. یک ستاره‌ی Kimball برای همین تاریخچه‌ی آدرس کدام بُعد را استفاده می‌کند، و کدام نوع SCD تاریخچه‌ی کامل را می‌دهد؟
3. یک دلیل برای انتخاب Data Vault و یک دلیل برای انتخاب Kimball اینجا بگو.
4. چرا لودر باید کلید کسب‌وکار را قبل از hash کردن نرمال کند؟

<details><summary>حدست چیست؟</summary>

1. یک satellite روی `hub_customer`، مثلاً `sat_customer_address`، با `customer_hk`، `load_dts`، `hash_diff`، ستون‌های آدرس و `record_source`. هر تغییر یک سطر اضافه می‌کند.
2. یک `dim_customer` با ویژگی‌های آدرس که به صورت SCD نوع ۲ (valid_from، valid_to، is_current) ردیابی می‌شوند. این تاریخچه‌ی کامل را در بُعد نگه می‌دارد.
3. Data Vault برای حسابرسی و بارگذاری موازی چند مبدأ قوی است. Kimball برای تحویل سریع داشبورد درآمد و تحلیلگرانی که ساده‌تر کار می‌کنند بهتر است.
4. همان کلید کسب‌وکار به شکل `" C-001"`، `"c-001"` یا `"C-001 "` hash های متفاوت می‌دهد، پس یک مشتری به چند hub تبدیل می‌شود. نرمال‌سازی (trim، حروف یکسان، مدیریت null یکسان، جداکننده‌ی ثابت) hash را قطعی می‌کند.

## 💬 گوشه‌ی مصاحبه

**سؤال: «Inmon یا Kimball، کدام را انتخاب می‌کنی؟»** جواب متوسط: «Kimball برای داشبورد سریع، Inmon برای یک منبع حقیقت واحد.» جواب سنیور: «به سازمان بستگی دارد. می‌پرسم چه کسی انبار را مصرف می‌کند، ارزش کسب‌وکار اولیه باید چه‌قدر سریع برسد، و الزامات حسابرسی چقدر سخت‌گیرانه‌اند. در عمل بُعدهای conformed به سبک Kimball می‌سازم، و اگر مبدأها زیاد و ناپایدار باشند، یک لایه‌ی تاریخ‌دار زیرش می‌گذارم که ایده‌های Inmon یا Data Vault در آن کمک می‌کنند.»

**سؤال: «Data Vault چیست و چرا بانک‌ها آن را دوست دارند؟»** جواب متوسط: «داده را به hubها برای کلیدهای کسب‌وکار، linkها برای روابط و satelliteها برای تاریخچه تقسیم می‌کند. بانک‌ها برای حسابرسی دوستش دارند.» جواب سنیور: «هر سطر فقط‌درج است و با منبعش زمان‌گذاری شده، پس می‌توانم هر وضعیت گذشته را بازتولید کنم و ثابت کنم چه چیزی کی بارگذاری شده. بارگذاری موازی است چون hash keyها به جستجوی sequence نیاز ندارند. هزینه join بیشتر است، پس برای گزارش martهای ستاره‌ای روی آن می‌گذارم.»

**سؤال: «conformed dimension چیست؟»** بُعدی است که بین جدول‌های فکت با همان کلیدها و همان معنا به اشتراک گذاشته می‌شود، و این اجازه می‌دهد martها به شکل منظم ترکیب شوند. bus matrix ابزار برنامه‌ریزی Kimball برای پیدا کردن آن‌هاست.

> **🎤 این را در مصاحبه بگو:** «روش را با محدودیت‌ها انتخاب می‌کنم. Kimball martهای سریع و قابل پرس‌وجو با بُعدهای conformed می‌دهد. Inmon یک مدل سازمانی یکپارچه می‌دهد. Data Vault تاریخچه‌ی قابل حسابرسی و فقط‌درج و بارگذاری موازی می‌دهد، با martهای ستاره‌ای روی آن. بیشتر انبارهای واقعی ترکیبی‌اند، و برای هر لایه، نام و قاعده‌اش را می‌گویم.»

## ⚠️ اشتباهات رایج

> **⚠️ مراقب باش:** گفتن اینکه Data Vault «یک اسکیمای ستاره‌ای با hubها» است. این مدل متفاوتی برای ذخیره و تاریخچه است. ستاره برای پرس‌وجو است؛ vault برای یکپارچه‌سازی و حسابرسی.

> **⚠️ مراقب باش:** پرس‌وجو مستقیم از raw vault در BI. join ها زیاد و خروجی سخت‌خوان است. برای مصرف‌کنندگان mart بساز.

- دیدن سه روش به عنوان متقابلاً انحصاری. معماری ترکیبی قاعده است.
- ساختن یک مدل کامل Inmon سازمانی قبل از تحویل هر ارزش کسب‌وکار.
- ساختن hub از کلیدی که پایدار نیست (مثلاً کد وضعیت) به جای شناسه.
- ذخیره‌ی ویژگی‌های توصیفی در hub یا link. آن‌ها باید در satellite باشند.
- hash کردن کلیدهای کسب‌وکار بدون نرمال‌سازی، و بعد تعجب از ظاهر شدن تکرار.
- بازنویسی سطرهای satellite، که مسیر حسابرسی را که این روش برایش وجود دارد پاک می‌کند.

## ✅ خودت را بسنج

1. کدام روش ابتدا یک انبار سازمانی نرمال می‌سازد و martها را از آن مشتق می‌کند؟
   - A) Kimball
   - B) Inmon
   - C) Data Vault 2.0
   - D) Medallion

<details><summary>جواب</summary>

**B** — رویکرد از بالا به پایین Inmon یک انبار 3NF یکپارچه‌ی سازمانی می‌سازد. martهای وابسته از آن مشتق می‌شوند.

</details>

2. در Data Vault ویژگی‌های توصیفی مثل ایمیل و تاریخچه‌شان کجا می‌روند؟
   - A) Hub
   - B) Link
   - C) Satellite
   - D) Bridge

<details><summary>جواب</summary>

**C** — satelliteها ویژگی‌های توصیفی و تاریخچه را با زمان بارگذاری نگه می‌دارند. hubها فقط کلید کسب‌وکار و metadata دارند و linkها روابط را.

</details>

3. کدام مفهوم Kimball اجازه می‌دهد چند mart روی معنای «مشتری» توافق داشته باشند؟

   - A) junk dimension
   - B) conformed dimension
   - C) degenerate dimension
   - D) mini-dimension

<details><summary>جواب</summary>

**B** — بُعد conformed بین جدول‌های فکت کلیدها و تعریف یکسان دارد، پس martهایی که در زمان‌های مختلف ساخته شده‌اند به شکل منظم ترکیب می‌شوند.

</details>

4. **(سنیور)** حسابرس می‌پرسد دو سال پیش آدرس مشتری در چه بوده، و داده یک سال است با Data Vault بارگذاری شده. چه چیزی این را پاسخ‌پذیر می‌کند، و پاسخ دادن چه هزینه‌ای دارد؟

   - A) هیچ؛ Data Vault تاریخچه نگه نمی‌دارد
   - B) سطرهای satellite فقط‌درج و با `load_dts` زمان‌دار هستند، پس سطر معتبر در آن زمان را انتخاب می‌کنی؛ هزینه join بیشتر است که یک جدول PIT یا mart می‌تواند برای کوئری‌های رایج پنهانش کند
   - C) باید یک backup پایگاه داده را بازیابی کنی
   - D) hubها آدرس را بر اساس سال نگه می‌دارند

<details><summary>جواب</summary>

**B** — satelliteهای فقط‌درج با زمان بارگذاری اجازه می‌دهند هر وضعیت گذشته بازسازی شود. trade-off تعداد join بیشتر است؛ جدول‌های PIT و martها هزینه را برای کوئری‌های رایج کم می‌کنند.

</details>

5. **(سنیور)** یک تیم کلیدهای کسب‌وکار را برای hubها hash می‌کند، ولی بعد از اینکه یک مبدأ کلیدها را با حروف کوچک و فاصله‌ی انتهایی می‌فرستد، مشتری‌های تکراری می‌گیرد. ریشه‌ی مشکل و راه حل چیست؟

   - A) تابع hash خراب است؛ به sequence برو
   - B) کلید کسب‌وکار قبل از hash نرمال نشده، پس کلیدهای برابر hash های متفاوت می‌دهند؛ به طور یکسان نرمال کن (trim، حروف، مدیریت null، جداکننده‌ها) و تعریف تابع را هرگز عوض نکن
   - C) hubها نمی‌توانند کلید متنی نگه دارند
   - D) satelliteها باعث تکرار در hub می‌شوند

<details><summary>جواب</summary>

**B** — یک کلید منطقی دو hash تولید می‌کند. قبل از hash نرمال کن و تعریف hash را ثابت نگه دار، چون کلیدها در کل vault ذخیره شده‌اند.

</details>

## 🗂️ فلش‌کارت

| جلو | پشت |
|---|---|
| Inmon | از بالا به پایین: انبار یکپارچه‌ی 3NF سازمانی، martها از آن مشتق می‌شوند |
| Kimball | از پایین به بالا: martهای ابعادی با بُعدهای conformed، با bus matrix برنامه‌ریزی می‌شوند |
| hub در Data Vault | یک سطر برای هر کلید کسب‌وکار به همراه metadata بارگذاری |
| link در Data Vault | رابطه بین hubها؛ یک سطر برای هر ترکیب |
| satellite در Data Vault | ویژگی‌های توصیفی و تاریخچه، فقط‌درج، با زمان بارگذاری |
| hash key (DV 2.0) | hash قطعی کلید کسب‌وکار نرمال‌شده؛ امکان بارگذاری موازی |
| raw vault در برابر business vault | raw داده را همان‌طور که رسیده نگه می‌دارد؛ business vault قواعد مشتق‌شده اضافه می‌کند |
| قوی‌ترین حسابرسی | Data Vault: فقط‌درج، `load_dts` و `record_source` در هر سطر |

## 🔗 ادامه

- **dimensional-modeling** اسکیمای ستاره‌ای و بُعدهای conformed را پوشش می‌دهد که Kimball و بیشتر martها به آن تکیه دارند.
- **scd** توضیح می‌دهد Kimball چطور تاریخچه را درون بُعدها نگه می‌دارد، برای مقایسه با satelliteها.
- **medallion-architecture** لایه‌های bronze، silver و gold را نشان می‌دهد که اغلب کنار vault در طراحی‌های lakehouse می‌نشینند.
- **data-lineage** کاری می‌کند `record_source` یک vault در عمل مفید باشد.
- **star-snowflake-obt** شکل martهایی را مقایسه می‌کند که روی هر کدام از این روش‌ها می‌سازی.
