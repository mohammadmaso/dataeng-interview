## 🎯 خلاصه

> یک **index** (ایندکس) ساختار مرتب‌شده‌ی جداگانه‌ای است که به دیتابیس اجازه می‌دهد ردیف‌ها را بدون خواندن کل جدول پیدا کند. ایندکس خواندن را سریع‌تر می‌کند، نوشتن را کندتر، و فضای دیسک هم می‌گیرد.

- ایندکس پیش‌فرض بیشتر دیتابیس‌های OLTP یک **B-tree** است: درخت متوازن با کلیدهای مرتب، که حتی برای میلیون‌ها ردیف با چند خواندن صفحه جواب می‌دهد.
- یک **index ترکیبی** روی `(a, b)` به کوئری‌هایی که روی `a` فیلتر می‌کنند، یا روی `a` و `b` کمک می‌کند. به کوئری‌ای که فقط روی `b` فیلتر می‌کند کمک نمی‌کند.
- یک **covering index** همه‌ی ستون‌های لازم کوئری را دارد، پس دیتابیس می‌تواند فقط از خود ایندکس جواب بدهد.
- هر ایندکس با هر insert و با هر update روی ستون‌هایش به‌روز می‌شود. ایندکس بیشتر یعنی نوشتن کندتر.

## 🌱 از ساده شروع کنیم (مبتدی)

> **💡 تشبیه:** ایندکس انتهای یک کتاب درسی. برای پیدا کردن «window function» فهرست (مرتب و کوتاه) را می‌خوانی و به صفحه‌ی ۲۱۲ می‌پری. بدون فهرست باید همه‌ی ۶۰۰ صفحه را بخوانی. ایندکس یک کتاب کوچک‌تر و مرتب است که به کتاب اصلی اشاره می‌کند، و هر بار که صفحه‌ای اضافه می‌کنی باید آن را هم به‌روز کنی.

برای کل این درس از این جدول استفاده کن:

```sql
CREATE TABLE orders (
  id          bigint PRIMARY KEY,
  customer_id int NOT NULL,
  status      text NOT NULL,        -- 'open', 'paid', 'shipped'
  created_at  timestamp NOT NULL,
  amount      numeric(10,2) NOT NULL
);
```

بدون ایندکس روی `customer_id`، این کوئری کل جدول را می‌خواند (**sequential scan** یا اسکن ترتیبی):

```sql
SELECT id, amount FROM orders WHERE customer_id = 42;
```

با یک ایندکس، دیتابیس مستقیم به ردیف‌ها می‌رود:

```sql
CREATE INDEX idx_orders_customer ON orders (customer_id);
```

هزینه را هم در نظر بگیر. ایندکس داده‌ی اضافه است که باید همیشه با جدول هماهنگ بماند. کوئری‌ای که روی `customer_id` فیلتر یا مرتب‌سازی نمی‌کند هیچ سودی نمی‌برد، و هر insert همچنان هزینه‌ی به‌روزرسانی ایندکس را می‌پردازد.

## 🔧 واقعاً چطور کار می‌کند (متوسط)

### B-tree

B-tree درختی متوازن از **صفحه‌ها** (block، در PostgreSQL معمولاً ۸ کیلوبایت) است. هر صفحه‌ی داخلی کلیدهای مرتب و اشاره‌گر به صفحه‌های فرزند دارد. صفحه‌های برگ کلیدها و یک اشاره‌گر به ردیف جدول را نگه می‌دارند (در PostgreSQL به آن **TID** می‌گویند).

برای جدولی با ۱۰ میلیون ردیف و حدوداً ۴۰۰ کلید در هر صفحه، عمق درخت حدود ۳ است: `log400(10,000,000) ≈ 2.9`. یک جستجو حدود ۳ صفحه‌ی ایندکس و ۱ صفحه‌ی جدول می‌خواند. اسکن کامل همه‌ی صفحه‌های جدول را می‌خواند.

چون B-tree مرتب است، این موارد را هم پشتیبانی می‌کند:

- برابری: `WHERE customer_id = 42`
- بازه: `WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01'`
- مرتب‌سازی: `ORDER BY created_at` (اگر ترتیب ایندکس با ORDER BY یکی باشد، مرحله‌ی sort اضافه نمی‌شود)
- تطبیق پیشوندی: `WHERE name LIKE 'Ali%'`، ولی **نه** `LIKE '%Ali'`

### ایندکس ترکیبی و ترتیب ستون‌ها

```sql
CREATE INDEX idx_orders_cust_created ON orders (customer_id, created_at);
```

ایندکس اول بر اساس `customer_id` و بعد داخل هر مشتری بر اساس `created_at` مرتب است. این قانون **پیشوند چپ (leftmost-prefix)** را می‌دهد:

| کوئری | استفاده‌ی خوب از ایندکس؟ | چرا |
|---|---|---|
| `WHERE customer_id = 42` | بله | پیشوند `customer_id` |
| `WHERE customer_id = 42 AND created_at >= '2026-01-01'` | بله | هر دو ستون، بازه روی ستون دوم |
| `WHERE created_at >= '2026-01-01'` | معمولاً نه | ستون اول نیست، پس ردیف‌های مطابق در کل درخت پراکنده‌اند |
| `WHERE customer_id = 42 ORDER BY created_at` | بله | ردیف‌ها از قبل مرتب‌اند |

ستون‌های **برابری** را اول و ستون **بازه** را آخر بگذار. ایندکس `(created_at, customer_id)` یک بازه‌ی تاریخ را اسکن می‌کند و برای هر ردیف `customer_id` را چک می‌کند، که خیلی کم‌انتخاب‌گرتر است.

### covering index و index-only scan

```sql
-- کوئری فقط customer_id و amount را لازم دارد
CREATE INDEX idx_orders_cover ON orders (customer_id) INCLUDE (amount);

SELECT customer_id, amount FROM orders WHERE customer_id = 42;
```

`INCLUDE` (از PostgreSQL نسخه‌ی ۱۱) ستون‌های اضافه را در صفحه‌های برگ ذخیره می‌کند، بدون اینکه جزو کلید جستجو باشند. اگر همه‌ی ستون‌های لازم در ایندکس باشند، PostgreSQL می‌تواند **index-only scan** انجام دهد و جدول را رد کند. این کار فقط برای ردیف‌هایی ممکن است که در **visibility map** به‌عنوان قابل‌دیدن علامت خورده‌اند، و این نقشه را `VACUUM` نگه می‌دارد. روی جدولی با آپدیت‌های زیاد، planner ممکن است برای بعضی ردیف‌ها باز هم سراغ جدول برود.

### ایندکس جزئی (partial index)

```sql
CREATE INDEX idx_orders_open ON orders (customer_id) WHERE status = 'open';
```

این ایندکس فقط ردیف‌هایی را دارد که با `WHERE` می‌خوانند. کوچک است، نوشتنش ارزان است، و فقط وقتی استفاده می‌شود که planner بتواند ثابت کند شرط کوئری یعنی `status = 'open'`. کوئری با `WHERE status = 'open'` از آن استفاده می‌کند؛ کوئری بدون فیلتر وضعیت، نه.

### انواع ایندکس در PostgreSQL

| نوع | مناسب برای | مثال معمول |
|---|---|---|
| B-tree (پیش‌فرض) | برابری، بازه، مرتب‌سازی | `id`، `created_at` |
| GIN | هر ردیف چند مقدار دارد: آرایه، `jsonb`، جست‌وجوی متنی کامل | `WHERE tags @> '{vip}'` |
| GiST | هندسه، بازه، نزدیک‌ترین همسایه، محدودیت exclusion | `WHERE period && '[2026-01-01,2026-02-01)'` |
| BRIN | جدول‌های خیلی بزرگ که مقدارها با ترتیب فیزیکی هم‌راستاست | جدول لاگ زمان‌دار |

**BRIN** (Block Range INdex) کمترین و بیشترین مقدار هر گروه از صفحه‌های جدول را ذخیره می‌کند. خیلی کوچک است، ولی فقط وقتی مفید است که ستون با ترتیب فیزیکی ردیف‌ها هم‌بسته باشد، مثل `event_time` در جدولی که فقط append می‌شود.

## 🧠 عمق و trade-offها (سنیور)

- **تقویت نوشتن (write amplification).** یک insert هم جدول را و هم **همه‌ی** ایندکس‌ها را به‌روز می‌کند. آپدیتی که یک ستون ایندکس‌شده را عوض کند، یک ورودی جدید در ایندکس می‌سازد. آپدیت‌های HOT در PostgreSQL (heap-only tuple) وقتی ستون ایندکس‌شده‌ای عوض نشده و جای کافی در صفحه هست، تغییر ایندکس را رد می‌کنند. پنج ایندکس روی یک جدول داغ می‌تواند نوشتن را چند برابر کندتر کند نسبت به یک ایندکس.
- **کم‌انتخاب‌گری (selectivity) مهم است.** اگر یک شرط حدود ۴۰٪ ردیف‌ها را مطابقت دهد، planner معمولاً اسکن ترتیبی را ترجیح می‌دهد: جستجوی تصادفی ایندکس برای این تعداد ردیف از خواندن مرتب جدول گران‌تر است. ایندکس وقتی بیشترین کمک را می‌کند که شرط انتخاب‌گر باشد.
- **Clustered در برابر non-clustered.** در InnoDB (MySQL) خود جدول B-tree کلید اصلی است (clustered). ایندکس ثانویه کلید اصلی را ذخیره می‌کند، پس جستجو از طریق آن دو بار درخت را طی می‌کند. در PostgreSQL، heap بی‌ترتیب است و همه‌ی ایندکس‌ها non-clustered هستند. دستور `CLUSTER` جدول را یک‌بار مرتب می‌کند؛ بعد از آن نگه‌داری نمی‌شود.
- **OLAP متفاوت است.** انبارهای داده و موتورهای ستونی (ClickHouse، StarRocks، Redshift، BigQuery، Snowflake) به ذخیره‌ی مرتب، zone map (کمینه و بیشینه‌ی هر بلاک) و partition pruning تکیه می‌کنند، نه به B-tree های زیاد. ClickHouse یک **sparse primary index** دارد: یک ورودی برای هر بلاک از ردیف‌ها که بر اساس کلید `ORDER BY` جدول مرتب است. قبل از طراحی ایندکس، مستندات موتور خودت را ببین؛ مکانیزم‌ها فرق دارند.
- **پایش.** دنبال ایندکس‌های استفاده‌نشده باش (`pg_stat_user_indexes.idx_scan` مدت طولانی نزدیک صفر) و bloat ایندکس بعد از آپدیت‌های سنگین. هر ایندکس بی‌استفاده فقط هزینه‌ی نوشتن است.
- **کی ایندکس نسازیم.** جدول‌های کوچک (اسکن کامل چند صفحه ارزان‌تر است)، ستون‌های با تنوع خیلی کم به‌تنهایی (یک boolean با ۵۰ به ۵۰)، و جدول‌های staging پرنوشتن که فقط یک بار خوانده می‌شوند.

## 🧪 امتحان کن

از PostgreSQL نسخه‌ی ۱۳ به بعد استفاده کن. جدول `orders` بالا را بساز و با `generate_series` یک میلیون ردیف وارد کن.

1. قبل و بعد از `CREATE INDEX idx_orders_customer ON orders (customer_id);` این را اجرا کن: `EXPLAIN SELECT id, amount FROM orders WHERE customer_id = 42;`. نوع اسکن را در هر دو پلن توضیح بده.
2. ایندکس `(customer_id, created_at)` را بساز. کدام کوئری‌ها از آن استفاده‌ی خوب می‌کنند: (الف) `WHERE created_at > now() - interval '7 days'`، (ب) `WHERE customer_id = 42 AND created_at > now() - interval '7 days'`؟
3. یک partial index برای `status = 'open'` بساز و توضیح بده چرا کوئری با `WHERE status = 'paid'` از آن استفاده نمی‌کند.

<details><summary>راه‌حل‌ها را نشان بده</summary>

**۱.** قبل: `Seq Scan on orders`. بعد: `Index Scan using idx_orders_customer` (یا `Bitmap Heap Scan` اگر ردیف‌های زیادی مطابقت کنند). تعداد ردیف‌های خوانده‌شده از یک میلیون به ردیف‌های آن مشتری کم می‌شود.

**۲.** (الف) از `(customer_id, created_at)` به‌خوبی استفاده نمی‌کند: ستون اول نیست. (ب) به‌خوبی استفاده می‌کند: برابری روی ستون اول و بازه روی ستون دوم. اگر کوئری‌هایی مثل (الف) مهم‌اند، ایندکس جدا روی `(created_at)` بساز.

**۳.** partial index فقط ردیف‌های `status = 'open'` را دارد. کوئری `'paid'` به ردیف‌هایی نیاز دارد که ایندکس ندارد، پس planner نمی‌تواند از آن استفاده کند.

</details>

## 💬 گوشه‌ی مصاحبه

**سؤال: «چرا با وجود ایندکس روی این ستون، کوئری‌ام کند است؟»** جواب متوسط: «ببین کوئری اصلاً می‌تواند از ایندکس استفاده کند: تابع روی ستون، پیشوند چپ اشتباه، یا کم‌انتخاب‌گری. بعد `EXPLAIN ANALYZE` بزن.» جواب سنیور: «اول پلن را نگاه می‌کنم. اگر جدول را می‌خواند، شکل شرط (sargability)، ترتیب ستون‌های ترکیبی، تازگی آمار، و فاصله‌ی تخمین ردیف planner با تعداد واقعی را چک می‌کنم. بعد ایندکس را با هزینه‌ی نوشتن روی آن جدول می‌سنجم.»

**سؤال: «آیا باید هر ستونی را که در WHERE می‌آید ایندکس کنم؟»** نه. هر ایندکس نوشتن را کند می‌کند و فضا می‌گیرد. مسیرهای دسترسی کوئری‌های مهم را ایندکس کن، با پلن تأیید کن، و ایندکس‌های بی‌استفاده را حذف کن.

> **🎤 این را در مصاحبه بگو:** «ایندکس یک کپی مرتب از چند ستون است که به دیتابیس اجازه می‌دهد ردیف‌ها را رد کند. ترتیب ستون‌ها را از کوئری می‌گیرم: برابری اول، بازه آخر. وقتی بخواهم index-only scan داشته باشم ستون‌های `INCLUDE` اضافه می‌کنم، و همیشه هزینه‌ی نوشتن روی جدول را هم حساب می‌کنم.»

## ⚠️ اشتباهات رایج

> **⚠️ مراقب باش:** فرض کنی ایندکس ترکیبی `(a, b)` به کوئری‌ای که فقط روی `b` فیلتر می‌کند کمک می‌کند. معمولاً نمی‌کند، چون B-tree اول بر اساس `a` مرتب است.

> **⚠️ مراقب باش:** روی یک ستون ایندکس بسازی و بعد آن را داخل تابع ببری. `WHERE DATE(created_at) = '2026-01-01'` نمی‌تواند از ایندکس `created_at` استفاده کند. آن را به بازه بنویس: `WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'`.

- ساختن ایندکس برای همه‌ی ستون‌ها «برای احتیاط». هر ایندکس در هر نوشتن هزینه دارد.
- گذاشتن ستون بازه اول در ایندکس ترکیبی، که ستون‌های بعدی را برای فیلتر تقریباً بی‌فایده می‌کند.
- فراموش کردن اینکه `LIKE '%text'` (wildcard اول) نمی‌تواند از B-tree استفاده کند. اگر لازم است، ایندکس GIN با `pg_trgm` بساز.
- انتظار index-only scan بدون `VACUUM` اخیر. visibility map باید به‌روز باشد.
- باور اینکه ایندکس همیشه استفاده می‌شود. planner بر اساس هزینه تصمیم می‌گیرد؛ کم‌انتخاب‌گری یا جدول کوچک می‌تواند اسکن ترتیبی را سریع‌تر کند.

## ✅ خودت را بسنج

۱. جدولی `INDEX (country, city)` دارد. کدام کوئری بیشترین سود را می‌برد؟
   - A) `WHERE city = 'Tehran'`
   - B) `WHERE country = 'IR' AND city = 'Tehran'`
   - C) `WHERE city LIKE 'Teh%'`
   - D) `WHERE id = 7`

<details><summary>جواب</summary>

**B** — هر دو ستون با ترتیب ایندکس می‌خوانند (برابری روی ستون اول، برابری روی ستون دوم). A نمی‌تواند از ستون اول استفاده کند، پس ایندکس کمکی ندارد. C پیشوند روی `city` است، که ستون اول نیست. D از کلید اصلی استفاده می‌کند، نه از این ایندکس.

</details>

۲. می‌خواهی `SELECT customer_id, amount FROM orders WHERE customer_id = ?` بدون دست زدن به جدول اجرا شود. ایندکس درست کدام است؟
   - A) `(amount)`
   - B) `(customer_id) INCLUDE (amount)`
   - C) `(customer_id, amount, id)` در هر سفارش
   - D) یک ایندکس GIN روی `amount`

<details><summary>جواب</summary>

**B** — کلید جستجو `customer_id` است و `amount` در برگ ذخیره می‌شود تا index-only scan ممکن شود. A روی `customer_id` فیلتر نمی‌کند. D برای داده‌ی چندمقداری است، نه این کوئری.

</details>

۳. کوئری `WHERE DATE(created_at) = '2026-01-01'` با وجود ایندکس روی `created_at` کند است. راه‌حل چیست؟
   - A) اضافه کردن `DESC` به ایندکس
   - B) بازنویسی به بازه‌ی نیم‌باز روی خود `created_at`
   - C) بالا بردن `work_mem`
   - D) جایگزین کردن B-tree با ایندکس hash

<details><summary>جواب</summary>

**B** — تابع روی ستون ایندکس را پنهان می‌کند. بازه‌ی نیم‌باز (از اول روز تا قبل از روز بعد) باعث می‌شود ایندکس استفاده شود. A تغییری نمی‌دهد و C و D مشکل تابع روی ستون را حل نمی‌کنند.

</details>

۴. (سنیور) جدول `orders` ۵۰٬۰۰۰ insert در ثانیه می‌گیرد، ۶ ایندکس دارد، و ۳ تا از آن‌ها ۹۰ روز است که صفر اسکن داشته‌اند. توصیه‌ی تو چیست و چرا؟
   - A) دو ایندکس دیگر اضافه کنم تا نوشتن سریع‌تر شود
   - B) بعد از اطمینان از اینکه پنجره‌ی آماری یک چرخه‌ی کامل کسب‌وکار را پوشش داده و هیچ constraint به آن‌ها نیاز ندارد، آن‌ها را حذف کنم
   - C) جدول را به partial index تبدیل کنم
   - D) همه‌ی ستون‌ها را BRIN کنم

<details><summary>جواب</summary>

**B** — ایندکس بی‌استفاده فقط هزینه‌ی نوشتن و فضا دارد. قبل از حذف مطمئن شو پنجره‌ی آماری یک چرخه‌ی کامل را دیده (جاب‌های ماهانه ممکن است هفته‌ها بی‌استفاده به نظر برسند) و ایندکس‌هایی که کلید اصلی یا unique constraint را پشتیبانی می‌کنند نگه داری. A هزینه را بالا می‌برد. C و D بار نوشتن را کم نمی‌کنند.

</details>

۵. چرا ساختن `CREATE INDEX` روی یک جدول بزرگ در production نیاز به دقت دارد؟
   - A) روی جدولی که داده دارد نمی‌شود ایندکس ساخت
   - B) `CREATE INDEX` معمولی هنگام ساخت، نوشتن روی جدول را قفل می‌کند؛ PostgreSQL گزینه‌ی `CREATE INDEX CONCURRENTLY` را دارد که طولانی‌تر است و داخل بلاک تراکنش اجرا نمی‌شود
   - C) ایندکس‌ها همیشه هنگام خواندن از نو ساخته می‌شوند
   - D) ایندکس فقط در حافظه ذخیره می‌شود

<details><summary>جواب</summary>

**B** — ساخت معمولی قفلی می‌گیرد که نوشتن را متوقف می‌کند. `CONCURRENTLY` این قفل را کم می‌کند، با هزینه‌ی کار بیشتر و مراحل اضافه اگر وسط کار خطا بدهد. A و C نادرست‌اند، و D هم غلط است چون ایندکس روی دیسک است.

</details>

## 🗂️ فلش‌کارت

| رو | پشت |
|---|---|
| ایندکس B-tree چیست؟ | درخت متوازن و مرتب از صفحه‌ها که کلید را در چند خواندن پیدا می‌کند؛ پیش‌فرض PostgreSQL و بیشتر OLTP |
| قانون پیشوند چپ | ایندکس `(a, b)` برای فیلتر روی `a` یا `a` و `b` مفید است، نه برای `b` به‌تنهایی |
| covering index | ایندکسی که همه‌ی ستون‌های لازم کوئری را دارد، پس جدول خوانده نمی‌شود (index-only scan) |
| `INCLUDE` چه می‌کند؟ | ستون‌های اضافه را در برگ ذخیره می‌کند بدون اینکه کلید جستجو شوند (PostgreSQL نسخه‌ی ۱۱+) |
| partial index | ایندکس روی زیرمجموعه‌ای از ردیف‌ها که با `WHERE` تعریف می‌شود |
| BRIN | کمینه و بیشینه‌ی هر بازه‌ی بلاک را ذخیره می‌کند؛ کوچک، مناسب جدول بزرگ با ترتیب فیزیکی هم‌بسته |
| چرا ایندکس نوشتن را کند می‌کند؟ | هر insert و هر update روی ستون ایندکس‌شده باید همه‌ی ایندکس‌ها را هم به‌روز کند |
| چرا `DATE(col) = ...` از ایندکس استفاده نمی‌کند؟ | تابع ستون را پنهان می‌کند؛ آن را به بازه‌ی روی ستون خام بنویس |
