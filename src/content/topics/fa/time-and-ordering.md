## 🎯 خلاصه

> ساعت‌های ماشین‌های مختلف با هم توافق ندارند و پیام‌ها زمان متغیری می‌گیرند. پس «قبل از» باید بر اساس **علیت (causality)** تعریف شود (چه چیزی می‌توانسته روی چه چیزی تأثیر بگذارد)، نه بر اساس timestamp چاپ‌شده روی یک رویداد. سیستم‌های توزیع‌شده ترتیب قابل اعتماد را از **ساعت‌های منطقی**، از **یک لاگ واحد**، یا از **عدم قطعیت کراندار ساعت** می‌گیرند، و هر کدام محدوده‌ی خودشان را دارند.

- **ساعت‌های فیزیکی** (ساعت دیواری که با NTP همگام می‌شود) drift و skew دارند. حتی ممکن است به عقب بپرند. هرگز فقط با آن‌ها رویدادهای چند ماشین را مرتب نکن.
- **Lamport clock** یک شمارنده می‌دهد که علیت را رعایت می‌کند، اما عدد کوچک‌تر ثابت نمی‌کند که آن رویداد زودتر بوده.
- **Vector clock** تشخیص می‌دهد دو رویداد علّی به هم مربوط‌اند یا **هم‌زمان (concurrent)**.
- **Hybrid logical clock (HLC)** یک timestamp نزدیک به زمان فیزیکی نگه می‌دارد و در عین حال علیت را رعایت می‌کند.
- در سیستم‌های داده، ترتیب قابل اعتماد معمولاً **ترتیب داخل یک partition یا یک لاگ** است (offset در Kafka، موقعیت لاگ در دیتابیس). بین partitionها ترتیب سراسری وجود ندارد.

## 🌱 از ساده شروع کنیم (مبتدی)

> **💡 Analogy:** سه دوست روی کاغذ یادداشت می‌نویسند، و هرکدام یک ساعت مچی دارند که چند ثانیه اختلاف دارد. یادداشتی که با ساعت ۱۰:۰۰:۰۵ مهر خورده ممکن است قبل از یادداشتی نوشته شده باشد که با ۱۰:۰۰:۰۳ مهر خورده، چون ساعت‌ها با هم فرق دارند. برای مرتب کردن واقعی، باید بدانی کی چه چیزی را **بعد از خواندن** چه چیزی نوشته. «این را بعد از خواندن یادداشت تو نوشتم» قابل اعتمادتر از هر ساعتی است.

یک شکست مشخص: دو سرور رویدادهای یک کاربر را ثبت می‌کنند:

```text
server A clock: 10:00:05.200  -> event "order placed"
server B clock: 10:00:04.900  -> event "payment captured"

Sorted by timestamp:  payment captured, then order placed
Real order:           order placed, then payment captured
```

مرتب‌سازی بر اساس timestamp پرداخت را قبل از سفارش گذاشت. ساعت‌ها چند صد میلی‌ثانیه با هم فاصله داشتند، که بدون همگام‌سازی دقیق عادی است. پایپ‌لاینی که به این timestampها اعتماد کند، داستان اشتباهی می‌سازد.

پس به‌جایش چه کنیم؟ یا یک **شماره‌ی توالی** که یک منبع واحد صادر می‌کند (مثلاً موقعیت لاگ دیتابیس)، یا ساعتی که **گام‌های علّی** را می‌شمارد، نه ثانیه‌ها.

## 🔧 واقعاً چطور کار می‌کند (متوسط)

### دو نوع زمان روی یک ماشین

- **زمان ساعت دیواری** (time of day) با NTP تنظیم می‌شود؛ NTP پروتکلی است که ماشین‌ها را با سرورهای زمان همگام می‌کند. دقت معمول در یک شبکه‌ی محلی خوب میلی‌ثانیه است و روی ماشین‌های شلوغ یا بد پیکربندی‌شده بدتر می‌شود. وقتی NTP آن را اصلاح می‌کند، ساعت ممکن است به عقب بپرد.
- **زمان monotonic** هرگز به عقب نمی‌رود، اما بین ماشین‌ها معنایی ندارد. برای اندازه‌گیری مدت زمان روی یک ماشین استفاده‌اش کن.

timestampهای ساعت دیواری برای «تقریباً کی» و داشبوردهای انسانی خوب‌اند. برای «کدام زودتر بود» ضعیف‌اند.

### Lamport clock

هر پروسه یک شمارنده‌ی `L` نگه می‌دارد:

۱. قبل از هر رویداد محلی، `L = L + 1`.
۲. هنگام ارسال پیام، `L` فعلی را ضمیمه کن.
۳. هنگام دریافت پیامی با مقدار `m`، `L = max(L, m) + 1` بگذار.

مثال کار‌شده با سه پروسه:

```text
P1: a (L=1) ---- send m (L=2) ------------------+
P2: c (L=1)                                    |
P2: receive m -> L = max(1, 2)+1 = 3   <-------+   event r
P2: d (L=4)
P3: e (L=1)
```

تضمین: اگر `a` (از نظر علّی) قبل از `b` رخ داده باشد، آن‌گاه `L(a) < L(b)`. عکس این درست نیست: `L(e) = 1` و `L(a) = 1` چیزی درباره‌ی این‌که `a` و `e` به هم مربوط‌اند نمی‌گوید. عددهای Lamport یک ترتیب کلی سازگار می‌دهند (با شناسه‌ی پروسه برای تساوی‌ها)، اما این ترتیب می‌تواند رویدادهای هم‌زمان را به ترتیبی بگذارد که هرگز رخ نداده.

### Vector clock

هر پروسه یک بردار با یک شمارنده برای هر پروسه نگه می‌دارد. هر رویداد خانه‌ی خودش را افزایش می‌دهد. پیام‌ها کل بردار را حمل می‌کنند و گیرنده بیشینه‌ی المان‌به‌المان را می‌گیرد و سپس خانه‌ی خودش را افزایش می‌دهد.

```text
P1: a -> [1,0,0]     send to P2
P2: b -> [1,1,0]     (received [1,0,0], then increments P2)
P3: d -> [0,0,1]     no contact with P1 or P2

Compare a=[1,0,0] with b=[1,1,0]: a <= b element-wise -> a happened before b
Compare a=[1,0,0] with d=[0,0,1]: neither <= the other -> concurrent
```

Vector clockها به سؤال «آیا این‌ها هم‌زمان‌اند؟» جواب می‌دهند، که Lamport نمی‌تواند. هزینه‌اش این است که بردار با تعداد پروسه‌ها بزرگ می‌شود؛ به همین دلیل در گروه‌های کوچک استفاده می‌شوند، مثلاً مخزن‌های replicated که تاریخچه‌ی نسخه را نگه می‌دارند (سیستم‌های سبک Dynamo)، نه برای میلیون‌ها کلاینت.

### Hybrid logical clock

یک timestamp از نوع HLC یک زوج است: یک بخش فیزیکی نزدیک به ساعت دیواری محلی، و یک شمارنده‌ی منطقی که تساوی‌ها را می‌شکند و وقتی ساعت‌های فیزیکی عقب‌اند علیت را حفظ می‌کند. مقدار HLC هم زمان قابل‌خواندن است و هم رویدادهای علّی را مرتب می‌کند. دیتابیس‌هایی مثل CockroachDB از timestampهای سبک HLC برای multi-version concurrency control استفاده می‌کنند.

### عدم قطعیت کراندار: TrueTime

Google Spanner مسیر دیگری دارد. API به نام TrueTime یک بازه‌ی `[earliest, latest]` برمی‌گرداند که زمان واقعی را محدود می‌کند و با GPS و ساعت‌های اتمی ساخته شده است. یک تراکنش قبل از این‌که قابل دیدن شود، عدم قطعیت را صبر می‌کند (commit wait)، پس تراکنش‌های بعدی timestampهای بزرگ‌تر می‌گیرند. این external consistency می‌دهد، اما سخت‌افزار و زیرساخت ویژه می‌خواهد که اغلب تیم‌ها ندارند.

### Event time، ingestion time و processing time

برای داده‌ی جریانی سه زمان مهم است:

| زمان | معنی | مثال |
|---|---|---|
| Event time | زمانی که در منبع رخ داده | ضربه‌ی کارت روی گیت |
| Ingestion time | زمانی که broker یا gateway دریافتش کرده | `LogAppendTime` در Kafka |
| Processing time | زمانی که job تو آن را پردازش می‌کند | لحظه‌ای که پنجره بسته می‌شود |

پنجره‌ها باید بر اساس event time باشند. watermarkها (ببین [[watermark]]) به موتور می‌گویند event time تا کجا پیش رفته، و [[late-arriving-data]] چیزی است که بعد از آن نقطه می‌رسد. processing time نتایجی می‌دهد که به شلوغی کلاستر بستگی دارند و بازتولیدشان سخت است.

### ترتیب در Kafka

Kafka رکوردها را **داخل یک partition** مرتب می‌کند. offset موقعیت در لاگ همان partition است و هر consumer آن partition همان ترتیب را می‌بیند. رکوردهایی با کلید یکسان (با partitioner پیش‌فرض) به همان partition می‌روند، پس ترتیب هر key در آن partition حفظ می‌شود. بین partitionها ترتیبی وجود ندارد. producerی که idempotence دارد ترتیب را در تلاش‌های مجدد داخل یک partition حفظ می‌کند (تعداد درخواست‌های in-flight را در تنظیمات client بررسی کن). ببین [[kafka-architecture]] و [[kafka-producers]].

## 🧠 عمق و trade-offها (سنیور)

- **با device time مرتب نکن.** کلاینت‌های موبایل و IoT ساعت‌های غیرقابل اعتماد دارند که گاهی ساعت‌ها اشتباه‌اند. device time را به‌عنوان event time ذخیره کن، زمان دریافت سرور را به‌عنوان ingestion time، و رویدادهایی را که device time‌شان با زمان دریافت فاصله‌ی زیادی دارد علامت بزن. صریح تصمیم بگیر کدام‌یک پنجره‌هایت را هدایت می‌کند.
- **لاگ را منبع حقیقت کن.** برای CDC، موقعیت لاگ خود دیتابیس (LSN در PostgreSQL، موقعیت binlog در MySQL) ترتیب واقعی commitهاست. timestampهای داخل ردیف‌ها ممکن است با آن یکی نباشند، مخصوصاً برای تراکنش‌های طولانی که دیرتر از شروعشان commit می‌شوند. ببین [[cdc]].
- **سؤال‌های بین partitionها.** «کدام رویداد بین دو partition زودتر رخ داد؟» از Kafka به‌تنهایی جواب ندارد. به یک کلید علّی (موجودیت یکسان در یک partition)، یک شماره‌ی توالی از producer، یا یک store که نسخه صادر می‌کند نیاز داری.
- **باگ‌های skew ساعت.** نشانه‌ها: ردیف‌هایی که «قبل از» ساخته شدنشان تغییر کرده‌اند، مدت‌های منفی، پنجره‌های dedup که تکراری‌ها را نمی‌بینند، و تعارض‌های last-write-wins که نوشته‌ی اشتباه برنده می‌شود. offset NTP را روی هر host اندازه بگیر و برایش alert بگذار.
- **last-write-wins یک تصمیم ساعتی است.** LWW تعارض‌ها را با timestamp حل می‌کند. وقتی ساعت‌ها اختلاف دارند، بی‌صدا نوشته‌ها را دور می‌ریزد. فقط وقتی استفاده کن که از دست رفتن یک به‌روزرسانی قابل قبول است، یا از version vector استفاده کن و ادغام را به application بسپار.
- **داده‌ی دیررسیده و watermark.** watermark خیلی تهاجمی رویدادهای دیررسیده‌ی معتبر را دور می‌ریزد. watermark خیلی شل state را برای همیشه نگه می‌دارد. allowed lateness را از توزیع تأخیر اندازه‌گیری‌شده انتخاب کن، نه از حدس.
- **چه چیزی را پایش کنی.** offset ساعت هر host، event-time lag (زمان فعلی منهای بیشترین event time پردازش‌شده)، watermark lag، سهم رویدادهای دیررسیده، و نرخ ناهم‌ترتیبی به‌ازای هر key.

## 💬 گوشه‌ی مصاحبه

**سؤال: «چطور رویدادها را بین ماشین‌ها مرتب می‌کنی؟»**

- متوسط: «فقط به timestampهای ساعت دیواری اعتماد نمی‌کنم. از یک توالی از یک منبع واحد استفاده می‌کنم، مثل offset لاگ یا موقعیت commit دیتابیس، یا اگر علیت لازم است، یک ساعت منطقی.»
- سنیور: «ترتیب به محدوده وابسته است. داخل یک partition یا یک لاگ واحد، offset همان ترتیب است. بین partitionها به یک کلید علّی یا نسخه نیاز دارم. برای تحلیل بر اساس event time، event time را صریح انتخاب می‌کنم، با watermark و allowed lateness مشخص، و offset ساعت هر host را پایش می‌کنم، چون skew بی‌صدا پنجره‌های dedup و last-write-wins را خراب می‌کند.»

**سؤال: «تفاوت Lamport و vector clock چیست؟»** Lamport شمارنده‌ای می‌دهد که علیت را در یک جهت رعایت می‌کند. vector clock می‌تواند بگوید دو رویداد هم‌زمان‌اند.

> **🎤 Say this in the interview:** «timestampهای ماشین‌های مختلف تخمین‌اند، نه یک ترتیب. ترتیب را از یک لاگ واحد، از علیت، یا از عدم قطعیت کراندار می‌گیرم. برای استریمینگ، event time را صریح انتخاب می‌کنم و برای داده‌ی دیررسیده طراحی می‌کنم.»

## ⚠️ اشتباهات رایج

> **⚠️ Watch out:** «همه‌ی سرویس‌ها را بر اساس `created_at` مرتب کن، ترتیب واقعی به دست می‌آید.» skew ساعت و commitهای دیررس این را خراب می‌کنند.

> **⚠️ Watch out:** «Kafka ترتیب را برای کل topic تضمین می‌کند.» فقط داخل یک partition تضمین می‌کند.

- استفاده از processing time برای پنجره‌ها، که باعث می‌شود نتایج با بار کلاستر تغییر کنند.
- استفاده از `time.time()` برای اندازه‌گیری مدت زمان. از ساعت monotonic استفاده کن.
- فرض این‌که timestamp Lamport علیت را در هر دو جهت نشان می‌دهد.
- فراموش کردن این‌که ساعت دستگاه‌های موبایل و سنسورهای IoT می‌تواند خیلی اشتباه باشد.
- یکی گرفتن ingestion time با event time، که داده‌ی دیررسیده را در پنجره‌ی اشتباه می‌گذارد.

   - D) timestampها تا ۱ میلی‌ثانیه با زمان فیزیکی برابرند

<details><summary>Answer</summary>

**B** — ترتیب علّی یک مقدار Lamport کوچک‌تر می‌دهد. عکس آن درست نیست، پس عدد کوچک‌تر علیت را ثابت نمی‌کند.

</details>

3. یک topic در Kafka با ۶ partition دارد. یک consumer دو رویداد با یک کلید سفارش را در یک partition می‌خواند. کدام گزاره درست است؟
   - A) ترتیب در کل topic تضمین شده است
   - B) رویدادها به ترتیب offset آن partition می‌رسند
   - C) ترتیب تصادفی است چون timestampها استفاده نمی‌شوند
   - D) هر consumer group آن‌ها را بر اساس event time دوباره مرتب می‌کند

<details><summary>Answer</summary>

**B** — ترتیب داخل یک partition همان ترتیب offset است، و با partitioner پیش‌فرض کلید یکسان همیشه به همان partition می‌رود. بین partitionها ترتیبی وجود ندارد.

</details>

4. **(سنیور)** یک پایپ‌لاین جدول «آخرین وضعیت هر سفارش» را با گرفتن ردیفی با بزرگ‌ترین `updated_at` از یک استریم CDC می‌سازد. گاهی یک وضعیت قدیمی، وضعیت جدید را بازنویسی می‌کند. علت محتمل و راه‌حل چیست؟
   - A) Kafka پیام‌ها را می‌اندازد
   - B) timestampهای سرورهای برنامه skew دارند، یا یک تراکنش طولانی با `updated_at` قدیمی دیرتر commit شده؛ ترتیب را بر اساس موقعیت لاگ دیتابیس منبع (LSN یا offset binlog) بگذار، یا یک ستون نسخه که دیتابیس افزایش می‌دهد استفاده کن
   - C) کلید اصلی وجود ندارد
   - D) راه‌حل اضافه کردن partition بیشتر است

<details><summary>Answer</summary>

**B** — فیلد ساعت دیواری ترتیب commit نیست. موقعیت لاگ دیتابیس منبع ترتیب واقعی commitهاست، پس از آن استفاده کن، یا از نسخه‌ای که هنگام نوشتن به‌صورت صعودی تعیین می‌شود.

</details>

5. **(سنیور)** چرا TrueTime اسپنر نیاز به commit wait دارد، و تیمی که چنین سخت‌افزاری ندارد چه کار می‌کند؟
   - A) برای پنهان کردن latency شبکه از کلاینت‌ها
   - B) API یک بازه‌ی عدم قطعیت گزارش می‌دهد و تراکنش صبر می‌کند تا timestampش قطعاً در گذشته باشد، پس تراکنش‌های بعدی timestampهای بزرگ‌تر می‌گیرند؛ تیم‌های بدون این سخت‌افزار به موقعیت لاگ، ستون نسخه یا دیتابیسی تکیه می‌کنند که ترتیب را برایشان مدیریت می‌کند
   - C) برای اجرای backup
   - D) اگر ساعت‌ها با NTP همگام باشند، commit wait لازم نیست

<details><summary>Answer</summary>

**B** — ساعت تا یک میزان کراندار عدم قطعیت دارد. صبر کردن برای آن عدم قطعیت تضمین می‌کند تراکنش بعدی نمی‌تواند timestamp قدیمی‌تری بگیرد. تیم‌های بدون این زیرساخت به موقعیت لاگ، نسخه، یا دیتابیسی تکیه می‌کنند که ترتیب را برایشان حل می‌کند.

</details>

## 🗂️ فلش‌کارت

| Front | Back |
|---|---|
| ساعت دیواری در برابر ساعت monotonic | ساعت دیواری برای زمان روز است و ممکن است بپرد؛ monotonic فقط مدت‌زمان را روی یک ماشین اندازه می‌گیرد |
| تضمین ساعت Lamport | ترتیب علّی یعنی timestamp کوچک‌تر؛ timestamp کوچک‌تر علیت را ثابت نمی‌کند |
| vector clock چه اضافه می‌کند؟ | رویدادهای هم‌زمان را تشخیص می‌دهد، نه فقط ترتیب را |
| HLC | timestampی شبیه زمان فیزیکی به‌علاوه‌ی شمارنده‌ی منطقی؛ علیت را حفظ می‌کند |
| event time در برابر ingestion time | زمان رخ دادن در منبع در برابر زمانی که سیستم دریافت کرده |
| محدوده‌ی ترتیب در Kafka | داخل یک partition، بر اساس offset؛ بین partitionها نه |
| چرا به device time نمی‌شود اعتماد کرد؟ | ساعت گوشی و IoT می‌تواند خیلی اشتباه باشد |
| ایده‌ی TrueTime | بازه‌ی عدم قطعیت کراندار به‌علاوه‌ی commit wait |
