## به زبان ساده (مبتدی)
مدرسه به هر دانش‌آموز یک شماره‌ی جدید می‌دهد که ربطی به نام یا تاریخ تولدش ندارد. اگر نامش عوض شود شماره همچنان معتبر است. کلید جانشین چنین شناسه‌ای در جدول انبار داده است: عددی ساختگی که یک سطر را مشخص می‌کند تا انبار به شناسه‌های نامرتب سیستم‌های دیگر وابسته نباشد.

## نحوه‌ی کار (متوسط)
در مدل‌سازی ابعادی، هر سطر dimension یک کلید جانشین می‌گیرد (دنباله‌ی عددی یا hash قطعی) که کلید join از fact است. شناسه‌ی اصلی مبدأ به‌عنوان کلید طبیعی/کسب‌وکار به‌صورت یک ستون می‌ماند.

```
CREATE TABLE dim_customer (
  customer_sk   BIGINT PRIMARY KEY,   -- surrogate
  customer_id   VARCHAR,              -- business/natural key
  name          VARCHAR,
  valid_from    DATE,
  valid_to      DATE,
  is_current    BOOLEAN
);
-- fact rows reference customer_sk, not customer_id
```

دلیل استفاده: انبار را از تغییر کلید مبدأ یا برخورد بین سیستم‌ها جدا می‌کند؛ SCD نوع ۲ را ممکن می‌کند (چند نسخه از یک مشتری، هرکدام با کلید خودش)؛ joinهای روی عدد باریک ارزان‌اند؛ و سطرهای ویژه مثل `-1 = Unknown` برای dimension دیررس یا مفقود را ممکن می‌سازد. کلیدهای مبتنی بر hash (مثلاً از کلید کسب‌وکار به‌علاوه‌ی نسخه) در pipelineهای توزیع‌شده رایج‌اند چون موازی و بدون sequence مرکزی ساخته می‌شوند.

## نگاه سنیور و نکات مصاحبه
مصالحه‌ها: sequence نیاز به هماهنگی دارد و بارگذاری موازی/backfill را سخت می‌کند (کلیدها باید در اجرای مجدد پایدار باشند؛ از hash قطعی یا جدول lookup استفاده کنید) و بارگذاری fact یک مرحله‌ی lookup کلید می‌خواهد. برخورد hash نظریاً ممکن است، پس hash عریض بگیرید. کلید جانشین را به‌عنوان شناسه‌ی کسب‌وکار در معرض مصرف‌کننده نگذارید. در stackهای ELT/lakehouse (dbt) تابع `generate_surrogate_key` از کلیدهای طبیعی hash می‌سازد. در سیستم‌های ستونی کلید طبیعی پهن آن‌قدر ارزان است که بعضی تیم‌ها برای dimensionهای بدون SCD کلید جانشین نمی‌سازند.

سؤال مصاحبه: «چرا fact را مستقیم با شناسه‌ی مبدأ join نکنیم؟» پاسخ: شناسه‌ی مبدأ ممکن است تغییر کند، بین سیستم‌ها برخورد کند و نسخه‌ی تاریخی را نشان نمی‌دهد؛ کلید جانشین join پایدار، نسخه‌دار و فشرده می‌دهد و جایی برای عضو نامشخص.
