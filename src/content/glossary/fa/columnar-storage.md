## به زبان ساده (مبتدی)
دفترچه‌ی تلفن نام، آدرس و شماره را برای هر نفر کنار هم می‌نویسد (سطرمحور). ذخیره‌ی ستونی همه‌ی شماره‌ها را در یک فهرست و همه‌ی نام‌ها را در فهرستی دیگر می‌گذارد. اگر فقط جمع همه‌ی شماره‌ها را بخواهید همان یک فهرست را می‌خوانید و بقیه را رها می‌کنید؛ پس پرسش‌های مربوط به چند ستون خیلی سریع‌تر می‌شوند.

## نحوه‌ی کار (متوسط)
کوئری‌های تحلیلی معمولاً چند ستون از جدول‌های بسیار پهن ولی سطرهای زیادی را لمس می‌کنند. در ذخیره‌ی ستونی هر ستون در بلوک پیوسته‌ی خودش است، پس کوئری فقط ستون‌های لازم را می‌خواند. همسایه‌های هم‌نوع فوق‌العاده خوب فشرده می‌شوند (dictionary، run-length، delta) و موتورها داده را به صورت batchهای vectorized پردازش می‌کنند که از cache پردازنده و SIMD خوب استفاده می‌کند.

```
Row store:     [id1,name1,amt1] [id2,name2,amt2] [id3,name3,amt3]
Column store:  ids:[id1,id2,id3]  names:[name1,name2,name3]  amts:[amt1,amt2,amt3]

SELECT SUM(amt) FROM sales;   -- column store reads only the amts block
SELECT * FROM sales WHERE id=2; -- row store reads one contiguous record
```

نمونه‌ها: فایل‌های Parquet/ORC، ClickHouse، StarRocks، Redshift، BigQuery، DuckDB، Snowflake. ذخیره‌ی سطری (PostgreSQL، MySQL) برای OLTP برنده است: خواندن یا به‌روزرسانی کل یک رکورد یک جا را لمس می‌کند.

## نگاه سنیور و نکات مصاحبه
هزینه‌ها: بازسازی سطر کامل خواندن چند فایل ستونی می‌خواهد، insert/update تک‌سطری گران است (برای همین بافر، partهای به سبک LSM، delta store و فایل تغییرناپذیر به‌علاوه‌ی merge) و point lookup به index یا primary index تُنُک نیاز دارد. ترتیب sort اهرم بزرگ در ClickHouse و Parquet خوشه‌بندی‌شده است: داده‌ی sort‌شده بر اساس ستون‌های فیلتر رایج بهتر فشرده می‌شود و data skipping را ممکن می‌کند. late materialization (اول فیلتر روی چند ستون، سپس خواندن ستون‌های دیگر فقط برای سطرهای منطبق) بهینه‌سازی کلیدی است.

سؤال مصاحبه: «چرا `SELECT *` در column store بد است؟» پاسخ: مجبور می‌شود همه‌ی ستون‌ها خوانده و decode شوند و مزیت اصلی از بین می‌رود؛ فقط ستون‌های لازم را انتخاب کنید تا موتور بقیه را رد کند و بایت خیلی کمتری بخواند.
